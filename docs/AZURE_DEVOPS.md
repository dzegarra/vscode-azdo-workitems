# Azure DevOps REST API — what we use and what we learned

Findings verified against our organization (`ABB-PAMA-BVL`, project `Flow Digital Architecture`). API version `7.1` unless noted. All calls go through `AzdoClient` (`src/azdoClient.ts`) → `recordedFetch` (`src/requestRecorder.ts`).

When you use a new endpoint or find that something here is wrong, update this file in the same change (developers and AI agents alike); write down only what you verified.

## Authentication and exploring

- The extension uses the VS Code Microsoft sign-in: `vscode.authentication.getSession('microsoft', ['499b84ac-1321-427f-aa17-267ca6975798/.default'])` (that GUID is the Azure DevOps resource).
- To explore read-only from a terminal: `az rest --resource 499b84ac-1321-427f-aa17-267ca6975798 --url "https://dev.azure.com/ABB-PAMA-BVL/Flow%20Digital%20Architecture/_apis/<path>&api-version=7.1"`. Only GET; never write to production data while testing.
- Signed-in user id: `GET https://dev.azure.com/{org}/_apis/connectionData` → `authenticatedUser.id` (same GUID as reviewers / `System.AssignedTo.id`).

## Work items

- My work items: WIQL `POST wit/wiql` (`[System.AssignedTo] = @Me` and the iteration paths), then `GET wit/workitems?ids=…&$expand=relations` (max 200 ids per call; `fields=` cannot be combined with `$expand`).
- Teams I belong to: `GET {org}/_apis/projects/{project}/teams?$mine=true`; current iteration of a team: `GET {project}/{team}/_apis/work/teamsettings/iterations?$timeframe=current` (404 when none). The response already carries the sprint dates in `attributes`: `startDate` / `finishDate` are **midnight UTC of the first and last days** (Platform Sprint 123: `2026-10-14T00:00:00Z` → `2026-10-27T00:00:00Z`, a Wednesday to a Tuesday), plus `timeFrame: "current"`; compare only the date part (verified 2026-10-21).
- Relations (`src/workItemLinks.ts`): parent/children `System.LinkTypes.Hierarchy-Reverse/Forward`; predecessors/successors `System.LinkTypes.Dependency-Reverse/Forward`; duplicates `System.LinkTypes.Duplicate-Reverse` (name "Duplicate Of": the work item holding it is the duplicate) / `System.LinkTypes.Duplicate-Forward` (name "Duplicate": held by the original), topology `tree`, so a duplicate has at most one original (names and topology verified with `GET {org}/_apis/wit/workitemrelationtypes`; the direction follows the reverse name "Duplicate Of", the same convention as `Hierarchy-Reverse` = Parent, not yet checked on a real duplicate); branches `ArtifactLink` `vstfs:///Git/Ref/{projectId}%2F{repoId}%2FGB{branch}`; PRs `vstfs:///Git/PullRequestId/{projectId}%2F{repoId}%2F{prId}`.
- Dates of the work item (verified 2026-10-25 on #66280, no extra request: they come with `GET wit/workitems?$expand=relations`): `Microsoft.VSTS.Common.ActivatedDate` (first move to an active state), `Microsoft.VSTS.Common.StateChangeDate` (last state change), `System.ChangedDate`, `System.CreatedDate`. The full history of state changes would be `GET wit/workitems/{id}/updates` (not used: one request per work item). The Sprint timeline starts the coding span at `ActivatedDate`.
- **A query as of a moment** (verified 2026-10-28 on Platform Sprint 122): WIQL accepts `ASOF '2026-10-27T23:59:59Z'` at the end, after `ORDER BY`, for `@Me` and for `[System.AssignedTo] IN ('name@abb.com', …)`; the response echoes `"asOf"`. It returns what matched at that moment: the user's items (tasks included) in Sprint 122 (30 Sep – 13 Oct) were 41 as of 14 Oct 08:00 UTC and 19 from 14 Oct 08:48 on, when the unfinished ones were moved to Sprint 123 (#66900, a task: `System.IterationPath` 122 → 123 at 2026-10-14T08:48Z). The team moves the unfinished work on the first morning of the next sprint, so the end of the last day (UTC) still sees it in the sprint that ended. `GET wit/workitems?ids=…&$expand=relations&asOf=…` is accepted (no error with both); that its `relations` are those of that moment is not checked yet. In a WIQL body sent from bash the backslashes of an iteration path are written `\\\\` (bash, then JSON).
- **"Ever in an iteration"** (verified 2026-10-28 on Platform Sprint 123): WIQL accepts `[System.IterationPath] EVER '<path>'` (no `ASOF`): it returns the work items that had that iteration path in any revision, before the sprint started included. On Sprint 123: 5 of the user's Backlog Items and Bugs at its close (`ASOF` its last day), 16 with `EVER`, every one of the 5 among them. The other conditions (`[System.AssignedTo] = @Me`) apply to the current revision, not to the revision that had the path.
- **Updates of a work item** (`GET wit/workItems/{id}/updates`, verified 2026-10-28 on #67145): each update has `rev` and the fields it changed as `fields."<ref>".oldValue` / `.newValue`; the moment is `fields."System.ChangedDate".newValue`. The first update creates the work item (`oldValue` absent, e.g. its first `System.IterationPath`). The Sprint timeline reads `System.State` changes from it (TIMELINE-35).
- Field names: the form label "Integrated in Build" is the API field "Integration Build" (`Microsoft.VSTS.Build.IntegrationBuild`); `src/alerts.ts` resolves names, form labels and reference names.
- Rich text images are attachments that need the token: the Work Item Details panel downloads them and embeds them as data URIs (only for URLs of the organization).
- Iteration tree with dates: `GET wit/classificationnodes/Iterations?$depth=…` (cached a few minutes). Paths come as `\Project\Iteration\…`; work items use `Project\…`.
- States per type (`GET wit/workitemtypes/{type}`, `states` and `transitions`; verified 2026-10-24): **Product Backlog Item** New, Approved (Proposed), Committed (InProgress), Done (Completed), Removed. **Bug** New, Approved, ReOpened (Proposed), Committed, Ready-to-Test (InProgress), Done (Completed), Removed; any state can move to any other, so the "testers only" rules (Done, Bug creation) are team rules, not enforced by the process. Note: Azure DevOps puts Ready-to-Test in the InProgress category while the extension counts it as finished (STATE-2).

## Pull requests

- Reviewed history (verified read-only, org ABB-PAMA-BVL, 2026-10): `git/pullrequests?searchCriteria.reviewerId=<id>&searchCriteria.status=all&$top=N` returns `reviewers[]` with `vote` (10, 5, 0, -5, -10, `hasDeclined`) and, for completed/abandoned PRs, `closedDate`. It is ordered by creation date (newest first) and mixes in the user's own PRs (13 of 50). `$top=50` reached back only ~3 weeks (50 PRs from 2026-09-22), `$top=100` ~11 weeks (since 2026-07-27): 43 of those 100 were reviewed by me (39 completed, 2 active, 2 abandoned), 13 closed in the last 30 days. We use 100; a PR created before the oldest listed one but closed within the window is missed.
- Lists: `git/pullrequests?searchCriteria.creatorId=…` / `searchCriteria.reviewerId=…` (also returns the user's own PRs as reviewer), `searchCriteria.status=active|completed|all`, `$top`.
- **Labels (tags) come only in the list response** (`labels: [{ name, active }]`, absent when none); `GET git/pullrequests/{id}` does not return them.
- `completionOptions` (`deleteSourceBranch`, `transitionWorkItems`, `mergeStrategy`) and `autoCompleteSetBy` (auto-complete on) are in both list and single responses.
- Reviewers: `vote` (10 approved, 5 with suggestions, 0 none, -5 waiting for author, -10 rejected), `isRequired` (absent when false), `isContainer` (groups), `hasDeclined`. The author appears as a reviewer.
- **Policy evaluations** (the "what blocks the merge"): `GET policy/evaluations?artifactId=vstfs:///CodeReview/CodeReviewId/{projectId}/{prId}&api-version=7.1-preview.1` — **plain 7.1 is refused**. Fields: `status` (queued, running, approved, rejected, notApplicable, broken), `configuration.isBlocking`, `configuration.type.displayName` (Minimum number of reviewers, Required reviewers, Comment requirements, Work item linking, Require a merge strategy, Build, Status), `configuration.settings` (`minimumApproverCount`, `creatorVoteCounts`, build `displayName`).
- Linked work items of a PR: `git/repositories/{repo}/pullRequests/{id}/workitems` (ids only).
- **Commits of a PR** (verified read-only, org ABB-PAMA-BVL, User_Interface, 2026-10-25): `GET git/repositories/{repo}/pullRequests/{id}/commits?api-version=7.1` returns `{ count, value: [{ commitId, author: { name, email, date }, committer: { name, email, date }, comment, url }] }`, **newest first**; dates are ISO UTC without fractions (`2026-10-23T07:42:32Z`). `$top` works (`count` follows it), **`$skip` is ignored**; the next page comes with the response header `x-ms-continuationtoken`, sent back as the query parameter `continuationToken` (verified with `$top=1` on a PR of 2 commits). The default page size (100) is the documented one, not verified. The author date is what the extension uses for the first commit (the committer date changes on rebase and cherry-pick); in the PRs checked both were equal.
- Retarget a PR: `PATCH git/repositories/{repo}/pullrequests/{id}` `{ "targetRefName": "refs/heads/develop" }` (unverified: implemented from the API reference, to be confirmed in real use). A branch has a completed PR: `GET …/pullrequests?searchCriteria.sourceRefName=refs/heads/<b>&searchCriteria.status=completed&$top=1`.
- Publish a draft: `PATCH git/repositories/{repo}/pullrequests/{id}` `{ "isDraft": false }`. Add a tag: `POST git/repositories/{repo}/pullRequests/{id}/labels` `{ "name": "…" }`; create with tags: `labels: [{ name }]` in the create body (fallback POST if not echoed).
- **Ahead / behind a branch** (verified read-only, org ABB-PAMA-BVL, 2026-10-24): `GET git/repositories/{repo}/stats/branches?name=<branch>&baseVersionDescriptor.version=<base>&baseVersionDescriptor.versionType=branch&api-version=7.1` → `{ aheadCount, behindCount, … }` (branch names without `refs/heads/`, URL-encoded). One request per branch; it does not depend on the PR, so the `lastMergeTargetCommit` of the PR (the target commit Azure DevOps last merged with) says nothing about how far the target moved since.
- Restart the merge of a PR ("Restart merge" of the web UI): `PATCH git/repositories/{repo}/pullrequests/{id}` `{ "mergeStatus": "queued" }` (unverified: implemented from the API reference and community reports, to be confirmed in real use). Azure DevOps only recomputes `mergeStatus` (conflicts) on a push, a completion or this.
- Complete a PR: `PATCH git/repositories/{repo}/pullrequests/{id}` `{ "status": "completed", "lastMergeSourceCommit": { "commitId": "<the head the user saw>" }, "completionOptions": { "mergeStrategy": "squash", "deleteSourceBranch": true, "transitionWorkItems": false } }` (unverified: from the API reference, to be confirmed in real use). The commit id makes Azure DevOps refuse the completion if somebody pushed in between; no `mergeCommitMessage` keeps the default `Merged PR <id>: <title>`.

- **Whole-team queries** (verified read-only, org ABB-PAMA-BVL, 2026-10-25): `GET _apis/projects/{project}/teams?$mine=true` returns the teams of the user (7 here). `GET {project}/{team}/_apis/work/teamsettings/iterations?$timeframe=current` returns the current sprint of a team (`attributes.startDate`, `finishDate`, `timeFrame`); each team has its own path (`…\\MVP R3\\Platform Sprint 123`). `POST wit/wiql` with `[System.WorkItemType] IN ('Product Backlog Item','Bug') AND [System.State] <> 'Removed' AND [System.IterationPath] IN (…)` and no assignee filter returned 128 work items for two teams (21 assignees, 3 unassigned) in one request; `GET wit/workitems?ids=…&$expand=relations&errorPolicy=Omit` gives them in batches of 200 (those 128 items have 331 child links: 2 more batches). `System.AssignedTo` is an object with `displayName`, `uniqueName` and `id` (the identity id; verified equal to `connectionData.authenticatedUser.id` for the signed-in user). **One listing of all the active PRs of the project**: `GET git/pullrequests?searchCriteria.status=active&$top=200` (no repository in the path) returned all 63 active PRs of every repository (11 repositories) with `reviewers[]` (votes, `isRequired`), `isDraft`, `mergeStatus`, `creationDate`, `createdBy` and `lastMergeSourceCommit.commitId`; `$skip` pages it (verified: `$top=5&$skip=5` returned the same PRs as items 6 to 10 of `$top=10`). The 96 PRs linked to those items and their tasks were 20 active and 76 closed; closed ones need `GET {project}/_apis/git/pullrequests/{id}` once each (they never change).

### Threads (`git/repositories/{repo}/pullRequests/{id}/threads`)

- Text comments: first comment `commentType: 'text'`; deleted comments have `isDeleted: true` and no content. Thread `status`: active, pending, fixed, wontFix, closed, byDesign. **Who changes a status is not recorded.**
- System threads (`properties.CodeReviewThreadType.$value`):
  - `IsDraftUpdate` with `CodeReviewIsDraftNowSet` `"0"` = **published** ("X published the pull request."), `"1"` = back to draft. The latest one with "0" is the publication date.
  - `ReviewersUpdate`: actor `CodeReviewReviewersUpdatedByIdentity`, target `…AddedIdentity` / `…RemovedIdentity` / `…ChangedIdentity` (+ `…ChangedToRequired`), referring to keys of the thread's `identities` map; groups have `isContainer: true`. Self-join: Added = By; decline: Removed = By and content "declined".
  - `VoteUpdate` (`CodeReviewVoteResult`), `RefUpdate` (`CodeReviewRefNewCommitsCount`), `AutoCompleteUpdate`, `StatusUpdate` (completed), `PolicyStatusUpdate` (noise, skipped).
  - **What the Sprint timeline reads from them** (verified read-only on 15 completed PRs and 2 active ones of `User_Interface`, org ABB-PAMA-BVL, 2026-10-25; counts per PR: 6 to 20 threads): `VoteUpdate` has `CodeReviewVoteResult` (`"10"`, `"5"`, `"-5"`, `"-10"`, `"0"` to reset) and `CodeReviewVotedByIdentity` = a key of that thread's own `identities` map (the keys are "1", "2"… and mean different people in different threads), whose `displayName` is the voter (the comment says "<name> voted 10"); `ReviewersUpdate` has `CodeReviewReviewersUpdatedNumAdded` / `NumRemoved` / `NumChanged` (a change to required or optional has `…ChangedToRequired`), and one thread per reviewer added (a PR that added 4 reviewers had 4 threads within about 40 seconds); `RefUpdate` has `CodeReviewRefNewCommits` (`;`-separated ids) and `CodeReviewRefNewHeadCommit`; `AutoCompleteUpdate` has `CodeReviewAutoCompleteNowSet` (`"1"`); `StatusUpdate` has `CodeReviewStatus` (`Completed`); text comment threads have no `CodeReviewThreadType`, their `status` and the first comment's `commentType: 'text'`. **`PolicyStatusUpdate` only covers the work item link and required-reviewer policies, not the CI**: the CI history comes from the builds (below).
  - **There is no history of conflicts**: only the current `mergeStatus` of the PR (`conflicts`) is available, and Azure DevOps recomputes it on a push, a completion or a restart of the merge. The timeline draws a conflicts mark at now for an open PR that has them and nothing in the past.
- Link to a thread in the browser: `<PR web URL>?discussionId={threadId}`.

## Git refs and diffs

- **`refs?filter=heads/<branch>` matches by prefix** (`heads/feature/a` also returns `heads/feature/ab`): compare names exactly. Each ref has `objectId` and `creator` (the branch owner).
- Delete a remote branch: `POST git/repositories/{repo}/refs` `[{ name, oldObjectId, newObjectId: "0000…0000" }]` (refused if someone pushed since `oldObjectId`).
- **Did a PR change a file?** `GET git/repositories/{repo}/diffs/commits?baseVersion={lastMergeTargetCommit}&baseVersionType=commit&targetVersion={lastMergeSourceCommit}&targetVersionType=commit&diffCommonCommit=true&$top=2000` → `changes[].item.path`, `allChangesIncluded`. The "commits by itemPath" API gave false positives: do not use it. Paths start with `/`, and the list also has entries for the **folders** of the changed files (e.g. `/build-notes` next to `/build-notes/pid-notes.md`), so match files by name, not by prefix alone.
- Repository by id: `GET git/repositories/{id}` (names of other repositories, cached).

## Builds, tests, coverage

- PR runs: `build/builds?branchName=refs/pull/{id}/merge&$top=…&queryOrder=queueTimeDescending`; keep the latest per pipeline. **The same query without that reduction is the whole CI history of the PR** (verified read-only, 2026-10-25, 4 PRs: 1, 2, 3 and 4 runs; every push queues one run per pipeline about a second after the `RefUpdate` thread, `queueTime` ≤ `startTime` < `finishTime`, `result` seen: `succeeded` and `failed`; `partiallySucceeded` and `canceled` come from the API reference, not seen in these PRs): the Sprint timeline asks it with `$top=100` for the PRs of an expanded row. `sourceVersion` is the merge commit of the run, not the head of the PR, and `triggerInfo` has only `pr.number` and `pr.triggerRepository`: a run belongs to the latest push when it starts after it. Web URL in `_links.web.href`; tests tab: `&view=ms.vss-test-web.build-test-results-tab`.
- Runs of one repository: `repositoryId={id}&repositoryType=TfsGit` (both needed; without them the pipelines of the other repositories come too, e.g. `RMC_WORKSPACE_DEV`). `requestedFor={userId}`, `reasonFilter=manual` or `individualCI,batchedCI`, `minTime={ISO date}` all filter server-side. Each build has `reason` (`pullRequest`, `manual`, `individualCI`…) and `sourceBranch`.
- **Post-merge runs**: `reason=individualCI` (or `batchedCI`), `requestedBy` = `Microsoft.VisualStudio.Services.TFS`, `requestedFor` = whoever completed the PR (not necessarily its author), and `triggerInfo["ci.message"]` = `Merged PR 13837: <title>` (plus `ci.sourceSha`, `ci.sourceBranch`). Manual runs have `triggerInfo: {}` and `requestedBy` = the user.
- Runs of the base branch (alarm of a broken develop): `build/builds?branchName=refs/heads/develop&repositoryId={id}&repositoryType=TfsGit&$top=50&queryOrder=queueTimeDescending` (unverified on our organization: built like the PR runs query, which uses the same `branchName` filter; to be confirmed with real data).
- Why a run failed: `build/builds/{id}/timeline` → failed `Task` records by `order`; ignore tasks named "Publish…" (publishing hiccups are not the cause).
- **Per-person whole-team queries** (verified read-only, org ABB-PAMA-BVL, 2026-10-25): `GET {org}/_apis/projects/{project}/teams/{teamId}/members?$top=1000&api-version=7.1` returns `{ count, value: [{ identity: { id, displayName, uniqueName, imageUrl, descriptor… } }] }` (no admin flag in this response); 7 teams gave 78 memberships, 31 distinct people (so deduplicate by `identity.id`). `identity.id` is the same id as `System.AssignedTo.id` of the work items. In WIQL, `[System.AssignedTo] IN ('<uniqueName>', …)` works (3 people: 10 items in the current Platform sprint, per-person counts 7 and 3 and nobody else), and so does the display name (same 10 items) or `'Display Name <uniqueName>'`; **an identity id (`'60675883-…'`) is accepted but matches nothing (0 items, no error)**, so never query by id. `1=1` is not valid WIQL (`Expecting field name`): do not build an empty condition, skip the query instead. Quotes in names are doubled like in any WIQL string.
- **PRs completed in a period, one listing for the project** (verified read-only, 2026-10-25): `GET {project}/_apis/git/pullrequests?searchCriteria.status=completed&searchCriteria.queryTimeRangeType=closed&searchCriteria.minTime=2026-10-14T00:00:00Z&$top=200&api-version=7.1` returned the 68 PRs closed since the start of the sprint of every repository of the project (all `completed`, `closedDate` from 2026-10-14T07:30 on); without `minTime`/`queryTimeRangeType` the same call returns the 200 latest by creation (back to 2026-09-22), so the filter works. `$top=30&$skip=30` returns the second page (distinct from the first: `$skip` pages it). The items carry `closedDate`, `reviewers`, `lastMergeSourceCommit`, `repository`, but not `webUrl` (built from the repository name). It replaces `GET git/pullrequests/{id}` per merged PR (76 requests at once on the first version).
- PR responses (`git/pullrequests`) include `creationDate` and, once completed or abandoned, `closedDate` (ISO); the draft → published moment is only in the `IsDraftUpdate` system threads (`publishedAt` in `src/pullRequestTimeline.ts`).
- Test runs: `test/runs?buildUri=vstfs:///Build/Build/{id}`; failed count from `test/runs/{runId}/statistics` (`unanalyzedTests` is not reliable); failing tests `test/runs/{runId}/results?outcomes=Failed&$top=5` (error messages contain ANSI codes and Storybook boilerplate to strip).
- **Coverage summary lives on another host**: `https://vstmr.dev.azure.com/{org}/{project}/_apis/testresults/codecoverage?buildId={id}&api-version=7.1-preview.1` → `coverageData[].coverageStats` ("Lines": covered/total, `delta` = percentage points vs the previous build of the PR, `isDeltaAvailable`); `coverageDetailedSummaryStatus: noModulesFound` = no coverage. Per file: `test/codecoverage?buildId={id}&flags=7&api-version=7.1-preview.1` (`linesNotCovered` absent when 0). Cache only finalized results.

## Packages

- Azure Artifacts has its own host: `https://feeds.dev.azure.com/{org}/{project}/_apis/packaging/Feeds/{feed}/packages?protocolType=UPack&packageNameQuery=…&includeAllVersions=true` (the name query also matches longer names: compare exactly). Used for "Integrated in Build" (`rmc.image.deploy` in feed `bison_deployimage_rmc`).

## Throttling

- Azure DevOps throttles with HTTP 429 and/or `Retry-After`, `X-RateLimit-Resource`, `X-RateLimit-Delay`, `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset` headers. The recorder flags them; "Show Azure DevOps Usage" reports requests per feature, per minute, errors and throttling.
