# Decisions

Why the extension behaves the way it does. Each entry: the decision, and the reason (often a team rule or something learned about Azure DevOps). Add an entry when you make a choice someone could later "fix" without knowing why, and correct or remove the entries a change makes wrong — in the same change (developers and AI agents alike).

## Team rules

The extension enforces or supports these team rules; many features exist because of them.

| Rule                                                                                                                                                                                                           | Where the extension helps                                                                                                          |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Branches are named `<feature\|bugfix>/<module>/<id>-<short-name>` (Backlog Item → `feature`, Bug → `bugfix`)                                                                                                   | Create branch; branch ↔ work item detection (`src/naming.ts`)                                                                      |
| PR titles follow `[<ids>] <Feature Name>: <description>`                                                                                                                                                       | Create PR; warning on published PRs                                                                                                |
| Every PR has a short description, at least 2 required reviewers (people, not groups) and a linked Backlog Item or Bug                                                                                          | Warnings on My Pull Requests cards                                                                                                 |
| No PR waits for its reviewers more than 24 hours                                                                                                                                                               | "Waiting for your review" box, status bar, reminders, daily digest                                                                 |
| Branches are deleted once their PR is merged                                                                                                                                                                   | Delete branch for branches of completed PRs; warning when auto-complete does not delete the branch                                 |
| Only testers complete Bugs                                                                                                                                                                                     | Red error when a Bug PR's auto-complete would complete the linked Bug                                                              |
| Changes testers should know about are explained in a build notes file (`build-notes/*-notes.md`, one per feature); PRs without such changes get the tag `no-build-notes`                                       | Build notes warning, "Add tag" button, check in Create PR                                                                          |
| Completing a work item whose predecessors are not done should be agreed with their owners                                                                                                                      | Open predecessors on the cards (one caution with the other completion issues), dependency map                                      |
| Each PR has its own PR task: In Progress while the PR is in review, Done when it is completed (the task stands for "in review": Backlog Items and Bugs have no such state)                                     | Create PR creates / links it, Publish starts it, completion notification offers Done, alerts                                       |
| Alerts (Done with open tasks, missing PR task, blocking tags, empty required fields, Integrated in Build when Ready to Test, task branch not linked to its work item, duplicate out of sync with its original) | Alerts on the cards, banner, badge, status bar                                                                                     |
| A duplicate ("Duplicate Of" link) is planned in the same iteration as its original and both are in the same state                                                                                              | Red alerts on both sides of the pair (Rules ALERT-9, ALERT-10), **Open** the other one; duplicate cards toned down, Dups filter    |
| The branch of a task is also linked to its Backlog Item or Bug (Development section)                                                                                                                           | Alert "Branch … of task … is not linked to this work item" with the **Link branch** quick fix; Create branch for a task links both |
| "Integrated in Build" of a Bug Ready to Test = last published `rmc.image.deploy` version + `+`                                                                                                                 | Fill button and proposal when moving to Ready to Test                                                                              |

## Scope and data

- **Only the user's work items** ("Assigned to Me", "My Work Items"), in the **current iteration of every team the user belongs to** (`teams?$mine=true`), unless teams are selected. Teams sharing a sprint are merged; different sprints are grouped.
- **Tasks are never cards of their own** nor filter values: they are parts of their Backlog Item / Bug, always nested in its card (including tasks assigned to other developers, with their initials). Tasks are not shown in the dependency map and get no "Dependency map" button.
- **Filters apply to Backlog Items and Bugs only**; nested tasks are never filtered. Work items with alerts follow the filters unless `filter.alwaysShowAlerts` (default off: the banner says how many are hidden and "Show only these" reveals them).
- **Several branches per work item**: named after it, Development links, source branches of its active PRs. The **main branch** (checked out, else named after it, else the link) drives the card's buttons; each other branch of this repository has its own Checkout. Finished work items list only their deletable branches (completed PR, see below) and other _local_ branches, because remote refs and links outlive deleted branches.
- **Delete branch is offered when the branch's PR is completed, not when the work item is finished**: the team deletes a branch once its PR is merged, and the state of the work item says little about it (a Backlog Item with several PRs stays Active while its first branch is already merged; a Done one may have been merged without a PR from the extension). A branch is deletable when (1) it exists in this repository, locally and/or in Azure DevOps, (2) a PR with `sourceRefName = refs/heads/<branch>` is `completed`, and (3) no PR from that branch is still `active` (a new PR may have been opened from it). Abandoned PRs do not count; the work item state is neither required nor blocking. `develop`, `main`, `master` and `release/*` are never offered, even if a PR used them as source. The rule is pure (`src/deletableBranches.ts`) and applies per branch to the branches of a work item (all of them, not only the main one) and of a task. PRs come from the ones already fetched for the cards (linked PRs); the command checks again with Azure DevOps (branch, active PR, completed PR) because the list can be minutes old. Existence is only asked to Azure DevOps for branches with a completed PR that are not local, through the same 10-minute cache as the task branches (`forgetBranch` after a deletion). Offered: branch rows (a **Delete** each), the card button only when exactly one branch is deletable (like Checkout, a card button would be ambiguous), the task pill menu (danger item; tasks of other developers do not get it), the command palette (lists them all), and the notification of one of my PRs being completed, merged with the existing offer to set its task Done (one notification; `myPullRequests.notifications` `merged` or `taskDone` enabled). Finished work items with no completed-PR branch list only their local branches and say "No branch to delete": whether the main branch still exists is no longer asked for them.
- **Branch existence is asked to Azure DevOps** (`refs?filter=`), not trusted from local `origin/*` refs or Development links, which stay after a branch is deleted.
- **PRs / branches of other repositories** are shown dimmed; only this repository's PRs decide whether "Create PR" is offered.
- **Fixed-by links**: a Bug is "fixed by" a Backlog Item when the Backlog Item is its **predecessor** (some Bugs are really missing features). The reverse direction is just a dependency.
- **Duplicates** (`src/duplicates.ts`, alerts in `src/alerts.ts`). The work item holding the "Duplicate Of" link (`Duplicate-Reverse`) is the duplicate, the other end the original. Team rule: the two are planned in the same iteration and move through the same states. Decisions: (1) it is a **red alert**, not an amber caution, because it is a team rule to fix, so it counts in the badge, the status bar and the Summary, and skips the filters with `filter.alwaysShowAlerts`; (2) the states must be **the same state** (spelling-tolerant, STATE-1), not only the same category, and it is the **real** state that counts, never the shown "In review" (STATE-10), which would flag pairs whose Azure DevOps states are identical; (3) **both sides** get the alert, so an original in the list warns about a duplicate assigned to someone else, and a pair where both are in the list counts twice (each breaks the rule); (4) **unknown means silent**: the related work items come with the predecessors / successors in the same batched request (no extra request), and the ones that could not be loaded say nothing (a false red alert costs more than a missed one); (5) the quick fix only **opens** the other work item, as which side to move is the developers' call; (6) a duplicate's card is **toned down** (dashed left bar, faded title only, so the buttons and the popovers inside keep their contrast) because the work is tracked on the original, but not while it has an alert, which must stand out; (7) the Dups filter only has a "Duplicates" chip (hiding the originals makes no sense) and only appears when some card is a duplicate. Like every alert they only apply to `alerts.workItemTypes` (ALERT-GATE).
- **Startup waits for the git extension.** The built-in git extension announces a repository before its state is loaded: on a cold start `state.remotes` is empty for a while, so the organization / project / repository could not be detected and every first load failed until the next poll (about 2 minutes). `WorkItemsStore.whenRepositoryReady()` (`src/repositoryGate.ts`, decision in the pure `src/repositoryReadiness.ts`) resolves when the git API is `initialized` and the repository has remotes, or at once when `totalflowx.organization/project/repository` are all set. It gives up after 30 s so a repository that really has no `origin` still gets the clear error. During the wait the sidebar shows "Loading…" and nothing records or shows an error. The store loads, the pollers, the status bar, the Work Item Details panel and the dependency map await it before `resolveContext`, and so do the commands (the `command()` helper of `src/extension.ts`), so running one in the first seconds after a cold start waits instead of failing.

## Reviews and pull requests

- **Completed PRs of "My Pull Requests" are listed for a chosen period** (`totalflowx.myPullRequests.completedPeriod`: hidden / 24 h / 7 days / 30 days; default 24 h). The latest 50 completed PRs are fetched in one request. Completed PRs barely change, so their threads (for the timeline popover) are fetched **once per PR, only while it is inside the period**, and cached in the watcher (entries of PRs no longer returned are dropped); this keeps the request budget low even with 30 days. Completed PRs outside the period cost no requests. Only active PRs get policies, runs and build notes.
- **Build notes are a folder of files, one per feature** (`build-notes/*-notes.md`, since User_Interface PR 13922): a single `developer-notes.md` edited by every PR caused merge conflicts, so the team split it and the build notes tool merges the files. Changing **any** of them satisfies the rule (the extension does not try to tell which feature a PR belongs to). Only files directly in the folder whose name ends with `totalflowx.buildNotes.fileSuffix` count, as the tool globs them: `_template.md` (copied to start a feature) and subfolders do not. `developer-notes.md` still matches the suffix, so branches from before the split still count. The old `totalflowx.buildNotes.path` setting was replaced by `directory` + `fileSuffix` (a new key, so a saved file path is ignored rather than read as a folder). Create PR's "I'll write the notes" lets the user pick the file (with the feature name of its first `# ` heading) instead of opening a fixed one.
- **Waiting time counts from the publication** of the PR (last time it left draft, from the `IsDraftUpdate` system thread), not its creation: reviewers are not asked to review drafts.
- **Phases of a completed PR** (`src/pullRequestPhases.ts`; mini timeline, "took" and the header summary of "My Pull Requests"). Computed from the system threads already cached for the timeline popover, so no extra requests. Phases cover creation to completion without gaps: **draft** (created as draft until published, and again whenever re-drafted), **review**, shown as "In review" (from publication, or from a push after "waiting for author", until a reviewer votes; also the time until the last approval when several approvals are needed), **author**, shown as "Waiting for author" (from a "waiting for author" or "rejected" vote until the next push, reset or approval) and **merge**, shown as "Ready to merge" (from the last approval after which nobody asked for changes or reset the votes, until completion; it can be empty). Votes of the required reviewers decide when some of them voted, otherwise those of anybody but the author. Without threads, or without approvals in them, the PR counts as review until completion and merge is empty. Durations and the "took" total count **working time** (`totalflowx.reviews.workingDays`), like the review waiting time, so a PR left over a weekend does not look slow; the shares of the bands use the same scale (calendar time only when the whole PR lies on days off). The webview gives short phases a minimum width (`src/phaseLayout.ts`) and moves the event dots with the bands, so they stay on the phase where they happened. A re-vote after a push (the usual way a required approval is renewed) moves the start of merge to that vote, so the days between the first approvals and the push count as review.
- **The waiting time of a review counts working days only** (`totalflowx.reviews.workingDays`, default Monday to Friday; `src/workingTime.ts`). The team rule is "24 h" of working time, but counting calendar time made a PR published on Friday afternoon look 69 h overdue on Monday. All 24 hours of a working day count (it is not "3 office days"), so Friday 15:00 is due Monday 15:00. The due date, the time left, the urgency, the bar, the overdue reminder interval and the waiting time of published PRs in "My Pull Requests" use it, so authors and reviewers see the same number; drafts (age since creation) and "completed X ago" stay calendar time. Local time zone, days walked from midnight to midnight so daylight saving days are 23/25 h. **Holidays and days off are not handled** (they would need extra requests per iteration); a possible follow-up.
- **"Reviewed" PRs are display-only and kept apart.** `totalflowx.reviews.reviewedPeriod` (hidden by default) lists the PRs of others the user already voted on (`toReviewedRequests`, src/reviewedRequests.ts) below the waiting ones. The watcher stores them in separate fields (`activeReviewed`, `closedReviewed`), never in `requests`: the badge, urgency, Summary, status bar, digest and `detectReviewEvents`/notifications only read `requests`, so a reviewed PR can never count or notify (a test asserts it). The one exception is the private sprint recap: the user's votes go to the fun journal, which nothing else reads (see [Fun features](#fun-features-totalflowxfunenabled)). Active ones come from the existing `getPullRequestsToReview` response (no request). Completed/abandoned ones need `searchCriteria.status=all&reviewerId=…&$top=100` (the active query cannot return them), made only while the period is day/week/month, inside `withFeature('reviews')`, at most every 10 minutes (history changes little), or on "Check now" / when the period is first selected.
- **"Reviewed" PR details are fetched lazily, only for unfolded rows.** Reviewed rows are foldable tiles; the webview posts `setReviewedExpanded` (the unfolded ids, again when it loads with its saved state) and `ReviewRequestsWatcher.setReviewedExpanded` fetches with `PullRequestExtrasLoader.fetch` + `fetchFilesChanged` inside `withFeature('reviews')`, following the pure policy of src/reviewedRequests.ts (`reviewedIdsToFetch` / `reviewedIdsToDrop`, tested). Why: a PR's details cost 4-7 GETs (policies, threads, work item ids, builds, iterations, changes; plus work item types and build test/coverage details, both cached), so fetching them for every listed PR (up to 100 over a month) would multiply the review polling. Closed PRs never change: fetched once, cached for the session (0 per poll). Active ones are fetched on unfold and refreshed at each poll only while unfolded (the poll has just read their threads, so those are reused); folding drops their details so an old copy is never shown. The large layout of the box keeps reviewed PRs folded (it only applies to the waiting ones) so it does not trigger mass fetches. The details have no timeline / time left / bar: the PR is not waiting. They never feed the badge, urgency, Summary or notifications. The webview keeps at most the 50 most recent unfolded ids.
- **Required reviewers first**; optional reviews are listed only on demand. The overdue/due-soon counters count required reviews only (the 24 h rule is about them). Optional reviews are **tracked even while hidden**, so switching them on does not flood notifications (trade-off: an optional PR that became overdue while hidden does not notify at that moment).
- **"Ready to merge" (green) means nothing stops the merge**: published, every blocking policy satisfied (approvals included), no conflicts, no warnings, and every **required reviewer** has approved. Waiting for approvals is not green.
- **Required reviewers block "Ready to merge" even without branch policies** (`pendingRequiredReviewers`, src/myPullRequests.ts). Why: `isReadyToMerge` only looked at policy evaluations, and a PR whose target is a feature branch has none (PR 13847: 0 evaluations, two required people at vote 0 was shown as ready). Pending = required, not the author, not declined, vote below 5 (approved with suggestions counts as approved); people who sent the PR back (waiting / rejected) are left out because the feedback steps and warnings already name them (no duplicate text). A required group is listed only when no required person is pending and nobody but the author approved, since a group votes through its members. Next says `Approval of <names> missing` unless a blocking "Required reviewers" / "Minimum number of reviewers" policy step already says it. A PR with no approval from anybody but the author, and no blocking reviewer policy, is not ready either and Next says `No approvals yet` (only when nothing else is missing). Unknown policies (not fetched) do not trigger `No approvals yet`.
- **Next and Ready agree**: `Ready to merge` / `Will complete automatically` are only produced without warnings; with warnings and nothing else missing, Next says `Fix the warnings` (amber, red when a warning is an error). Why: the card used to say "Ready to merge" in green next to a missing Ready badge when only a warning (e.g. auto-complete without deleting the branch) was left. `nextTone` is `ready` only without warnings.
- **Removed work items are closed for branch actions** (`isClosedState`: done category or removed): no Create branch / Checkout / Create PR, only Delete branch when deletable, the same as the task rules (`canCreate*ForTask` exclude done or removed parents). The branch rows and the compact branch signal use the same function.
- **"Open in a worktree" in the pickers creates the worktree** when the branch has none (`openOrCreateWorktree`, with the pure `worktreeOpenAction`): the items of the pickers of the task pill and the branch rows post `openWorktree`, which used to throw "has no worktree" for branches without one. It opens the worktree when it exists, as before.
- **"Next" line** is computed from the PR's **blocking branch policy evaluations**, not guessed.
- **Rule warnings only on published PRs** (drafts are work in progress). The Bug auto-complete rule is an _error_ (red): only testers may complete Bugs; when present, even "Will complete automatically" is shown in red.
- **Branches start from `develop`; another base is opt-in.** Team rule, so the default path has no extra question: the module picker only has an optional "Base" row. Large work items sometimes need a task branch built on another, unmerged branch of the same work item. The chosen base is stored in the local git config (`branch.<name>.totalflowxBase`): it is per machine and invisible to Azure DevOps, which is enough because Create PR runs on the machine that created the branch; branches without it target `develop` as always. Create PR ignores the stored base when its branch is gone or its PR is completed.
- **Retarget warning**: squash merges leave stacked branches behind (the PR still targets the merged base and would show its commits again), so a PR whose target has a completed PR of the user (or no longer exists, when the git extension already knows the remote branches) is flagged with a **Retarget to develop** action. It only uses data already polled; the PATCH needs a confirmation because it may require a rebase.
- **Reviewer/vote notifications ignore the user's own actions**; reviewer changes are attributed from the `ReviewersUpdate` system threads.
- **Checkout of a PR / branch never silently carries changes**: with uncommitted changes it asks (worktree / stash / anyway). "Create branch" creates without switching, then proposes Checkout or a worktree.
- **Worktrees** go to `<repo>.worktrees/<branch>` (the layout the team already used), `<repo>` being the main working tree even when the command runs from a worktree window (otherwise, with `/` in branch names, each worktree got its own nested `.worktrees` maze; `mainWorktreeFolder`); the `.env.local` files are copied from the main working tree, copy `.env.local` files, open in a new window that runs `npm ci` once (marker in the worktree's private git dir, never in the working tree).

## CI, coverage and requests

- **CI runs are followed for the PRs of the user's work items and all the user's PRs**; fast polling (15 s) only while a run is active, otherwise an idle check (60 s) to discover re-runs/new pushes. A failed fetch keeps the last known runs.
- **The CI status bar item is labelled `CI` and ordered by severity; canceled runs are only in the tooltip.** The rocket icon looked like one more run state, and the order (failed, partial, running, queued, succeeded) puts first what needs the user. A canceled run (usually replaced by a newer push or stopped by hand) asks nothing from the user, so it only adds noise to the text; it stays in the tooltip with its icon and totals. When canceled runs are all there is, they are shown so the item is not empty (`ciStatusText`, src/pipelines.ts; STATUSBAR-CI-\*).
- **The CI runs use colour emojis, not codicons** (`STATE_ICONS`, src/pipelines.ts): the status bar can only colour a whole item, not one codicon, so ✅ and ❌ make a failure easy to tell from a success at a glance, in the item, its tooltip and its picker alike. Running keeps the animated `$(sync~spin)` codicon: the motion says more than a colour. The section titles of the tooltip (AFTER MERGE, RUNS WITHOUT A PULL REQUEST) are in capitals so they read as section labels, not as one more PR.
- **The colour of the CI item follows the checked out branch** (STATUSBAR-CI-3/9): it answers "how is the branch I am working on?", while the counts and the tooltip keep the overview of every run (a failure of another PR no longer turns the item red). The state is the most severe one of the branch's PR runs, else of its manual runs; merges never count. VS Code allows only two fills on a status bar item (`statusBarItem.errorBackground`, `statusBarItem.warningBackground`; any other background is ignored), so failed is red and partially succeeded orange, and the other states tint the text with contributed colours (`totalflowx.ci.*Foreground`, pale defaults in light themes because the light status bar is a saturated blue). No webview: the API has none for status bar items or their tooltips.
- **The CI tooltip has one block per PR, the PR of the checked out branch first** (`src/ciTooltip.ts`, STATUSBAR-CI-5/7). The flat list (run line, its failures, then the PR title) made it hard to tell which lines belonged to which PR: now the header (PR link + title) comes first, the runs are indented below it, and a rule separates the blocks. Indentation uses `&nbsp;` because four leading spaces would make a Markdown code block in the hover. Titles and test names go through `appendText` (escaped).
- **Runs without a PR and runs after a merge are shown in their own sections, only the user's own** (STATUSBAR-CI-6/8). Manual runs (`reason=manual`, e.g. an experiment branch) are requested for the user (`requestedFor`). Post-merge runs on develop are **matched by the PR number** in `Merged PR <id>:` against the user's PRs (active and completed, from the My Pull Requests poll), not by `requestedFor`: that is whoever completed the PR, which may not be the author. Other CI pushes are ignored. A manual run on a branch that has a PR stays with the manual runs: it is a different build from the PR validation. Window: 24 h (`totalflowx.pipelines.branchRunsHours`, 0 = off), so old experiments do not stay forever. Cost: 2 requests (the push one is skipped when the user has no PR), every 15 s only while one of these runs is active, otherwise at most once a minute, even while PR runs keep the fast polling going. They count in the status bar item (a failure there needs the user) but not in the Summary "failed CI runs" row, which stays about PRs (SUMMARY-5); their coverage is not recorded (records are per PR).
- **A broken base branch raises an alarm you cannot miss** (`src/baseBranchHealth.ts` pure, `src/baseBranchAlert.ts`; BASE-CI-\*; `totalflowx.pipelines.baseBranchAlert`, on by default). Team rule: develop must always be stable, and a red develop must be fixed before anything else, whoever broke it. So it is not limited to the user's own merges like the AFTER MERGE section (STATUSBAR-CI-8). Choices: (1) **its own query**, `branchName=refs/heads/<base>` on the open repository, last 50 runs of any reason and **no time window**: the push query of STATUSBAR-CI-8 is skipped without own PRs, turned off with `branchRunsHours: 0` and limited to 24 h, and none of these may hide a develop broken three days ago; schedules and manual runs on develop count too (it is develop's code). (2) **Broken = the last finished, not canceled run of a pipeline is failed or partially succeeded**: a running run (maybe the fix) and a cancel never clear it, only a succeeded run does. (3) **The culprit is the first failure after the last green run**, not the latest failure: a later merge that did not fix it did not break it. A **re-run of the failed jobs keeps the build id** and makes the build active again: it keeps the state it had at the previous fetch (`finishedStates`), otherwise a re-run of the breaking build would turn develop green or move the culprit and show the modal again; after a cold start during a re-run there is no previous state, so develop looks green until the re-run finishes (accepted). **Known limit**: the 50 runs are shared by every pipeline on develop, so a rarely run pipeline (a nightly) can fall out of the window after more than 50 runs of the others and read as green; `maxBuildsPerDefinition` may fix it, to verify with real data. (4) **Pipelines with no run on develop for 14 days are ignored** (a pipeline that no longer runs there would keep the alarm forever) and a team can list pipelines to ignore (`baseBranchIgnoredPipelines`, e.g. a flaky nightly). (5) **Request budget**: one request at most once a minute with the CI polling and on each load; develop runs never make the polling fast (develop runs after every merge of every team, and every fast tick also refetches all the followed PRs), so the alarm comes within about a minute; only the failing runs get their details (cached by build id). (6) **Four layers**: a red status bar item, leftmost, that stays until green (no dismiss: the alarm ends when the branch is fixed); a **modal** dialog, the only VS Code UI that cannot be overlooked, **once per incident** (pipeline + breaking build), remembered in the global state before it shows so the other windows (worktrees open their own) and reloads do not show it again; it is triggered from the state, not from a run that just finished, so a develop broken while VS Code was closed is announced at startup; never awaited, so the polling goes on while it is open; no reminders: the status bar item is the reminder. A red banner at the top of the sidebar (with the clock time it broke, not an elapsed time: the webview only renders when the state is posted, so an elapsed time would go stale) and the first Summary row (+1 on the badge, which shows without opening the sidebar). (7) The modal is blunt ("Your merge broke develop") only when one PR broke every new incident and it is in My Pull Requests; otherwise it is the neutral text, also while that list is not loaded. (8) **The siren is not a fun feature**: its own setting (`pipelines.baseBranchAlarmSound`, `application` scope, on) instead of `fun.sounds`, which is off by default; square waves, two tones, about 1.8 s. Like the other sounds it only plays while the sidebar is visible (whether a webview may play audio without a click must be confirmed in a real VS Code). Not done: an editor tab that opens by itself (too intrusive for now) and OS-level notifications (VS Code has no API; spawning a Windows toast from WSL is fragile).
- **The notification of a finished run names the PR by its title and links its work items** (`finishedRunMessage`, `src/runDetails.ts`): an id alone does not say which PR it is. The work items are Markdown links in the text (`[#1234](command:totalflowx.openDetails?[1234])`), which VS Code notifications render and run, rather than buttons: a PR can have several work items and buttons are kept for actions on the run (Open Run, Show Tests). They come with no extra request: for the user's own PRs the work items Azure DevOps links to the PR (already fetched for My Pull Requests), else the work items of the list (and their tasks) that link the PR. The title comes from the PRs the store already knows; without one the notification shows only the id, as before.
- **A separate status bar item for the user's own PRs that need them** (`src/myPullRequestsStatusBar.ts`, pure logic in `src/myPullRequestsAttention.ts`). Why separate: the review item is about other people's PRs and its colour follows the 24 h rule; the own PRs have different reasons and a different colour logic, and each can be switched off (`totalflowx.myPullRequests.showInStatusBar`). It reads the same models as the sidebar (`MyPullRequestsWatcher.models()`), so it costs no request. Which reasons count (active, published PRs only): Rejected, Waiting for author, conflicts, failed or partially succeeded CI, unresolved comments. Not counted: missing approvals or running CI (nothing to do but wait), drafts (work in progress) and PRs that complete by themselves. "Ready to merge" is shown too (good news that still needs an action: complete the PR) but never colours the item. Colour: red when something blocks the PR and only the author can fix it (rejected, conflicts, failed CI); yellow when it is a request or a chore (waiting for author, unresolved comments); default for ready only (STATUSBAR-MYPR-\*).
- **Coverage is the coverage of the code tested by the PR's run** (the PR pipeline runs the affected tests). Shown to motivate: levels (60/80/95), positive deltas celebrated, decreases neutral (no blame), files below target to open, personal best and streak (only the user's own PRs, one entry per PR). No team ranking (it would push people to game the number).
- **Request budget**: tags come with the PR list (0 requests); "PR changed the build notes file" = 1 diff request per PR per push (cached by last pushed commit); branch existence, repository names, work item types are cached. The usage report and request log exist to keep this honest.

## Dependency map

- **Iterations are `<Project>\<Release>\<Sprint>`**: depth 1 = limbo (ignored, counted in a note), depth 2 = release container ("not scheduled in a sprint yet" column after its sprints), depth ≥ 3 = sprint.
- **Columns are sprint periods** (same start/finish dates), with one lane per team sprint, always in the same team order; different date ranges get their own columns. Do not compare iterations by the container's dates (a release starts long before its sprints).
- **Risk**: done → grey; predecessor in a release or limbo → "not scheduled yet"; same sprint period (even different teams) → tight; later period → late; earlier → ok. The same rule drives the cards' open-predecessor warnings and the Work Item Details panel.
- **Done work items are always shown** (the "Hide done" option was removed): hiding them cut the chains and made the arrows of the remaining work items look unexplained. What matters at a glance is handled by the dashed grey arrows and the state colours; "Hide bugs" and "Sort by state" cover decluttering.
- **The border of a card is coloured by state, its ID by type, as in the sidebar** (the whole border, 3 px on the left, so the state reads at a glance on small cards; ID colours from `typeIdClass`). My work items used to have a blue frame; the state border took its place, so they are told by the highlighted **Me** of the footer. `media/dependencies.css` is loaded after `webview.css`: a border colour set on `.node` alone overrides the `state-border-*` classes (that bug made every card grey), so `.node` draws its border in `--bar`, set per state in `webview.css`.
- **Priority** (1 critical … 4 very low, `Microsoft.VSTS.Common.Priority`) is a pill in the card header with the same solid colours as the sidebar. **P1 work still to do glows in red** (not finished ones: the emphasis is about not missing critical work; they keep the pill): only a red halo **behind** the card (`box-shadow`), as if lit from behind, inspired by the lit cells of the UniFi UI. The card itself is unchanged (no red border or tint: the user preferred this to a thick outline and then to a tinted card), so it keeps its state border. It is also the **tie-breaker of the ordering**: when two work items weigh the same, the higher priority goes first (P1 … P4, then no priority), then the ID.
- **Ordering of a lane** (pure, `layoutGraph`): barycenter, 8 sweeps alternating left→right and right→left (a single direction leaves the last columns unsettled), the weight of a card being the average **vertical position in pixels** of its neighbours (card centre, lane headers and gaps included), not its row: lanes of different sizes in different columns would skew a row index. Deterministic: ties by priority then ID; the result does not depend on the order of the input.
- **Sort by state** (off by default) groups each lane by state in this order: in progress (Committed, In Progress, Active), not started (New, Approved, To Do, and any state we do not know: the `proposed` category), finished (Ready to Test, Done, Closed…), removed. Rationale: **active work first**, finished work is context. Inside a group the line-straightening order applies, so with the option on some arrows cross more: that is the price of the grouping.
- **Hide bugs** (off by default) hides Bug work items and their arrows; the focused work item is never hidden. It is applied **before** the "without dependencies" rule: a work item whose only links were to hidden bugs has nothing left to show, so it is hidden too unless "Show work items without dependencies" is on (the point of hiding bugs is to declutter, and a lone card would look like a work item with no dependencies at all). The "+N" count still includes dependencies that are bugs.
- Work items without dependencies are shown on demand.

## UI choices

- Compact layout is the default for work items and both PR boxes; a compact row unfolds into the full card in place.
- Boxes (Waiting for your review, My Pull Requests) look like framed panels, deliberately different from the iteration group headers.
- **The PR boxes have no thick left bar; their background and frame colour tell whether they need you, even collapsed.** The 4 px bar is the state bar of the tiles and means nothing on a box. Waiting for your review: red when a required review is overdue, orange when any PR is waiting, neutral when none. My Pull Requests: orange when an active PR needs you (same rule as the tile pulse), blue when there are active PRs (drafts included) and none needs you, neutral otherwise. Completed PRs and the Reviewed list never count. It reuses `countLate` and `needsAttention` (src/panelTone.ts, rules PANEL-TONE-1..2), so it costs no request.
- **The activity bar badge lives on the native "Summary" tree view, not on the webview view.** VS Code creates (resolves) a webview view only when it is first shown, so on a cold start there is no `WebviewView` to set `badge` on until the user opens the sidebar. A `TreeView` made with `createTreeView` at activation exists immediately, so `src/summaryView.ts` sets its badge (work items with alerts + PRs waiting for review, `src/summaryRows.ts`) at startup and on every change of the store and the watchers. The webview view must not set a badge too: the container would show a double count. Whether the badge of a _collapsed_ tree view reaches the container icon must be confirmed in a real VS Code.
- The PR history popover lists the latest events first.
- **The `Tasks` header of a card shows how many tasks are in each state, coloured, instead of `done/total`.** `done/total` only tells what is finished; the breakdown also tells what is being worked on. A segmented bar shows the proportions and each count sits on its own segment, so there is nothing to match by eye (an earlier version put the counts before the bar). Segments follow the workflow order, **To do, In progress, Done**, the same as the compact `to do/in progress/done` (a progress-bar order with Done first was tried and rejected by the user). **The numbers left the bar**: with the counts inside the segments the bar had to be 11 px thick, which the user found heavy, and the text on the segment colours was hard to read. The bar is a slim 4 px line (rounded ends, 1 px gaps) and each count is a small circle (14 px; a pill for 2+ digits) centred on its segment and on the line, like a marker on a track, touching the line (a ring in the card colour that separated them was removed at the user's request: the circle should sit on the line). Nothing is clipped (the circles are taller than the line); the circle is in the flow of its segment, so the segment's minimum width is the circle's width and circles never overlap, even for 1 to do and 14 done. Colours are the state categories of the work item cards (grey, blue, green); the tooltip and `aria-label` of the header spell the counts out (the bar is `aria-hidden`) so colour is not the only cue. **Two looks behind `totalflowx.tasks.countStyle`** (`filled` | `outlined`, class `task-counts-<style>` on `#app`, `normalizeTaskCountStyle` in `src/taskCountStyle.ts`; unknown values mean `filled`) because the user wanted to choose. `filled` is the default because its contrast is guaranteed: the circle is filled with the state colour and the number has a fixed text colour per theme kind, like the solid pills (priority, due soon), not a theme colour (the state colours vary a lot between themes and a text colour that follows the theme can vanish on them). Dark themes use `#1f1f1f` (contrast 4.8 to 9.0 on the default colours); light and high-contrast themes use `#000000` (4.9 to 9.4: white would give only 4.3 on green and 3.6 on blue, below the 4.5 needed for small text). `outlined` fills the circle with the card background and draws the ring and the number in the state colour, the same colours as the compact row's counts; in light themes those colours are too pale as text on the card (grey 2.1:1), so there the ring and the number are darkened 40% toward black (5.3 to 8.5 on the default colours). The theme's grey is translucent in light themes, so the segments and filled circles are painted over the card background to be opaque. Removed tasks are left out, as before (they never block a work item). The compact row (SIGNAL-7) keeps the short `to do/in progress/done` text (e.g. `2/1/3`) to take little room, with each number in the colour of its state and the slashes muted; its title says what each position means.
- **The ID in the header of a card (and of a compact row) opens the Work Item Details panel, not Azure DevOps**, and cards have no Details button: every other work item ID in the sidebar already opened the panel, and the button took room in the action footer. Azure DevOps is one click further, through the panel's **Open in Azure DevOps** button.
- Figma links open in the Figma VS Code extension when installed, but it does not select the linked frame (limitation of that extension, v0.4.7); the browser button opens the exact frame.
- **The tiles of My Pull Requests that need the user get a background effect, chosen with `totalflowx.myPullRequests.attentionEffect` (`none` | `static` | `pulse` (default) | `waves` | `shimmer` | `ripple` | `rainbow` | `breathe`; `needsAttention` in `src/myPullRequestsAttention.ts`, effect list and class in `src/attentionEffect.ts`).** The user asked for it: the status bar item says it, but a sidebar that is open should also show _which_ PR it is; first it was a boolean pulse (never released), then the user asked to choose the effect. Triggers: the status-bar "need you" reasons (`attentionReasons`: Waiting for author / Rejected, conflicts, failed or partially succeeded CI, unresolved comments) **plus** the team-rule warnings of the tile (`pr.warnings`), so it is deliberately broader than the status bar item, which ignores rule warnings. Active, published PRs only (drafts and completed ones never get it). Only My Pull Requests: the author is the one who can act on these; the tiles of Waiting for your review have their own urgency bar and pulse, and work item cards are not about a decision of the user. Background only, drawn on the `::before` (and `::after` for `ripple`, which needs two layers) pseudo-element behind the content: the tile's own background, hover styles, green "ready", the left bar and menus are untouched; the pseudo-elements sit inside the padding edge, ignore the pointer and clip themselves (no `overflow:hidden` on the tile, because popovers and menus must not be clipped). Peak opacity 12-20 % so the text contrast holds in dark and light; only opacity, transform and background-position are animated, with slow cycles (2.4-10 s). The colour is the fixed orange `--waiting` (#f0883e dark, #bc4c00 light), not the theme warning colour, which is gold in some themes and would read as a task; `rainbow` is the only exception, because the user asked for it explicitly. A `glitch` effect (brief jitters of offset bands) was offered and removed at the user's request. All motion sits in `prefers-reduced-motion: no-preference`; with reduced motion every animated effect falls back to the static 8 % tint (`static` is exactly that). `none` draws nothing. On by default (`pulse`), unlike the "Working on" card animations (off by default, because many cards would move at once and "here" is only a bookmark): few PRs need attention at a time. Class `attention-<effect>` on `#app` switches it; unknown values mean `pulse`.
- **Hovering a card or PR tile does not change its background by default (`totalflowx.appearance.hoverStyle` = `border` | `tint` | `accent`)**: the old hover painted the tile with the list hover colour (`--vscode-list-hoverBackground`), which in many themes is close to the muted greys, the blue IDs and the state colours, so the text became harder to read exactly when the user was looking at it. `border` (default) leaves the background alone: the whole border takes the colour of the tile's thick left bar (the state of the work item: grey proposed, blue in progress…; the state of the PR: purple completed…; red alerts, blue "Working on", green ready to merge), so the hover says the same thing as the bar instead of adding a blue that means nothing there, and a soft shadow lifts the tile; contrast is unchanged. `tint` is a 5% foreground mix over the tile's own background (so "Working on" keeps its blue underneath), `accent` brightens the left bar and widens it by 2 px with an inset shadow (the content does not move). The style is a class on `#app` (`hover-<style>`, `normalizeHoverStyle` in `src/hoverStyle.ts`; unknown values mean `border`), the same rules apply on `:focus-within`. `--card-hover` stays for buttons, menus and rows, where there is no text-contrast problem to solve.
- **"In review" is a derived, display-only state, and it can be switched off (`totalflowx.workItems.showInReviewState`).** Backlog Items and Bugs have no such state in Azure DevOps, and a Committed item whose only remaining work is getting its PRs approved looked the same as one still being coded. The team's PR task already stands for "in review" (see PR tasks), so the state is derived from the tasks (Rule STATE-10): Committed, at least one task In Progress, every In Progress task a PR task, every other task Done (Removed ignored). A PR task is one whose title matches `alerts.pullRequestTaskPattern` **or** that is linked to a PR, so neither a missing link nor an unusual title hides it. No tasks, or all of them Done, does not count: nothing is waiting for review. Actions, alerts, task rules and **Change state** keep the real state (the tooltip of the button tells it), so nothing depends on a state Azure DevOps does not have. The Dependency Map and the Work Item Details panel show it only for work items whose tasks are known (the user's own work items; the open item of the panel, whose children are fetched anyway): fetching the tasks of every predecessor and successor would cost requests, so those keep their real state.
- **Settings are grouped by feature in the Settings editor, with keys named after their category and `application` scope for personal choices.** With ~80 settings on one flat page, related ones ended up far apart. `contributes.configuration` is an array of categories (Connection, Work Items List, Working On, Branches & Pull Request Creation, My Pull Requests, Reviews, CI & Coverage, Team Rules, Appearance, Advanced), each property with an `order`. Grouped **by feature** (where someone looks for "something about reviews"), except two cross-cutting groups: **Team Rules** (alerts, build notes, Integrated in Build: agreed by the team, meant for a committed `.vscode/settings.json`) and **Advanced** (poll intervals, `pipelines.branchRunsHours`, request log: rarely touched, and they drive the request budget). **Keys were renamed to match the categories** (`layout` → `workItems.layout`, `stateOrder` / `showInReviewState` → `workItems.*`, `hoverStyle` → `appearance.hoverStyle`, `baseBranch` / `branchTypeByWorkItemType` / `branchModules` / `linkBranchToWorkItem` / `stateOnBranchCreated` → `branches.baseBranch` / `.typeByWorkItemType` / `.modules` / `.linkToWorkItem` / `.workItemStateOnCreate`, `prFeatureNames` / `moduleToFeature` → `pullRequests.featureNames` / `.featureByModule`, `notifications.events` / `.pollIntervalSeconds` → `myPullRequests.notifications` / `.notificationsPollIntervalSeconds`, `statusBar.currentWorkItem` → `workingOn.showInStatusBar`) and the deprecated `tasks.hoverCardDelay` was removed, **without a migration of the old values**: the extension has a single user, whose settings did not use the old keys, so a migration would have been code to keep for nothing. If it ever gets more users, renames need a migration on activation. **Scope**: the personal choices the sidebar writes to the user settings (layouts, filters, the box toggles) and the look (hover, popover delay, task counts, animations, attention effect, fun) are `application`, so they follow the user everywhere (also into WSL / remote windows, where they are read from the local user settings) and a workspace cannot override them. Everything else keeps the default `window` scope, which already allows workspace settings; `resource` was not used, because it only adds per-folder values in multi-root workspaces and `getConfiguration(SECTION)` is read without a URI. `branchModules` / `prFeatureNames` must stay non-`application`: **Add new…** writes them to the workspace settings. **Totalflow X: Open Settings** opens the editor filtered on the extension (`@ext:<id>`, id from `context.extension.id`).

- **One orange caution for what blocks completion (open predecessors, blocking tags, empty fields), and no "ready to start" badge nor start confirmation**: the green "ready" showed on every not started item without links, so it said little, and the modal before starting got in the way of work that is allowed. Orange means warning, not blocker: starting is free, completion is what the issues block. So the caution covers every _open_ work item (not only the not started ones) and the popover lists the details of each issue: open predecessors, tags of `alerts.blockingTags` (user-editable, no new setting), and, for Backlog Items only, an empty Acceptance criteria and the empty `alerts.requiredFields` (Effort, Effort in days). Closed items show nothing. Blocking tags have no red alert (there used to be "Started while tagged"): starting an item with such a tag is allowed, only completing it is blocked, so the orange caution is the right level and showing both was a duplicate. Empty required fields still overlap (red "… is empty" and the caution); that is accepted: the alert is a red problem in the work, the caution a pre-completion checklist that also shows before starting. Acceptance criteria is HTML (Azure DevOps rich text), so `<div><br></div>` and `&nbsp;` count as empty; the field is already in the work item response (`$expand=relations`), so it costs no request. Alerts disabled (`alerts.enabled` off) means no rules, so only the predecessors remain.

## Fun features (`totalflowx.fun.enabled`)

- **Opt-in, private, never comparative.** Off by default: some people dislike confetti at work, and the sidebar is always visible. Nothing is a leaderboard or compares people: comparisons turn fun into pressure and invite gaming the numbers. The "karma" of the recap only compares the user's own reviews with their own PRs.
- **No new request.** Everything comes from responses the pollers already fetch: finished runs (`PipelineWatcher.onFinished`), the user's PRs and their threads (`PullRequestNotifier`, which now also keeps `creationDate`, `closedDate` and the publication date from the threads it already reads), the review poll (`getPullRequestsToReview`, the same response that feeds `activeReviewed`), and the sprint dates that `$timeframe=current` already returned (`attributes`).
- **A journal, recorded whatever the setting** (`src/funJournal.ts`, `FunJournalStore`, global state key `totalflowx.funJournal:<org>/<project>`). Recording always means the recap is complete when the user turns the features on, or opens it by hand. Lists are capped (500 entries). Several windows share the global state, so every recorder is idempotent by id and the store reads just before writing; a window that finds the entry already there says nothing about it, so a streak or a first approval is celebrated once.
- **Green streak = the user's own runs**: PR runs of the user's PRs (`isMine`; the store also follows other people's PRs linked to the user's work items), manual runs and post-merge runs (both already only the user's, STATUSBAR-CI-6/8). Canceled runs are left out (a cancel says nothing about the code); partially succeeded counts as red; a re-run of the failed jobs keeps the build id, so its new outcome replaces the old one. Ordered by finish time. Runs that finished while VS Code was closed are not caught up (the order would be guesswork). The status bar cannot animate, so a broken streak is told in the run notification.
- **The reviews counted by the recap break the "Reviewed is display-only" rule on purpose, in one place only.** `votedPullRequestIds` (REVIEWED-2) feeds the journal, which only the recap reads: the badge, urgency, Summary, status bar, digest and notifications still never see reviewed PRs. It works whatever `reviewedPeriod` is (the active PRs come with every review poll).
- **Merged PR**: one notification only. When the completion offer (tasks to Done, branch to delete, MYPR-OFFER) shows, it stays as it is and only the confetti celebrates; otherwise the celebration text replaces the plain "merged" text. Confetti is posted only to a sidebar that is open and visible (a webview view may not exist yet), and both the JS and the CSS skip it with reduced motion.
- **"This sprint"** is the sprint whose dates contain the merge (UTC days, as Azure DevOps stores them); without dates the count is left out rather than guessed. The countdown compares the local date with the date part of the finish date and counts working days (`reviews.workingDays`), today and the last day included, since "days left" matters in working days.
- **Clean board row** is only shown with the alerts on (without them a clean board means nothing) and some work items listed; it comes after "Nothing needs your attention", never counts in the badge and is not clickable.
- **Recap panel**: static HTML, scripts disabled, its own small stylesheet (`media/recap.css`), so no fourth bundle. Offered once per iteration path (marked in the journal before the notification shows, so two windows do not both offer it).
- **Sounds are a second opt-in** (`fun.sounds`, on top of `fun.enabled`): someone may like the confetti but not noise in an open-plan office. They are synthesized in the sidebar webview with the Web Audio API (oscillators with a fade), so there is no audio file to ship and the strict CSP needs no `media-src`. The extension host (Node) has no audio API, and spawning a system player (`afplay`, PowerShell, `paplay`) is per-platform and plays nothing under WSL, where the extension host runs; webviews render on the client side (Windows), so their sound reaches the user's speakers. VS Code's own accessibility signals cannot be played by extensions. The cost: like the confetti, the sound only plays while the sidebar is open and visible; keeping the webview alive when hidden (`retainContextWhenHidden`) would cost memory for the whole session, not worth a chime. Only three moments make a sound (merge, streak record, broken streak): comments and votes are frequent and would get noisy. The siren of a broken develop is not one of them: it has its own setting (see the base branch alarm). Whether VS Code's webviews let audio start without a click in the page must be confirmed in a real VS Code; if not, the sound stays silent (the code catches it).
- **More card animations** (`rainbow`, `neon`, `retro`) live under `workingOn.animation`, not under `fun.enabled`: they are a look the user picks, not a celebration. Same constraints as the others (pseudo-elements, opacity / background-position only, nothing with reduced motion). A blinking cursor after the badge was tried for `retro`, but it widened the badge and wrapped the card header: the scanlines take no space.

## Naming and identity

- Namespace `totalflowx.*` for settings, commands, views; display name "Totalflow X devtools for Azure Devops". The **extension ID stays `abb-totalflowx.vscode-azdo-workitems`** so installed state (globalState) survives renames; the coverage records keep their old storage key `azdoWorkItems.coverageRecords:` for the same reason.
- The per-work-item tab is the **Work Item Details panel**; its button on cards is "Details".

## PR tasks: one per PR, matched by link

- A work item may have several PRs, so the PR-task alerts are per PR. A PR's task is the child task **linked to the PR** (ArtifactLink "Pull Request"), whatever its title; the title pattern (`totalflowx.alerts.pullRequestTaskPattern`) is only a legacy fallback for PRs with no linked task, used once. Why: the title matched only "the" PR task, so work item 66068 (PR 13770 completed with task 60985 Done, PR 13765 active with task 60984 "PID update" In Progress) was flagged wrongly.
- Create PR links the task through `workItemRefs` of the PR but keeps it out of the title ids (`[<ids>]` are the Backlog Items / Bugs). Publish and completion are **not** automatic in the same way: a published PR moves its task to In Progress (Publish in the extension right away; PRs published elsewhere on the next load, see below); completion only _offers_ Done, since the task may still have work left. It reuses the "merged" detection of the notifier (baseline, no new polling); the task lookup costs two requests per completed PR.
- Failing to create or move a task never undoes the PR: it only warns.
- **The tasks of PRs published elsewhere start by themselves** (`src/pullRequestTaskStarter.ts`, Rule TASK-PR-8, `totalflowx.pullRequestTasks.startWhenPublished`, on by default). Before, only Publish in the extension moved the task, and a PR published in Azure DevOps (or created published elsewhere) only raised ALERT-4 with a **Fix** button. Choices: (1) it runs **after each load of the list** and uses what the load already fetched (the tasks of the user's work items, also the ones of other developers, and their PRs): the only extra request is the user's id, once, and none at all when no task has a published PR; (2) **only the PRs the user created** (`createdBy.id`): a write to Azure DevOps on behalf of the user must come from the user's own work, and a colleague's extension moves the tasks of their PRs; (3) **Done and Removed tasks are left alone** (as with Publish, TASK-PR-4): reopening a closed task is a decision, so ALERT-4 still reports it; (4) **once per task / PR pair and session**: a failure is not retried on every load, and a task moved back by hand is not fought; (5) a notification says which tasks moved, then the list reloads. PRs linked to tasks outside the user's work items are not seen (that would cost requests per PR).
- **Create PR is offered per task branch, not per task.** A task can have several branches (e.g. a rework branch next to the first one) and one active PR used to hide **Create PR** for all of them. Now each usable branch (here and not deleted) without a PR, or with only an abandoned one, gets **Create PR from <branch>**, and the choice skips the branch question. Branches with a completed PR are left out on purpose: the team deletes them once merged (**Delete branch** is offered instead). A task with no usable branch keeps the old generic item (no active PR), which falls back to the branches of the work item.
- Branches created from a task row use the **parent's id and type** (team rule `<type>/<module>/<id>-<name>`, and `src/naming.ts` detects the work item from that id), with the short name proposed from the task title; the team already names extra branches that way (`feature/fui-common/66068-related-changes`). They are linked to the task as well as to the parent to tie task, branch and PR together: the task row then hides **Create branch**, and **Create PR** from the task prefers the task's linked branches over the parent's.
- **Task rows show every linked branch, deleted ones dimmed instead of hidden**: a Development link outlives its branch, and hiding it would make a task look branchless (and offer **Create branch** wrongly, which already keys on links). Existence of the branches linked to tasks is asked to Azure DevOps (`refs?filter=`, one request per distinct branch) and cached in memory for 10 minutes; a local branch with the same name counts as existing, and a failed request leaves the branch "not verified" (not deleted). In the picker of the task pill, a branch that exists offers **Checkout** (`checkoutHere`, kind `task`, straight to checkout) and **Open in a worktree** (`openWorktree`); deleted and other-repository branches are only on the hover card (a picker cannot show an inert item). A branch whose PR is completed and that still exists also offers **Delete branch** (red trash icon).
- **One pill per task row, with a native picker, instead of an icon per branch / PR plus two dashed create buttons**: the row of a card is narrow (260 px) and up to five small controls with different click meanings were confusing. The pill only summarises (icons coloured by state, counts; a dim "+" when empty); hover shows the details card (see the hover card entry below), click opens VS Code's QuickPick (see the picker entry below) that lists every action (checkout, worktree, delete, open PR, create branch / PR), titled `Task <id> · <title>`. The picker is not a popup of the pill, so the pill has no `aria-haspopup` / `aria-expanded`. Pure rules: `src/taskMenu.ts` (the sections), `src/actionRequests.ts` (title + sections of each trigger).
- **The switch between compact and large is a View Transition**: the two forms are different markup rendered again with `innerHTML`, so CSS transitions cannot morph them. `renderMorphing` (src/webview/main.ts) wraps the render in `document.startViewTransition` and gives each card / PR row a `view-transition-name` (`wi-<id>`, `review-<id>`, `mypr-<id>`; CSSOM, as the CSP blocks inline styles) only during the switch, and names the blocks around them (PR boxes, toolbar, filters, list) so they slide instead of cross-fading (their text showed twice). A duplicated name would abort the transition, so a second element with the same name is left out. Short (≈0.2 s) and clipped to the card's radius. Without the API (older VS Code) or with reduced motion the view is just rendered. Opening / closing the tasks of a card is the same morph (the card grows or shrinks with its tasks inside). Expanding / collapsing a PR box uses the same transition with only the blocks named: the box grows or shrinks with its rows inside it (named on their own, the rows would spill out of the shrinking box). The view the extension posts back after saving the layout is rendered without a transition: it is the same.
- **Only the card "here" can animate (the running border of `runningBorder` covers the card's border exactly, so it is as thick as the 5px left border on that side); card animations are off by default, the badge pulse is on** (`totalflowx.workingOn.animation`: `none` | `borderLight` | `runningBorder` | `glow` | `stripes` | `rainbow` | `neon` | `retro`; `totalflowx.workingOn.pulseBadge`): the sidebar is always visible, so continuous motion on many cards would distract; "In worktree" is a bookmark, not the current focus, so it never moves. The pulse (a halo expanding from the whole badge, every 2 s, like a live / recording light; a ring from the ● alone looked poor on the small glyph) is cheap and tells at a glance which one is live, hence on by default and independent from the card animation. All are pure CSS keyframes switched by classes on the list (`anim-*`, `pulse-badge`; strict CSP, no inline styles), built on pseudo-elements that take no space and ignore the pointer, so content, hover, the red `.has-alerts` border and the menus are untouched. They animate opacity / transform / background-position, except the running border: a short light moves along the border (`offset-path`) inside a masked ring that covers the card's border. A rotating conic gradient was tried first, but its speed followed the angle, not the border, so it raced along flat (compact) cards; the light moves at a constant 220 px/s instead, its duration set from each card's perimeter on every render (CSSOM, `placeRunningLights`), with a negative delay so a re-render does not restart it. The halo is blue (`--working-here`), never the red of alerts. Everything sits inside `@media (prefers-reduced-motion: no-preference)`, so with reduced motion the look is the static one. Classes come from `workingOnAnimationClasses` (`src/workingOn.ts`, tested); unknown values mean `none`.
- **"Waiting for author" has its own orange (`--waiting`)**: some themes define `charts.orange` as a dark red-brown (rgb(120,32,32) on a rgb(31,38,34) tile: contrast 1.49), and the theme's warning colour is the gold already used for tasks, so the two looked alike. `--waiting` is a fixed orange, #f0883e on dark themes and #bc4c00 on light ones (`body.vscode-light`), used for the tile border, the status pill, the reviewer chip, the PR rows of the work item cards, the task pill and the "Waiting for author" phase of the PR history; the solid badge is #f0883e with dark text. Warnings and "N unresolved" keep the theme's warning colour (`--warning-fg`, pulled 30% toward the text colour), and `--orange` is pulled 35% toward the text colour for the other uses. "N unresolved" took the tile's `--pill-color` because a later `.signal` rule won over `.signal-comments`; it is now `.signal.signal-comments`.
- **A PR sent back by a reviewer is never "Ready to merge"**: branch policies do not count "Waiting for author" (-5) or "Rejected" (-10) votes, so PR 13765 showed "Ready to merge" while a required reviewer was waiting for its author. Those votes now give a warning (Rejected: an error) and a Next step, which also keeps the PR out of "Ready to merge" and counts it in the Summary. People are named; a group only when none of its members is listed with the same vote (a group mirrors its members' votes). Their status badges are solid amber / red with a fixed text colour, like the other pills that must read in any theme.
- **Purple means a completed PR; worktrees are blue**: the "Completed" PR badge and everything about worktrees (the **⧉ In worktree** card, the worktree badge, Open worktree in the menus) were all purple, so a worktree could be read as "completed". Purple stays with completed PRs, as in Azure DevOps and GitHub. "In a worktree" means the same as "checked out here", that I'm working on it, so it takes the same blue (`--working-worktree: var(--working-here)`) and is told apart by shape: a thin dashed border, an outline badge and no tint, against the solid badge, thick border and tint of "here". Teal was rejected because the VS Code chart palette has none, so it would be hard-coded and hard to keep readable in both themes.
- **Branch rows: one badge and icon buttons, details in tooltips**: a row had a location pill, a worktree pill, a text "Checkout ▾" / "Open worktree ▾" (now "Checkout …" / "Open worktree …") and "Delete", so in a 260 px sidebar the name (long: `feature/<area>/<id>-<title>`) was truncated to a few characters, and the name is what identifies the row. Now there is **one badge** (`src/branchBadge.ts`, pure and tested: location, `not deleted` when the PR is merged, plus `⧉` when a worktree has the branch, with the worktree tone) and **icon buttons** (checkout / worktree icons with a … more-actions button, trash for Delete) whose `title` / `aria-label` carry the words ("Checkout <branch>", "Open the worktree of <branch>", "Delete the branch <name>"). What the short badge cannot say (what `local` means, the worktree folder, why it is `not deleted`) is in the badge tooltip. Only branch rows are compact (`checkoutButton({ iconOnly })`): the card-level and PR-box Checkout buttons keep their text because they are the primary action there. The `⧉` is a character, not an SVG, so the badge keeps one text colour and no extra width.
- **All the action menus are the native QuickPick, not an in-webview popover** (task pill, the … of branch rows, the … of the Checkout / Open worktree buttons of cards, "Waiting for your review" and "My Pull Requests"). An in-card popover menu was built first (notch, header, opening animation, keyboard and focus handling, key-based open state) and **rejected: a webview cannot draw outside the sidebar**, so the menus were cramped at 260–340 px (long branch names, descriptions) and needed a lot of machinery to behave like a menu. The QuickPick has the room (it is drawn at the top of the window, over the editor), keyboard handling, filtering and the user's theme for free, and the extension already used it for the details panel. How it works: every trigger posts ONE message, `showActions` (`{ title, sections }`), built by the pure section builders (`taskMenuSections`, `branchMenuSections`, `checkoutMenuSections` over `checkoutMenuItems`, the single source of truth; `src/actionRequests.ts` adds the title); the extension (`src/actionPicker.ts` pure, `src/actionPickerUi.ts` wrapper) shows a separator per section and an item per action, and the chosen item goes through `onMessage` as if the webview had posted the message of that button, so there is one code path per action. The sections come from the webview, so the extension only runs the allowlist of actions that the builders produce (`actionToMessage`: `checkoutHere`, `openWorktree`, `removeWorktree`, `deleteBranch`, `openPullRequest`, `createBranch`, `createPullRequest`) with the right field types and rebuilds the message from known fields (nothing else of the data is passed on); the delete flow keeps its own modal confirmation. **Items that only inform** (a checked out or deleted branch, "Checked out") are **left out**: a QuickPick cannot show an inert item (choosing it would do nothing and close the picker, which reads as a bug); that information is on the hover card and the badge of the row, and a trigger with nothing to choose does nothing (no empty picker). The **… of the details panel** (`totalflowx.checkoutMenu` / `totalflowx.worktreeMenu`) use the same picker and `checkoutMenuSections`, built by the extension from the current state of the branch (a worktree that appeared meanwhile gives Open / Remove worktree whichever of the two commands was asked); the chosen item runs the `totalflowx.checkoutHere` / `openWorktree` / `removeWorktree` commands, which are what the previous two pickers ended in (`checkoutBranch(..., 'here')`, `openOrCreateWorktree`, `removeWorktreeOf`). Icons: each item has a codicon and a theme colour from its action (`actionMenuIcon`, `src/actionMenu.ts`), the same in every picker, so users recognise it before reading: `git-branch` blue Checkout, `folder-opened` blue Open worktree, `close` orange Remove worktree, `trash` red Delete branch, `git-pull-request` green Open PR, `git-pull-request-create` green Create PR, `git-branch-create` yellow Create branch. They are set as `QuickPickItem.iconPath` (`ThemeIcon` + `ThemeColor` with `charts.*`, in the VS Code 1.95 typings the extension builds against); the shape carries the meaning on its own because whether the colour is drawn depends on the VS Code version and theme.
- **The Checkout / Open worktree button has a … (ellipsis), not a ▾**: a chevron says "opens below me", and the picker opens at the top of the window. The button is a plain button, not a popup of itself, so it has no `aria-haspopup` / `aria-expanded` and no rotating chevron (titles stay "More checkout options" / "More worktree options"). (A single … button replacing the whole split button was rejected earlier: users prefer the visible Checkout / Open worktree icon next to it.) The icon is drawn with filled dots (`icons.ts` `ellipsis`, `.button.caret .icon circle`).
- **All the popovers share one behaviour (delay, fade, focus, Esc, placement)**: the coverage details, the open predecessors, the PR history and the task pill card used to behave differently (the task card waited and faded, the others appeared instantly with `display`), which the user found inconsistent; native tooltips wait too, so everything waits. (1) One mechanism, only in the shared CSS (`.popover-anchor` on the wrapper, `.popover` on the direct child popover; the specific classes keep their own look and position): hidden with `opacity`/`visibility` (not `display`), so that showing can wait: on hover it fades in after `totalflowx.popovers.hoverDelay` ms (default 500, 0 to 3000; `normalizePopoverDelay` in `src/popoverDelay.ts`; the webview sets `--popover-delay` on `#app` through CSSOM), and hiding is a 0.12 s fade-out (not instant, on purpose: the `visibility` flip is delayed by the same 0.12 s because pressing Tab from the badge into the popover blurs the badge first; if the popover were hidden at that instant its file buttons could not take the focus. Esc and the click on a task pill hide at once). Moving the pointer across rows does not flash cards, because showing waits. Keyboard focus **on the trigger or inside the popover** (`.popover-anchor:has(:focus-visible)`) shows it at once, because a keyboard user cannot "hover longer" and must be able to Tab into the file buttons of the coverage popover; a mouse click focuses a button but is not `:focus-visible`, so a click does not keep the popover open after the pointer leaves (this is why `:focus-within` was dropped; it also keeps the nested badge inside the task card from opening the card's siblings: the rules use `>`, the direct child). **Esc** hides all of them (`.no-popovers` on the body, until the pointer moves). (2) After a **pointer click** on a task pill its card **stays hidden until the pointer leaves the pill and its card** (`suppressedTaskCard`, rendered as the class `card-suppressed`, because `render()` rebuilds the HTML on every update; cleared by a delegated `pointerover`, no render); keyboard clicks (`event.detail` 0) do not suppress it. Clicks on the text of any popover do not fold the row behind it. (3) **Placement**: the coverage popover (300 px, left edges aligned) and the task card (360 px, right edges aligned, `min(preferred, view - 16px)`) are placed by one routine: the pure `placePopover` (`src/popoverPlacement.ts`) clamps them to keep an 8 px margin on both sides and `placeAllPopovers` in `main.ts` writes `--popover-left` / `--popover-width` through CSSOM relative to the containing block. It uses `document.documentElement.clientWidth`, **not `window.innerWidth` or `100vw`**, which include the vertical scrollbar: with them a popover near the right edge made the whole sidebar scroll horizontally. Because hidden popovers (`visibility`) still count for the scroll width, **all** of them are placed after every render and on resize (not only on hover/focus, which left them stale after a re-render); the outer ones first, since a coverage badge can sit inside the task card. The predecessors and the PR history span their card (`left: 0; right: 0`) and need no placement. The padding on top of each popover is the pointer bridge. The task card has a lighter shadow, no notch, and a muted **"Click for actions"** footer when the picker has actionable items (`taskHasActions`).

## Task branches and "Working on"

- **Link an existing branch to a task from its pill** (`Link to <branch>` for the branches of the work item, `Link another branch…` for any branch of the remote): developers often work on the branch of the Backlog Item, or on a branch created outside the extension, and the task then had no branch (no pill state, no "Working on", no PR task match). The branch is also linked to the **work item** when it does not have it: a task branch that the work item does not link raises ALERT-2 at once, so asking would only add a second step. The list is the **remote** branches: Azure DevOps links a ref of the server, so a branch that was never pushed would give a dangling link. A modal confirmation precedes the write, like the other link quick fixes. Offered for open tasks of open work items, also when the task has branches already (several are allowed).
- **The parent card is "Working on" through the branch of one of its tasks** (`WorkingOnEntry.taskBranches`, only with `workingOn.includeLinkedWorkItems`, like the Development / PR rules): the developer is working on the Backlog Item or Bug whoever's task the branch is linked to, and the card with its "Working on" section is where the tasks are. The task row is highlighted too (`taskWorkingOn`: "here" light tint + bold title (no left accent: it looked heavy in a row), "worktree" dashed outline; no animation: the parent card already animates, and rows must keep their height). Styles are scoped as `.child.working-here` so the card rules (`.card.working-here`, `.working-here .working-dot`) never reach the rows.
- **Alert "Branch … of task … is not linked to this work item"** (`taskBranchNotLinked`, `src/alerts.ts`): when the branch of a task is not in the Development links of its work item. The team links branches to the work item; a branch linked only to a task means it was forgotten (Create branch for a task links both, so it only fires for branches linked by hand). It covers **every branch of every open task**, not only the checked-out one: the rule is about the data (the work item must show all its branches), not about what the developer happens to be doing; and checking only the current branch would hide the problem until someone checks it out. It is not reported for finished work items (Done / Ready to Test / Removed) nor for Done / Removed tasks (history), and only for branches of this repository. It needs no extra request: the links are already fetched. The quick fix (`totalflowx.linkTaskBranch`) confirms and uses `branches.linkToWorkItem`.
- **Alert "PR … of task … is not linked to this work item"** (`taskPullRequestNotLinked`, `src/alerts.ts`): the PR counterpart of the previous alert: a PR linked to an open task but not to its Backlog Item / Bug means the link was forgotten (Create PR links both, so it only fires for PRs created or linked by hand). Same scope (open tasks of unfinished items, once per PR). Differences: it compares against the **raw PR links** of the work item, not the fetched PRs, so a PR whose fetch failed is never reported as unlinked; **abandoned PRs are skipped** (history, like ALERT-3..5), while a PR of unknown status still alerts; and it covers **all repositories** (PR ids are collection-wide and the link carries project and repository, so the quick fix works anywhere), unlike branches, whose names are not unique across repositories. No extra request: the PR links of tasks and their statuses are already fetched. The quick fix (`totalflowx.linkTaskPullRequest`) confirms and uses `linkPullRequestToWorkItem`.
