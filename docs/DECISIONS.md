# Decisions

Why the extension behaves the way it does. Each entry: the decision, and the reason (often a team rule or something learned about Azure DevOps). Add an entry when you make a choice someone could later "fix" without knowing why, and correct or remove the entries a change makes wrong — in the same change (developers and AI agents alike).

## Team rules

The extension enforces or supports these team rules; many features exist because of them.

| Rule                                                                                                                                                                       | Where the extension helps                                                                          |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| Branches are named `<feature\|bugfix>/<module>/<id>-<short-name>` (Backlog Item → `feature`, Bug → `bugfix`)                                                               | Create branch; branch ↔ work item detection (`src/naming.ts`)                                      |
| PR titles follow `[<ids>] <Feature Name>: <description>`                                                                                                                   | Create PR; warning on published PRs                                                                |
| Every PR has a short description, at least 2 required reviewers (people, not groups) and a linked Backlog Item or Bug                                                      | Warnings on My Pull Requests cards                                                                 |
| No PR waits for its reviewers more than 24 hours                                                                                                                           | "Waiting for your review" box, status bar, reminders, daily digest                                 |
| Branches are deleted once their PR is merged                                                                                                                               | Delete branch for branches of completed PRs; warning when auto-complete does not delete the branch |
| Only testers complete Bugs                                                                                                                                                 | Red error when a Bug PR's auto-complete would complete the linked Bug                              |
| Changes testers should know about are explained in `build-notes/developer-notes.md`; PRs without such changes get the tag `no-build-notes`                                 | Build notes warning, "Add tag" button, check in Create PR                                          |
| Starting a work item whose predecessors are not done should be agreed with their owners                                                                                    | Open predecessors on the cards, confirmation before starting, dependency map                       |
| Each PR has its own PR task: In Progress while the PR is in review, Done when it is completed (the task stands for "in review": Backlog Items and Bugs have no such state) | Create PR creates / links it, Publish starts it, completion notification offers Done, alerts       |
| Alerts (Done with open tasks, missing PR task, blocking tags, empty required fields, Integrated in Build when Ready to Test)                                               | Alerts on the cards, banner, badge, status bar                                                     |
| "Integrated in Build" of a Bug Ready to Test = last published `rmc.image.deploy` version + `+`                                                                             | Fill button and proposal when moving to Ready to Test                                              |

## Scope and data

- **Only the user's work items** ("Assigned to Me", "My Work Items"), in the **current iteration of every team the user belongs to** (`teams?$mine=true`), unless teams are selected. Teams sharing a sprint are merged; different sprints are grouped.
- **Tasks are never cards of their own** nor filter values: they are parts of their Backlog Item / Bug, always nested in its card (including tasks assigned to other developers, with their initials). Tasks are not shown in the dependency map and get no "Dependency map" button.
- **Filters apply to Backlog Items and Bugs only**; nested tasks are never filtered. Work items with alerts follow the filters unless `filter.alwaysShowAlerts` (default off: the banner says how many are hidden and "Show only these" reveals them).
- **Several branches per work item**: named after it, Development links, source branches of its active PRs. The **main branch** (checked out, else named after it, else the link) drives the card's buttons; each other branch of this repository has its own Checkout. Finished work items list only their deletable branches (completed PR, see below) and other _local_ branches, because remote refs and links outlive deleted branches.
- **Delete branch is offered when the branch's PR is completed, not when the work item is finished**: the team deletes a branch once its PR is merged, and the state of the work item says little about it (a Backlog Item with several PRs stays Active while its first branch is already merged; a Done one may have been merged without a PR from the extension). A branch is deletable when (1) it exists in this repository, locally and/or in Azure DevOps, (2) a PR with `sourceRefName = refs/heads/<branch>` is `completed`, and (3) no PR from that branch is still `active` (a new PR may have been opened from it). Abandoned PRs do not count; the work item state is neither required nor blocking. `develop`, `main`, `master` and `release/*` are never offered, even if a PR used them as source. The rule is pure (`src/deletableBranches.ts`) and applies per branch to the branches of a work item (all of them, not only the main one) and of a task. PRs come from the ones already fetched for the cards (linked PRs); the command checks again with Azure DevOps (branch, active PR, completed PR) because the list can be minutes old. Existence is only asked to Azure DevOps for branches with a completed PR that are not local, through the same 10-minute cache as the task branches (`forgetBranch` after a deletion). Offered: branch rows (a **Delete** each), the card button only when exactly one branch is deletable (like Checkout, a card button would be ambiguous), the task pill menu (danger item; tasks of other developers do not get it), the command palette (lists them all), and the notification of one of my PRs being completed, merged with the existing offer to set its task Done (one notification; `notifications.events` `merged` or `taskDone` enabled). Finished work items with no completed-PR branch list only their local branches and say "No branch to delete": whether the main branch still exists is no longer asked for them.
- **Branch existence is asked to Azure DevOps** (`refs?filter=`), not trusted from local `origin/*` refs or Development links, which stay after a branch is deleted.
- **PRs / branches of other repositories** are shown dimmed; only this repository's PRs decide whether "Create PR" is offered.
- **Fixed-by links**: a Bug is "fixed by" a Backlog Item when the Backlog Item is its **predecessor** (some Bugs are really missing features). The reverse direction is just a dependency.
- **Startup waits for the git extension.** The built-in git extension announces a repository before its state is loaded: on a cold start `state.remotes` is empty for a while, so the organization / project / repository could not be detected and every first load failed until the next poll (about 2 minutes). `WorkItemsStore.whenRepositoryReady()` (`src/repositoryGate.ts`, decision in the pure `src/repositoryReadiness.ts`) resolves when the git API is `initialized` and the repository has remotes, or at once when `totalflowx.organization/project/repository` are all set. It gives up after 30 s so a repository that really has no `origin` still gets the clear error. During the wait the sidebar shows "Loading…" and nothing records or shows an error. The store loads, the pollers, the status bar, the Work Item Details panel and the dependency map await it before `resolveContext`, and so do the commands (the `command()` helper of `src/extension.ts`), so running one in the first seconds after a cold start waits instead of failing.

## Reviews and pull requests

- **Completed PRs of "My Pull Requests" are listed for a chosen period** (`totalflowx.myPullRequests.completedPeriod`: hidden / 24 h / 7 days / 30 days; default 24 h). The latest 50 completed PRs are fetched in one request. Completed PRs barely change, so their threads (for the timeline popover) are fetched **once per PR, only while it is inside the period**, and cached in the watcher (entries of PRs no longer returned are dropped); this keeps the request budget low even with 30 days. Completed PRs outside the period cost no requests. Only active PRs get policies, runs and build notes.
- **Waiting time counts from the publication** of the PR (last time it left draft, from the `IsDraftUpdate` system thread), not its creation: reviewers are not asked to review drafts.
- **Phases of a completed PR** (`src/pullRequestPhases.ts`; mini timeline, "took" and the header summary of "My Pull Requests"). Computed from the system threads already cached for the timeline popover, so no extra requests. Phases cover creation to completion without gaps: **draft** (created as draft until published, and again whenever re-drafted), **review**, shown as "In review" (from publication, or from a push after "waiting for author", until a reviewer votes; also the time until the last approval when several approvals are needed), **author**, shown as "Waiting for author" (from a "waiting for author" or "rejected" vote until the next push, reset or approval) and **merge**, shown as "Ready to merge" (from the last approval after which nobody asked for changes or reset the votes, until completion; it can be empty). Votes of the required reviewers decide when some of them voted, otherwise those of anybody but the author. Without threads, or without approvals in them, the PR counts as review until completion and merge is empty. Durations and the "took" total count **working time** (`totalflowx.reviews.workingDays`), like the review waiting time, so a PR left over a weekend does not look slow; the shares of the bands use the same scale (calendar time only when the whole PR lies on days off). The webview gives short phases a minimum width (`src/phaseLayout.ts`) and moves the event dots with the bands, so they stay on the phase where they happened. A re-vote after a push (the usual way a required approval is renewed) moves the start of merge to that vote, so the days between the first approvals and the push count as review.
- **The waiting time of a review counts working days only** (`totalflowx.reviews.workingDays`, default Monday to Friday; `src/workingTime.ts`). The team rule is "24 h" of working time, but counting calendar time made a PR published on Friday afternoon look 69 h overdue on Monday. All 24 hours of a working day count (it is not "3 office days"), so Friday 15:00 is due Monday 15:00. The due date, the time left, the urgency, the bar, the overdue reminder interval and the waiting time of published PRs in "My Pull Requests" use it, so authors and reviewers see the same number; drafts (age since creation) and "completed X ago" stay calendar time. Local time zone, days walked from midnight to midnight so daylight saving days are 23/25 h. **Holidays and days off are not handled** (they would need extra requests per iteration); a possible follow-up.
- **Required reviewers first**; optional reviews are listed only on demand. The overdue/due-soon counters count required reviews only (the 24 h rule is about them). Optional reviews are **tracked even while hidden**, so switching them on does not flood notifications (trade-off: an optional PR that became overdue while hidden does not notify at that moment).
- **"Ready to merge" (green) means nothing stops the merge**: published, every blocking policy satisfied (approvals included), no conflicts, no warnings. Waiting for approvals is not green.
- **"Next" line** is computed from the PR's **blocking branch policy evaluations**, not guessed.
- **Rule warnings only on published PRs** (drafts are work in progress). The Bug auto-complete rule is an _error_ (red): only testers may complete Bugs; when present, even "Will complete automatically" is shown in red.
- **Branches start from `develop`; another base is opt-in.** Team rule, so the default path has no extra question: the module picker only has an optional "Base" row. Large work items sometimes need a task branch built on another, unmerged branch of the same work item. The chosen base is stored in the local git config (`branch.<name>.totalflowxBase`): it is per machine and invisible to Azure DevOps, which is enough because Create PR runs on the machine that created the branch; branches without it target `develop` as always. Create PR ignores the stored base when its branch is gone or its PR is completed.
- **Retarget warning**: squash merges leave stacked branches behind (the PR still targets the merged base and would show its commits again), so a PR whose target has a completed PR of the user (or no longer exists, when the git extension already knows the remote branches) is flagged with a **Retarget to develop** action. It only uses data already polled; the PATCH needs a confirmation because it may require a rebase.
- **Reviewer/vote notifications ignore the user's own actions**; reviewer changes are attributed from the `ReviewersUpdate` system threads.
- **Checkout of a PR / branch never silently carries changes**: with uncommitted changes it asks (worktree / stash / anyway). "Create branch" creates without switching, then proposes Checkout or a worktree.
- **Worktrees** go to `<repo>.worktrees/<branch>` (the layout the team already used), copy `.env.local` files, open in a new window that runs `npm ci` once (marker in the worktree's private git dir, never in the working tree).

## CI, coverage and requests

- **CI runs are followed for the PRs of the user's work items and all the user's PRs**; fast polling (15 s) only while a run is active, otherwise an idle check (60 s) to discover re-runs/new pushes. A failed fetch keeps the last known runs.
- **Coverage is the coverage of the code tested by the PR's run** (the PR pipeline runs the affected tests). Shown to motivate: levels (60/80/95), positive deltas celebrated, decreases neutral (no blame), files below target to open, personal best and streak (only the user's own PRs, one entry per PR). No team ranking (it would push people to game the number).
- **Request budget**: tags come with the PR list (0 requests); "PR changed the build notes file" = 1 diff request per PR per push (cached by last pushed commit); branch existence, repository names, work item types are cached. The usage report and request log exist to keep this honest.

## Dependency map

- **Iterations are `<Project>\<Release>\<Sprint>`**: depth 1 = limbo (ignored, counted in a note), depth 2 = release container ("not scheduled in a sprint yet" column after its sprints), depth ≥ 3 = sprint.
- **Columns are sprint periods** (same start/finish dates), with one lane per team sprint, always in the same team order; different date ranges get their own columns. Do not compare iterations by the container's dates (a release starts long before its sprints).
- **Risk**: done → grey; predecessor in a release or limbo → "not scheduled yet"; same sprint period (even different teams) → tight; later period → late; earlier → ok. The same rule drives the cards' open-predecessor warnings and the Work Item Details panel.
- **Done work items are always shown** (the "Hide done" option was removed): hiding them cut the chains and made the arrows of the remaining work items look unexplained. What matters at a glance is handled by the dashed grey arrows and the state colours; "Hide bugs" and "Sort by state" cover decluttering.
- **Priority** (1 critical … 4 very low, `Microsoft.VSTS.Common.Priority`) is a pill in the card header with the same solid colours as the sidebar. **P1 work still to do glows in red** (not finished ones: the emphasis is about not missing critical work; they keep the pill): only a red halo **behind** the card (`box-shadow`), as if lit from behind, inspired by the lit cells of the UniFi UI. The card itself is unchanged (no red border or tint: the user preferred this to a thick outline and then to a tinted card), so "Mine" keeps its blue border. It is also the **tie-breaker of the ordering**: when two work items weigh the same, the higher priority goes first (P1 … P4, then no priority), then the ID.
- **Ordering of a lane** (pure, `layoutGraph`): barycenter, 8 sweeps alternating left→right and right→left (a single direction leaves the last columns unsettled), the weight of a card being the average **vertical position in pixels** of its neighbours (card centre, lane headers and gaps included), not its row: lanes of different sizes in different columns would skew a row index. Deterministic: ties by priority then ID; the result does not depend on the order of the input.
- **Sort by state** (off by default) groups each lane by state in this order: in progress (Committed, In Progress, Active), not started (New, Approved, To Do, and any state we do not know: the `proposed` category), finished (Ready to Test, Done, Closed…), removed. Rationale: **active work first**, finished work is context. Inside a group the line-straightening order applies, so with the option on some arrows cross more: that is the price of the grouping.
- **Hide bugs** (off by default) hides Bug work items and their arrows; the focused work item is never hidden. It is applied **before** the "without dependencies" rule: a work item whose only links were to hidden bugs has nothing left to show, so it is hidden too unless "Show work items without dependencies" is on (the point of hiding bugs is to declutter, and a lone card would look like a work item with no dependencies at all). The "+N" count still includes dependencies that are bugs.
- Work items without dependencies are shown on demand.

## UI choices

- Compact layout is the default for work items and both PR boxes; a compact row unfolds into the full card in place.
- Boxes (Waiting for your review, My Pull Requests) look like framed panels, deliberately different from the iteration group headers.
- **The activity bar badge lives on the native "Summary" tree view, not on the webview view.** VS Code creates (resolves) a webview view only when it is first shown, so on a cold start there is no `WebviewView` to set `badge` on until the user opens the sidebar. A `TreeView` made with `createTreeView` at activation exists immediately, so `src/summaryView.ts` sets its badge (work items with alerts + PRs waiting for review, `src/summaryRows.ts`) at startup and on every change of the store and the watchers. The webview view must not set a badge too: the container would show a double count. Whether the badge of a _collapsed_ tree view reaches the container icon must be confirmed in a real VS Code.
- The PR history popover lists the latest events first.
- Figma links open in the Figma VS Code extension when installed, but it does not select the linked frame (limitation of that extension, v0.4.7); the browser button opens the exact frame.

## Naming and identity

- Namespace `totalflowx.*` for settings, commands, views; display name "Totalflow X devtools for Azure Devops". The **extension ID stays `abb-totalflowx.vscode-azdo-workitems`** so installed state (globalState) survives renames; the coverage records keep their old storage key `azdoWorkItems.coverageRecords:` for the same reason.
- The per-work-item tab is the **Work Item Details panel**; its button on cards is "Details".

## PR tasks: one per PR, matched by link

- A work item may have several PRs, so the PR-task alerts are per PR. A PR's task is the child task **linked to the PR** (ArtifactLink "Pull Request"), whatever its title; the title pattern (`totalflowx.alerts.pullRequestTaskPattern`) is only a legacy fallback for PRs with no linked task, used once. Why: the title matched only "the" PR task, so work item 66068 (PR 13770 completed with task 60985 Done, PR 13765 active with task 60984 "PID update" In Progress) was flagged wrongly.
- Create PR links the task through `workItemRefs` of the PR but keeps it out of the title ids (`[<ids>]` are the Backlog Items / Bugs). Publish and completion are **not** automatic in the same way: publish (user's own action, in the extension) moves the task to In Progress; completion only _offers_ Done, since the task may still have work left. It reuses the "merged" detection of the notifier (baseline, no new polling); the task lookup costs two requests per completed PR.
- Failing to create or move a task never undoes the PR: it only warns.
- Branches created from a task row use the **parent's id and type** (team rule `<type>/<module>/<id>-<name>`, and `src/naming.ts` detects the work item from that id), with the short name proposed from the task title; the team already names extra branches that way (`feature/fui-common/66068-related-changes`). They are linked to the task as well as to the parent to tie task, branch and PR together: the task row then hides **Create branch**, and **Create PR** from the task prefers the task's linked branches over the parent's.
- **Task rows show every linked branch, deleted ones dimmed instead of hidden**: a Development link outlives its branch, and hiding it would make a task look branchless (and offer **Create branch** wrongly, which already keys on links). Existence of the branches linked to tasks is asked to Azure DevOps (`refs?filter=`, one request per distinct branch) and cached in memory for 10 minutes; a local branch with the same name counts as existing, and a failed request leaves the branch "not verified" (not deleted). In the actions menu of the task pill, a branch that exists offers **Checkout** (`checkoutHere`, kind `task`, straight to checkout) and **Open in a worktree** (`openWorktree`); deleted and other-repository branches are listed dimmed, without action. A branch whose PR is completed and that still exists also offers **Delete branch** (danger item).
- **One pill per task row, with an actions menu, instead of an icon per branch / PR plus two dashed create buttons**: the row of a card is narrow (260 px) and up to five small controls with different click meanings were confusing. The pill only summarises (icons coloured by state, counts; a dim "+" when empty); hover keeps the detail cards, click opens a menu anchored under the row (same width as the row, so it needs no JS positioning) that lists every action (checkout, worktree, open PR, create branch / PR). Only one menu is open at a time; its state (`openTaskMenu`) survives the re-renders caused by model updates and is dropped when its row disappears. Pure rules: `src/taskMenu.ts`.
- **Branch rows: one badge and icon buttons, details in tooltips**: a row had a location pill, a worktree pill, a text "Checkout ▾" / "Open worktree ▾" and "Delete", so in a 260 px sidebar the name (long: `feature/<area>/<id>-<title>`) was truncated to a few characters, and the name is what identifies the row. Now there is **one badge** (`src/branchBadge.ts`, pure and tested: location, `not deleted` when the PR is merged, plus `⧉` when a worktree has the branch, with the worktree tone) and **icon buttons** (checkout / worktree icons with the same ▾ menu, trash for Delete) whose `title` / `aria-label` carry the words ("Checkout <branch>", "Open the worktree of <branch>", "Delete the branch <name>"). What the short badge cannot say (what `local` means, the worktree folder, why it is `not deleted`) is in the badge tooltip. Only branch rows are compact (`checkoutButton({ iconOnly })`): the card-level and PR-box Checkout buttons keep their text because they are the primary action there. The `⧉` is a character, not an SVG, so the badge keeps one text colour and no extra width.
- **Branch rows use the same popover menu as task rows**: a row keeps its compact icon split button (Checkout or Open worktree + ▾) and its trash button, so the common action stays one click; the **▾** opens the in-card actions menu under the row (`src/actionMenu.ts` types, `src/actionMenuHtml.ts` renderer, `src/branchMenu.ts` pure and tested items) instead of a native QuickPick, the same kind of menu as the task pill. A single "⋯" button replacing both was tried and rejected by the user: they prefer the visible icons. Task and branch menus share one open-state (`openMenu`, keyed `task-<id>` / `branch-<id>-<name>`), so only one is open, and the same keyboard, outside-click, scroll and focus handling. The menu also lists Delete branch (danger) next to the trash button. "Remove worktree" is the only new message (`removeWorktree`, sharing the confirmation of the QuickPick). The PRs of a branch are not in its menu: the card's PR rows already have the buttons and the model has no source branch per PR. The Work Item Details panel has no menu machinery (no open state, a different script), so `renderBranchList` without `popover` keeps the ▾ QuickPick there.
- **Coloured icons in the action menus**: each item gets an icon and a colour from its action (`actionMenuIcon` in `src/actionMenu.ts`), not from the menu it is in, so the same action looks the same in the task and branch menus and users recognise it before reading. Colours are the theme's chart colours (dark and light); on the hover / focus selection background the icon takes the selection colour, because a blue icon on a blue selection would vanish. Create actions reuse the icon of what they create with a +.
- **The open menu points at its trigger**: the menu spans the row (long branch names fit at 260 px), so its edge is far from the ▾ or pill that opened it. The trigger stays pressed (`aria-expanded='true'` styled with the theme's active-toggle colours, ▾ rotated to ▴) and a notch on the menu's top edge sits under the trigger's centre (`--notch-x`, set through CSSOM by `pointMenuAtTrigger` after each render, because of the CSP). Aligning the menu to the trigger instead was rejected: it would make the menu narrower and wrap long names.
