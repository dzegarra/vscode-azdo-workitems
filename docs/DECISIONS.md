# Decisions

Why the extension behaves the way it does. Each entry: the decision, and the reason (often a team rule or something learned about Azure DevOps). Add an entry when you make a choice someone could later "fix" without knowing why, and correct or remove the entries a change makes wrong — in the same change (developers and AI agents alike).

## 1. General rules

**Release and hotfix procedures are deliberately not implemented yet.** The release and hotfix rules of [DEVELOPMENT_APPROACH.md](DEVELOPMENT_APPROACH.md) §8.1–8.2 (`release-*` branches, Release → Main and Main → Develop merges with Rebase and fast-forward, release PRs such as `[0000] Release - 1.0`, version tags on Main, the Checkpoint tag of PRs, feature branches created from a Release branch, Hotfix branches from Main; tracked in [DEVELOPMENT_APPROACH_COVERAGE.md](DEVELOPMENT_APPROACH_COVERAGE.md) as ⏸) are important, but they only apply once a release branch is created and developers stop working on new features (only bug fixes before the release). That is still a few months away (decided 2026-10-24); the extension will be updated a few days before it starts. Until then, do not add rules, warnings or flows for them, and do not report them as missing. One exception: `develop-*`, `release-*` and `hotfix-*` are already **protected** from Delete branch (DELETABLE-1), since that only prevents a mistake. Merge types of release PRs will never be checked: Azure DevOps branch policies already block the invalid ones.

**Where the extension departs from DEVELOPMENT_APPROACH.md on purpose** (details per rule in [DEVELOPMENT_APPROACH_COVERAGE.md](DEVELOPMENT_APPROACH_COVERAGE.md)):

- **Modules of the branch names**: the document's areas (`module`, `license`, `persistent`, `adaptercpp`…) are the backend team's; the UI team has its own catalog (`branches.modules`, `fui-*`, `pmui-*`). Do not align it with the document.
- **Work items completed on merge** (§8.2.5): it applies to Backlog Items only. Developers never complete Bugs: only testers, once they confirmed the fix (PR-WARN-3); a merged Bug goes to Ready to Test with "Integrated in Build" set. The document is wrong here.
- **Fix branches**: the document's revision AB says `anomaly/*`, the team uses `bugfix/*` (also in the July version of the document); waiting for the architect, keep `bugfix` until then.
- **Whole team as optional reviewers** (§8.2.1) and **comments resolved / approvals before completing** (§8.2.3) are enforced by Azure DevOps policies; the extension does not check them.

### Redesign (2026-10)

The UI is being rebuilt from a design made with all the rules known in advance (Claude Design canvas "Totalflow X Devtools Redesign", <https://claude.ai/artifact/DMR5fwa1qJBSPC5p5L8vJL>, private to its owner). Decisions taken with the user:

- **Every rule answers one question: what needs me now?** Each rule feeds one of five verbs, in the order of who waits on whom: review (a colleague waits on your vote), unblock (your PR waits on you), fix (a work item breaks a team rule), ship (nothing stops your merge), clean (branches and worktrees that can go; never urgent, never in the badge). A broken base branch is above all verbs. The badge, the status bar, the Summary view, the "Needs you" queue, the card and the details panel show the same signals with more detail at each step; the queue is built from the existing rules only (NOW-\*), so they cannot disagree.
- **The track**: every work item goes through six stations (Branch, Pull request, CI, Review, Ready to be merged, Done / Ready to Test) and each rule lights the station it belongs to (TRACK-\*). "Ready to be merged" and not "Merge", which reads as "being merged".
- **Delivered in phases on one branch**, each passing `npm run check` and reviewed by the user: pure models, sidebar, details panels, status bar / Summary / banners, Track board tab, Sprint timeline tab, Whole team views.
- **Documents and canvas follow the same seven blocks** (General rules, Sidebar, Work Item Details panel, Track board, Sprint timeline, Dependency map, Status bar & notifications): the documents were ordered by when things were built (sections 1-12, redesign phases), so a rule of one view was spread over several places. Rules used by more than one view, the actions and flows, the data shared by the Whole team views, look, fun and settings are General rules; each view keeps its own Whole team part. Rule IDs did not change. Superseded designs move to the Archive page of the canvas instead of being deleted: they may hold ideas to rescue later.

### Scope and data

- **Only the user's work items** ("Assigned to Me", "My Work Items"), in the **current iteration of every team the user belongs to** (`teams?$mine=true`), unless teams are selected. Teams sharing a sprint are merged; different sprints are grouped.
- **Tasks are never cards of their own** nor filter values: they are parts of their Backlog Item / Bug, always nested in its card (including tasks assigned to other developers, with their initials). Tasks are not shown in the dependency map and get no "Dependency map" button.
- **Several branches per work item**: named after it, Development links, source branches of its active PRs. The **main branch** (checked out, else named after it, else the link) drives the card's buttons; each other branch of this repository has its own Checkout. Finished work items list only their deletable branches (completed PR, see below) and other _local_ branches, because remote refs and links outlive deleted branches.
- **Delete branch is offered when the branch's PR is completed, not when the work item is finished**: the team deletes a branch once its PR is merged, and the state of the work item says little about it (a Backlog Item with several PRs stays Active while its first branch is already merged; a Done one may have been merged without a PR from the extension). A branch is deletable when (1) it exists in this repository, locally and/or in Azure DevOps, (2) a PR with `sourceRefName = refs/heads/<branch>` is `completed`, and (3) no PR from that branch is still `active` (a new PR may have been opened from it). Abandoned PRs do not count; the work item state is neither required nor blocking. `develop`, `main`, `master`, `develop-*`, `release-*`, `release/*` and `hotfix-*` are never offered, even if a PR used them as source. The rule is pure (`src/deletableBranches.ts`) and applies per branch to the branches of a work item (all of them, not only the main one) and of a task. PRs come from the ones already fetched for the cards (linked PRs); the command checks again with Azure DevOps (branch, active PR, completed PR) because the list can be minutes old. Existence is only asked to Azure DevOps for branches with a completed PR that are not local, through the same 10-minute cache as the task branches (`forgetBranch` after a deletion). Offered: branch rows (a **Delete** each), the card button only when exactly one branch is deletable (like Checkout, a card button would be ambiguous), the task pill menu (danger item; tasks of other developers do not get it), the command palette (lists them all), and the notification of one of my PRs being completed, merged with the existing offer to set its task Done (one notification; `myPullRequests.notifications` `merged` or `taskDone` enabled). Finished work items with no completed-PR branch list only their local branches and say "No branch to delete": whether the main branch still exists is no longer asked for them.
- **Branch existence is asked to Azure DevOps** (`refs?filter=`), not trusted from local `origin/*` refs or Development links, which stay after a branch is deleted.
- **PRs / branches of other repositories** are shown dimmed; only this repository's PRs decide whether "Create PR" is offered.
- **Fixed-by links**: a Bug is "fixed by" a Backlog Item when the Backlog Item is its **predecessor** (some Bugs are really missing features). The reverse direction is just a dependency.
- **Duplicates** (`src/duplicates.ts`, alerts in `src/alerts.ts`). The work item holding the "Duplicate Of" link (`Duplicate-Reverse`) is the duplicate, the other end the original. Team rule: the two are planned in the same iteration and move through the same states. Decisions: (1) it is a **red alert**, not an amber caution, because it is a team rule to fix, so it counts in the badge, the status bar and the Summary, and skips the filters with `filter.alwaysShowAlerts`; (2) the states must be **the same state** (spelling-tolerant, STATE-1), not only the same category, and it is the **real** state that counts, never the shown "In review" (STATE-10), which would flag pairs whose Azure DevOps states are identical; (3) **both sides** get the alert, so an original in the list warns about a duplicate assigned to someone else, and a pair where both are in the list counts twice (each breaks the rule); (4) **unknown means silent**: the related work items come with the predecessors / successors in the same batched request (no extra request), and the ones that could not be loaded say nothing (a false red alert costs more than a missed one); (5) the quick fix only **opens** the other work item, as which side to move is the developers' call; (6) a duplicate's card is **toned down** (dashed left bar, faded title only, so the buttons and the popovers inside keep their contrast) because the work is tracked on the original, but not while it has an alert, which must stand out; (7) the Dups filter only has a "Duplicates" chip (hiding the originals makes no sense) and only appears when some card is a duplicate. Like every alert they only apply to `alerts.workItemTypes` (ALERT-GATE).
- **Startup waits for the git extension.** The built-in git extension announces a repository before its state is loaded: on a cold start `state.remotes` is empty for a while, so the organization / project / repository could not be detected and every first load failed until the next poll (about 2 minutes). `WorkItemsStore.whenRepositoryReady()` (`src/repositoryGate.ts`, decision in the pure `src/repositoryReadiness.ts`) resolves when the git API is `initialized` and the repository has remotes, or at once when `totalflowx.organization/project/repository` are all set. It gives up after 30 s so a repository that really has no `origin` still gets the clear error. During the wait the sidebar shows "Loading…" and nothing records or shows an error. The store loads, the pollers, the status bar, the Work Item Details panel and the dependency map await it before `resolveContext`, and so do the commands (the `command()` helper of `src/extension.ts`), so running one in the first seconds after a cold start waits instead of failing.

- **The sprint title says what the teams share, not the iteration of one team** (SPRINT-TITLE-1): the user usually follows 4 teams whose iterations have the same dates and the same number ("Platform Sprint 122", "UX Sprint 122"…), so "Sprint 122" says it all; the name of the first team's iteration suggested only that team was shown. The full names stay one hover away on the "4 teams" chip.

### Pull requests and reviews

- **Waiting time counts from the publication** of the PR (last time it left draft, from the `IsDraftUpdate` system thread), not its creation: reviewers are not asked to review drafts.
- **Phases of a completed PR** (`src/pullRequestPhases.ts`; mini timeline, "took" and the header summary of "My Pull Requests"). Computed from the system threads already cached for the timeline popover, so no extra requests. Phases cover creation to completion without gaps: **draft** (created as draft until published, and again whenever re-drafted), **review**, shown as "In review" (from publication, or from a push after "waiting for author", until a reviewer votes; also the time until the last approval when several approvals are needed), **author**, shown as "Waiting for author" (from a "waiting for author" or "rejected" vote until the next push, reset or approval) and **merge**, shown as "Ready to merge" (from the last approval after which nobody asked for changes or reset the votes, until completion; it can be empty). Votes of the required reviewers decide when some of them voted, otherwise those of anybody but the author. Without threads, or without approvals in them, the PR counts as review until completion and merge is empty. Durations and the "took" total count **working time** (`totalflowx.reviews.workingDays`), like the review waiting time, so a PR left over a weekend does not look slow; the shares of the bands use the same scale (calendar time only when the whole PR lies on days off). The webview gives short phases a minimum width (`src/phaseLayout.ts`) and moves the event dots with the bands, so they stay on the phase where they happened. A re-vote after a push (the usual way a required approval is renewed) moves the start of merge to that vote, so the days between the first approvals and the push count as review.
- **The waiting time of a review counts working days only** (`totalflowx.reviews.workingDays`, default Monday to Friday; `src/workingTime.ts`). The team rule is "24 h" of working time, but counting calendar time made a PR published on Friday afternoon look 69 h overdue on Monday. All 24 hours of a working day count (it is not "3 office days"), so Friday 15:00 is due Monday 15:00. The due date, the time left, the urgency, the bar, the overdue reminder interval and the waiting time of published PRs in "My Pull Requests" use it, so authors and reviewers see the same number; drafts (age since creation) and "completed X ago" stay calendar time. Local time zone, days walked from midnight to midnight so daylight saving days are 23/25 h. **Holidays and days off are not handled** (they would need extra requests per iteration); a possible follow-up.
- **Required reviewers first**; optional reviews are listed only on demand. The overdue/due-soon counters count required reviews only (the 24 h rule is about them). Optional reviews are **tracked even while hidden**, so switching them on does not flood notifications (trade-off: an optional PR that became overdue while hidden does not notify at that moment).
- **"Ready to merge" (green) means nothing stops the merge**: published, every blocking policy satisfied (approvals included), no conflicts, no warnings, and every **required reviewer** has approved. Waiting for approvals is not green.
- **Required reviewers block "Ready to merge" even without branch policies** (`pendingRequiredReviewers`, src/myPullRequests.ts). Why: `isReadyToMerge` only looked at policy evaluations, and a PR whose target is a feature branch has none (PR 13847: 0 evaluations, two required people at vote 0 was shown as ready). Pending = required, not the author, not declined, vote below 5 (approved with suggestions counts as approved); people who sent the PR back (waiting / rejected) are left out because the feedback steps and warnings already name them (no duplicate text). A required group is listed only when no required person is pending and nobody but the author approved, since a group votes through its members. Next says `Approval of <names> missing` unless a blocking "Required reviewers" / "Minimum number of reviewers" policy step already says it. A PR with no approval from anybody but the author, and no blocking reviewer policy, is not ready either and Next says `No approvals yet` (only when nothing else is missing). Unknown policies (not fetched) do not trigger `No approvals yet`.
- **Next and Ready agree**: `Ready to merge` / `Will complete automatically` are only produced without warnings; with warnings and nothing else missing, Next says `Fix the warnings` (amber, red when a warning is an error). Why: the card used to say "Ready to merge" in green next to a missing Ready badge when only a warning (e.g. auto-complete without deleting the branch) was left. `nextTone` is `ready` only without warnings.
- **"Next" line** is computed from the PR's **blocking branch policy evaluations**, not guessed.
- **Size and age of a PR are cautions, not warnings** (MYPR-CAUTION-\*): every warning keeps a PR from being Ready and says "Fix the warnings", but a PR open for a week or changing 80 files cannot be fixed by its author right before merging; blocking it would only delay the merge more. Muted text, no effect on Ready, the pulse, the Summary or the status bar. Files are counted once per push (cached by the last merge source commit), 2 requests.
- **"Behind develop" is shown with Restart merge, not as a problem** (MYPR-BEHIND-1). The team rule is to merge develop into the branch before the PR (§8.1.2), but being behind is harmless: the risk is conflicts, and Azure DevOps only finds them when it merges the PR again (a push, a completion, or Restart merge). The extension does not restart the merge by itself (it is a write, and it would run on every poll); the user asks for it, after a confirmation. The count costs one request per PR after a push and at most every 10 minutes otherwise, because develop moves without the PR changing. Hidden while conflicts are already known.
- **The merge type is only checked for PRs into the base branch** (PR-WARN-11): release PRs use Rebase and fast-forward, and Azure DevOps policies already block invalid merge types there; only an auto-complete set with another type than squash on a PR into develop is flagged (without auto-complete, the type is chosen when completing, and Complete… uses squash).
- **Rule warnings only on published PRs** (drafts are work in progress). The Bug auto-complete rule is an _error_ (red): only testers may complete Bugs; when present, even "Will complete automatically" is shown in red.
- **A PR sent back by a reviewer is never "Ready to merge"**: branch policies do not count "Waiting for author" (-5) or "Rejected" (-10) votes, so PR 13765 showed "Ready to merge" while a required reviewer was waiting for its author. Those votes now give a warning (Rejected: an error) and a Next step, which also keeps the PR out of "Ready to merge" and counts it in the Summary. People are named; a group only when none of its members is listed with the same vote (a group mirrors its members' votes). Their status badges are solid amber / red with a fixed text colour, like the other pills that must read in any theme.

### States, alerts and cautions

- **"In review" is a derived, display-only state, and it can be switched off (`totalflowx.workItems.showInReviewState`).** Backlog Items and Bugs have no such state in Azure DevOps, and a Committed item whose only remaining work is getting its PRs approved looked the same as one still being coded. The team's PR task already stands for "in review" (see PR tasks), so the state is derived from the tasks (Rule STATE-10): Committed, at least one task In Progress, every In Progress task a PR task, every other task Done (Removed ignored). A PR task is one whose title matches `alerts.pullRequestTaskPattern` **or** that is linked to a PR, so neither a missing link nor an unusual title hides it. No tasks, or all of them Done, does not count: nothing is waiting for review. Actions, alerts, task rules and **Change state** keep the real state (the tooltip of the button tells it), so nothing depends on a state Azure DevOps does not have. The Dependency Map and the Work Item Details panel show it only for work items whose tasks are known (the user's own work items; the open item of the panel, whose children are fetched anyway): fetching the tasks of every predecessor and successor would cost requests, so those keep their real state.
- **Work started without tasks and stretch tags are red alerts; title prefix and story points go into the orange caution; a work item not updated gets a sleep icon** (ALERT-12, ALERT-13, COMPLETE-5, COMPLETE-6, REMIND-1). Tasks and stretch tags are rules the developer of the work item applies (§9.5, §13.4), so they are problems to fix now. The title and the story points are set by the Team Lead who creates the item (§7.1), so they are a pre-completion checklist, like the empty fields. The reminder (not updated for a working day) is not an error, and **not an issue before completion either**: that caution only lists what can block completing the item (the user's definition), and a forgotten item can be completed. It was first listed there, then moved to a "zZ" (sleep) badge before the title, with the details in its tooltip: it says "this item seems asleep" without counting as a problem. A quiet amber icon was not noticed, so (user's request) the badge is solid orange with the days (`zZ 5d`) and **the border of the card pulses in orange every 2 s, together with the badge** (REMIND-3): the goal is that the item is not forgotten, and the badge pulsing with the border tells where the explanation is. Once a second was tried and found too fast; 2 s is a little faster than the 2.4 s pulse of the PR tiles. Only the colour of the card's own border changes (an outer ring made the border look thicker than the others). It stops while the pointer or the focus is on the card (the normal hover border, the colour of the work item, shows: the user is already looking). **Alerts and "working on" have priority**: those cards keep their red / blue look and only the static badge (an alert is already louder; working on it means it is not forgotten). Personal opt-out `appearance.asleepPulse` (`application` scope, like the other animations); reduced motion gives a steady orange border. The orange is the fixed `#f0883e` of "Waiting for author", with dark text, readable on dark and light themes. **No reminder about the end of the sprint** (it was built, then removed at the user's request): the caution is about what blocks completion, finishing before the sprint ends is obvious, and the days left are already shown. **The stretch title prefix is optional and off by default** (`alerts.stretchTitlePrefix` empty): the document asks for a `[Stretched]` prefix, but the team was never told and suffixes "Stretched" to the titles instead (asked to the architect; the document's own example 3 uses a suffix too); only "more than one stretch tag" is checked until then. The **Stretch** action itself (copy, effort split, tag) is out of scope: a process to design separately. Title prefixes are a team list that grows (`alerts.titlePrefixes`, brackets included).
- **An iteration outside the sprint plan of the area's teams is a red alert** (ALERT-14). Azure DevOps shows a work item on a team's sprint board only when its area belongs to the team and its iteration is among the team's selected sprints; otherwise it is invisible there (example: area Platform Framework with the iteration Interface Apps Sprint 123). The rule reads the areas (`teamfieldvalues`) and the iterations of **all** project teams, not only the user's: the team that owns the area is usually not one of theirs. Any covering team that planned the sprint is enough. **Unknown means silent** (like ALERT-12): a team that could not be read, no team covering the area, or a container iteration raise nothing, because a false alarm costs more than a missed one. The plans are cached in memory for 1 h (about 2 requests per team, at most 6 in flight): team settings rarely change. Only the user's own work items of the current sprints are checked; the Whole team views have no alert rules (TEAM-5). No button: the fix (iteration or area) is the user's decision.
- **One orange caution for what blocks completion (open predecessors, blocking tags, empty fields), and no "ready to start" badge nor start confirmation**: the green "ready" showed on every not started item without links, so it said little, and the modal before starting got in the way of work that is allowed. Orange means warning, not blocker: starting is free, completion is what the issues block. So the caution covers every _open_ work item (not only the not started ones) and the popover lists the details of each issue: open predecessors, tags of `alerts.blockingTags` (user-editable, no new setting), and, for Backlog Items only, an empty Acceptance criteria and the empty `alerts.requiredFields` (Effort, Effort in days). Closed items show nothing. Blocking tags have no red alert (there used to be "Started while tagged"): starting an item with such a tag is allowed, only completing it is blocked, so the orange caution is the right level and showing both was a duplicate. Empty required fields still overlap (red "… is empty" and the caution); that is accepted: the alert is a red problem in the work, the caution a pre-completion checklist that also shows before starting. Acceptance criteria is HTML (Azure DevOps rich text), so `<div><br></div>` and `&nbsp;` count as empty; the field is already in the work item response (`$expand=relations`), so it costs no request. Alerts disabled (`alerts.enabled` off) means no rules, so only the predecessors remain.

### A merged PR is not Done while work is left

Work items 37691 (state Approved) and 60840 (one Task not started) showed in Done on the Track board because their PR was merged. The Done station (TRACK-7) now asks for the state and the tasks too: with a not started state or an open task it stays pending ("PR merged · 1 task open") and the card goes back to coding (BOARD-3: To start when not started, else Branch · Draft). Only a started work item with every task done or removed is the user's move to Done. Why: a PR is one slice of the work, not the work item.

### Actions and flows

- **Removed work items are closed for branch actions** (`isClosedState`: done category or removed): no Create branch / Checkout / Create PR, only Delete branch when deletable, the same as the task rules (`canCreate*ForTask` exclude done or removed parents). The branch rows and the compact branch signal use the same function.
- **"Open in a worktree" in the pickers creates the worktree** when the branch has none (`openOrCreateWorktree`, with the pure `worktreeOpenAction`): the items of the pickers of the task pill and the branch rows post `openWorktree`, which used to throw "has no worktree" for branches without one. It opens the worktree when it exists, as before.
- **Complete… moves the work items itself; Azure DevOps never transitions them** (`transitionWorkItems` false, src/pullRequestCompletion.ts, COMPLETE-PR-\*). DEVELOPMENT_APPROACH §8.2.5 says to complete the associated work items, but that is only right for Backlog Items: developers never complete Bugs (only testers, once they confirmed the fix), and Azure DevOps' option would complete both. So Backlog Items go to Done and Bugs to Ready to Test with "Integrated in Build" (the value of **Fill**, asked first and editable; an existing value is overwritten, since the build with this fix is a new one). A Backlog Item or Bug that still has another open task or another active PR is **kept** and the confirmation says why: moving it would raise ALERT-1 (Done / Ready to Test with open tasks) or close work that goes on in another PR; a PR that cannot be read counts as active, for the same reason. The work items are fetched again (not taken from the list) because the flow writes. The PR is completed at the commit of the card, so a push in between makes Azure DevOps refuse it; a failed work item update after the merge only warns (a merge cannot be undone). Only on the user's own PRs that are Ready to merge without auto-complete: the author completes the PR (§8.2.3), and with auto-complete Azure DevOps does it.
- **The acceptance criteria open with the checkout of a review** (REVIEW-CARD-6, REVIEW-AC-1, `reviews.openAcceptanceCriteria`): required reviewers verify them (§10), and the checkout is when the review starts. In a worktree the panels must open in its own window, which only exists after `vscode.openFolder`, so the ids travel in the setup marker of the worktree (the one that asks for `npm ci`, merged with it). VS Code only focuses a window already open on the folder, which then never reads the marker: a marker older than 2 minutes is ignored, so a later reload does not open old panels.
- **Branches start from `develop`; another base is opt-in.** Team rule, so the default path has no extra question: the module picker only has an optional "Base" row. Large work items sometimes need a task branch built on another, unmerged branch of the same work item. The chosen base is stored in the local git config (`branch.<name>.totalflowxBase`): it is per machine and invisible to Azure DevOps, which is enough because Create PR runs on the machine that created the branch; branches without it target `develop` as always. Create PR ignores the stored base when its branch is gone or its PR is completed.
- **Retarget warning**: squash merges leave stacked branches behind (the PR still targets the merged base and would show its commits again), so a PR whose target has a completed PR of the user (or no longer exists, when the git extension already knows the remote branches) is flagged with a **Retarget to develop** action. It only uses data already polled; the PATCH needs a confirmation because it may require a rebase.
- **Checkout of a PR / branch never silently carries changes**: with uncommitted changes it asks (worktree / stash / anyway). "Create branch" creates without switching, then proposes Checkout or a worktree.
- **Worktrees** go to `<repo>.worktrees/<branch>` (the layout the team already used), `<repo>` being the main working tree even when the command runs from a worktree window (otherwise, with `/` in branch names, each worktree got its own nested `.worktrees` maze; `mainWorktreeFolder`); the `.env.local` files are copied from the main working tree, copy `.env.local` files, open in a new window that runs `npm ci` once (marker in the worktree's private git dir, never in the working tree).
- **Leftover worktrees are tracked from what is already loaded, plus local git** (src/worktreeHygiene.ts pure, src/worktreeTracker.ts, WORKTREE-STALE-\*, WORKTREE-IDLE-\*). Developers forget the worktrees of merged PRs and finished reviews: once the item leaves the sidebar nothing pointed at them. The status comes from the PRs of the listed work items, My Pull Requests (active + recent completed), the active PRs where the user is a reviewer (closed ones only while "Reviewed" fetches them), the work item states and `git for-each-ref` (upstream `[gone]`, last commit date). No request is added: an unknown branch simply stays "in use" rather than costing a PR lookup per branch. `git status` per worktree (the ● flag) is read again at most every 5 minutes, or when the list changes, the view is refreshed or a picker opens.
- **The extension records what each worktree it creates is for** (`totalflowx.worktreeOrigins` in the global state: folder, branch, work item / task / PR id, date; WORKTREE-ORIGIN-1). Without it, a review worktree could not be told apart once the PR leaves the review list (the branch is not the user's, nor linked to a listed work item). Recorded through `WorkItemsStore.announceWorktree` / `onDidCreateWorktree`, since every checkout flow already has the store; a folder re-used for another branch drops its origin.
- **Uncommitted changes never hide a stale worktree**: they are shown (● and "uncommitted changes") and the removal still asks with "Remove (changes will be lost)". Hiding them would leave exactly the worktrees that are easiest to forget. Locked worktrees are never stale: a lock is a deliberate "keep". Approved reviews and old commits are only _idle_, not removable: the author may push again, and an old branch may still be in use.
- **The Remove Worktrees picker pre-selects the stale ones** (WORKTREE-PICK-1): the common case is removing exactly those; a separate **Clean Up Worktrees…** (Summary row, notification, view title) hides the ones in use.

### PR tasks: one per PR, matched by link

- A work item may have several PRs, so the PR-task alerts are per PR. A PR's task is the child task **linked to the PR** (ArtifactLink "Pull Request"), whatever its title; the title pattern (`totalflowx.alerts.pullRequestTaskPattern`) is only a legacy fallback for PRs with no linked task, used once. Why: the title matched only "the" PR task, so work item 66068 (PR 13770 completed with task 60985 Done, PR 13765 active with task 60984 "PID update" In Progress) was flagged wrongly.
- Create PR links the task through `workItemRefs` of the PR but keeps it out of the title ids (`[<ids>]` are the Backlog Items / Bugs). Publish and completion are **not** automatic in the same way: a published PR moves its task to In Progress (Publish in the extension right away; PRs published elsewhere on the next load, see below); completion only _offers_ Done, since the task may still have work left. It reuses the "merged" detection of the notifier (baseline, no new polling); the task lookup costs two requests per completed PR.
- Failing to create or move a task never undoes the PR: it only warns.
- **The tasks of PRs published elsewhere start by themselves** (`src/pullRequestTaskStarter.ts`, Rule TASK-PR-8, `totalflowx.pullRequestTasks.startWhenPublished`, on by default). Before, only Publish in the extension moved the task, and a PR published in Azure DevOps (or created published elsewhere) only raised ALERT-4 with a **Fix** button. Choices: (1) it runs **after each load of the list** and uses what the load already fetched (the tasks of the user's work items, also the ones of other developers, and their PRs): the only extra request is the user's id, once, and none at all when no task has a published PR; (2) **only the PRs the user created** (`createdBy.id`): a write to Azure DevOps on behalf of the user must come from the user's own work, and a colleague's extension moves the tasks of their PRs; (3) **Done and Removed tasks are left alone** (as with Publish, TASK-PR-4): reopening a closed task is a decision, so ALERT-4 still reports it; (4) **once per task / PR pair and session**: a failure is not retried on every load, and a task moved back by hand is not fought; (5) a notification says which tasks moved, then the list reloads. PRs linked to tasks outside the user's work items are not seen (that would cost requests per PR).
- **Create PR is offered per task branch, not per task.** A task can have several branches (e.g. a rework branch next to the first one) and one active PR used to hide **Create PR** for all of them. Now each usable branch (here and not deleted) without a PR, or with only an abandoned one, gets **Create PR from <branch>**, and the choice skips the branch question. Branches with a completed PR are left out on purpose: the team deletes them once merged (**Delete branch** is offered instead). A task with no usable branch keeps the old generic item (no active PR), which falls back to the branches of the work item.
- Branches created from a task row use the **parent's id and type** (team rule `<type>/<module>/<id>-<name>`, and `src/naming.ts` detects the work item from that id), with the short name proposed from the task title; the team already names extra branches that way (`feature/fui-common/66068-related-changes`). They are linked to the task as well as to the parent to tie task, branch and PR together: the task row then hides **Create branch**, and **Create PR** from the task prefers the task's linked branches over the parent's.

### Task branches and "Working on"

- **Link an existing branch to a task from its pill** (`Link to <branch>` for the branches of the work item, `Link another branch…` for any branch of the remote): developers often work on the branch of the Backlog Item, or on a branch created outside the extension, and the task then had no branch (no pill state, no "Working on", no PR task match). The branch is also linked to the **work item** when it does not have it: a task branch that the work item does not link raises ALERT-2 at once, so asking would only add a second step. The list is the **remote** branches: Azure DevOps links a ref of the server, so a branch that was never pushed would give a dangling link. A modal confirmation precedes the write, like the other link quick fixes. Offered for open tasks of open work items, also when the task has branches already (several are allowed).
- **The parent card is "Working on" through the branch of one of its tasks** (`WorkingOnEntry.taskBranches`, only with `workingOn.includeLinkedWorkItems`, like the Development / PR rules): the developer is working on the Backlog Item or Bug whoever's task the branch is linked to, and the card with its "Working on" section is where the tasks are. The task row is highlighted too (`taskWorkingOn`: "here" light tint + bold title (no left accent: it looked heavy in a row), "worktree" dashed outline; no animation: the parent card already animates, and rows must keep their height). Styles are scoped as `.child.working-here` so the card rules (`.card.working-here`, `.working-here .working-dot`) never reach the rows.
- **Alert "Branch … of task … is not linked to this work item"** (`taskBranchNotLinked`, `src/alerts.ts`): when the branch of a task is not in the Development links of its work item. The team links branches to the work item; a branch linked only to a task means it was forgotten (Create branch for a task links both, so it only fires for branches linked by hand). It covers **every branch of every open task**, not only the checked-out one: the rule is about the data (the work item must show all its branches), not about what the developer happens to be doing; and checking only the current branch would hide the problem until someone checks it out. It is not reported for finished work items (Done / Ready to Test / Removed) nor for Done / Removed tasks (history), and only for branches of this repository. It needs no extra request: the links are already fetched. The quick fix (`totalflowx.linkTaskBranch`) confirms and uses `branches.linkToWorkItem`.
- **Alert "PR … of task … is not linked to this work item"** (`taskPullRequestNotLinked`, `src/alerts.ts`): the PR counterpart of the previous alert: a PR linked to an open task but not to its Backlog Item / Bug means the link was forgotten (Create PR links both, so it only fires for PRs created or linked by hand). Same scope (open tasks of unfinished items, once per PR). Differences: it compares against the **raw PR links** of the work item, not the fetched PRs, so a PR whose fetch failed is never reported as unlinked; **abandoned PRs are skipped** (history, like ALERT-3..5), while a PR of unknown status still alerts; and it covers **all repositories** (PR ids are collection-wide and the link carries project and repository, so the quick fix works anywhere), unlike branches, whose names are not unique across repositories. No extra request: the PR links of tasks and their statuses are already fetched. The quick fix (`totalflowx.linkTaskPullRequest`) confirms and uses `linkPullRequestToWorkItem`.
- **Alert "Is … but "Integrated in Build" is still …"** (`staleIntegrationBuild`, Rule ALERT-11): a Bug with the field set that is neither Ready to Test nor Done/Removed was reopened, so the value names a build without the fix and would mislead testers next time. Choices: (1) it reuses the `integrationBuild.*` settings (field, types, states) instead of new ones, so "when the field must be set" lives in one place; (2) the quick fix **Clears** the field (after a modal showing the old value) rather than asking for a new value: the right build is only known when the Bug is Ready to Test again, where the empty-field alert and the state picker already propose it; (3) Done and Removed are excluded (a closed Bug keeps the build it shipped in).

### CI, coverage and requests

- **CI runs are followed for the PRs of the user's work items and all the user's PRs**; fast polling (15 s) only while a run is active, otherwise an idle check (60 s) to discover re-runs/new pushes. A failed fetch keeps the last known runs.
- **Coverage is the coverage of the code tested by the PR's run** (the PR pipeline runs the affected tests). Shown to motivate: levels (60/80/95), positive deltas celebrated, decreases neutral (no blame), files below target to open, personal best and streak (only the user's own PRs, one entry per PR). No team ranking (it would push people to game the number).
- **Request budget**: tags come with the PR list (0 requests); "PR changed the build notes file" = 1 diff request per PR per push (cached by last pushed commit); branch existence, repository names, work item types are cached. The usage report and request log exist to keep this honest.

### Whole team: shared by the Track board and the Sprint timeline

- **The Whole team views and the Sprint timeline fetch their extra data (teammates' work and PRs, work item history) only while their tab is open and visible**, cached by immutable keys, so they cost nothing when closed.
- **Read-only for others**: acting on somebody else's PR or work item from here would bypass their team's own flow; a click opens the details panel (works for any id) or the PR in the browser (URLs are validated to start with `https://dev.azure.com/` because they come from a webview).
- **No alert rules for others**: the alert rules need extra requests per item (rules, fields, dependencies) and are the owner's business; so no broken-rule marks and all finished items of others fold when Completed is off. This is intended, not a bug.
- **The people are picked one by one, per person and not per team** (replaces the first version, a Teams dropdown): on real data two teams alone gave 21 people plus the unassigned, and the user's teams together have 31 distinct members, mixed (UI, backend, tests...). Nothing in Azure DevOps says who works on which kind of feature, so only the user knows who to follow. The board follows the people they pick; teams only decide which sprints are read (the teams of the sidebar, else all of the user's). **Stored in the settings** (`totalflowx.teamView.people`, user level, `{id, name, uniqueName}`) and not in `globalState`: the choice is long-lived and personal, a setting is readable, hand-editable and survives a reinstall, and the name is kept so the picker can show people who have nothing in this sprint. Unlike the first version's team ticks it changes rarely (once per person). The scope (Mine / Whole team) stays in `globalState`: it is a UI toggle shared by the two tabs. Without people the view shows only the user's lane and a hint, and asks nothing (no query), so a user who never picks anyone pays nothing. There is no Unassigned lane: the query only brings the people chosen. The user is never listed: their lane is always there and comes from the store.
- **The WIQL asks for the people by sign-in name** (`uniqueName`, else the display name): an identity id in `IN` silently matches nothing (AZURE_DEVOPS.md). The identity id stays the key of lanes and of the setting because `System.AssignedTo.id` is stable and what `groupByPerson` already uses.
- **Budget**: nothing runs unless a visible board tab is in Whole team; a reload happens only when the store reloaded, the people changed or the user pressed Refresh (an attempt key; a failed attempt is not repeated alone, so there is no loop even if the redraw asks again). One listing of all the active PRs of the project replaces a request per PR (63 active PRs on our organization fit in one page of 200). Closed PRs never change: kept once seen. The PRs merged in the sprint come from one listing of the project's completed PRs since the sprint start (1 request per 200) instead of one `GET` per PR (the first version fired 76 at once, with no cap); only the rest (abandoned, older, other project) are read singly, at most 6 in flight, like every other fan-out (builds, threads, members of the teams). CI is only the state of the last run of each pipeline (no tests or coverage: those are one to three more requests per run and the card only needs red / running / green); runs are cached by `PR : last source commit` once none is queued or running. The wait of a review counts from the PR's creation, corrected with the thread that says when it left draft only for PRs that look overdue (a draft opened days ago and published today would otherwise look late), at most 20 per refresh and once per PR.
- **The team of a card** is the team whose current sprint contains its iteration path (the first selected one when teams share a sprint). People are told apart by the identity id of the assignee, not by name.
- **Same People picker as the board, not teams**: the user asked for it; the markup, CSS, messages and setting are shared (`src/webview/peoplePicker.ts`), so there is one place to change it. Rules TIMELINE-21, TEAM-1.
- **Rows of others are read-only**: actions (publish, complete, create PR) belong to their owner and need data the whole-team query does not have (branches, alerts); a click on the row expands it (collapsed by default), the `#id` opens the details panel and a PR opens in the browser. Rule TIMELINE-23.
- **The rows of the others are the user's rows, with four differences** (TIMELINE-23): they used to be a one-line compact label of their own, so the two views drifted apart (the PR rows of the others lost their linked task). One row builder and one markup serve both; only what cannot be the same differs: no buttons, no team-rule alerts and no test details (the team data do not have them, TEAM-5), and the text after the bar says what links the row to the user. The density is a separate choice (TIMELINE-32). They are indented under their person with a rail in the person's colour, so a long list of rows still reads as one person's.

### Completed work items and merged PRs are shown, unless the user hides them

- **Shown by default**: the board used to collapse the finished work items into one "N Done this sprint" card and give a merged PR of a split work item no card, and the timeline drew none of them. The user wants to see what was completed in the sprint: a sprint is also what was achieved, and for a developer it is the answer to "what did I do?". So the Done column has a full calm card for each finished work item (most recently finished first) and a faded card for each PR merged in the sprint of a work item that still has work (BOARD-5, BOARD-24); the timeline has the "DONE THIS SPRINT" list and the merged PR rows of TIMELINE-17, now also for finished work items (TIMELINE-19). A finished work item is not given merged-PR cards of its own: its one card stands for them (they are in its drawer).
- **One setting, one chip, on the Track board only (BOARD-25)**: `totalflowx.appearance.showCompleted` (user level, on) is the only state, written by the **Completed** chip of the board (global target) and read on every redraw (`onDidChangeConfiguration` already redraws it), so the choice survives a restart. The Sprint timeline used to share it; it now always shows the finished work (see "The timeline always shows the finished work"). It is in the Appearance category because it is a matter of how much the user wants to see, like `appearance.look`; it is not a team rule.
- **A finished work item that breaks a team rule stays visible when the rest is hidden**: hiding is for the work that is done and in order. A finished work item with a broken rule (for example a Bug in Ready to Test without a test task) is something the user must still fix; hiding it would make the rule silently invisible, which is against the point of the alerts (docs/DECISIONS.md#team-rules). So only the finished work items with no alert are hidden; the others keep their red card (board) or row (timeline). On the board, hidden means folded: the finished work items without an alert become the one dashed "N Done this sprint" card the board always had (the user still wants to see at a glance what was finished, without the full cards); merged-PR cards are not drawn.
- **The merged PR cards and rows are limited to the sprint**: the board takes the PRs merged since the first day of the sprint of its header, or in the last 14 days when the sprint dates are not known; the timeline takes the ones merged within its axis. Both read the latest 50 completed PRs My Pull Requests already has, so a PR older than those is not shown and no request is made for it (the threads of the merged PRs drawn by the timeline are still read once per PR, TIMELINE-14). Abandoned PRs are never shown: they are not completed work.
- **Hidden, the merged PRs are only counted**: with the chip off the work item has no merged PR rows when it is expanded, and the count in its state ("Committed · 3 PRs") still includes them; a finished work item with nothing to hide stays out of the list (TIMELINE-19).

### Look, colours and menus

- **The look is the user's choice**: a personal setting switches between the theme-aware look (VS Code theme variables, default) and the design's own palette and fonts (bundled, never loaded from the network: the webview CSP forbids it).
- **The design look is a setting, `appearance.look` (`theme` by default, `totalflow`)**: the user wanted both. It overrides the theme variables on the body, so every component follows without a second stylesheet; its fonts are bundled (`media/fonts`, OFL, latin and latin-ext for the Polish names) since the webview CSP forbids the network; high contrast themes always win, the user chose them to read the screen. The tab counts that need the user are amber in both looks (amber is reserved for "needs you").
- **"Waiting for author" has its own orange (`--waiting`)**: some themes define `charts.orange` as a dark red-brown (rgb(120,32,32) on a rgb(31,38,34) tile: contrast 1.49), and the theme's warning colour is the gold already used for tasks, so the two looked alike. `--waiting` is a fixed orange, #f0883e on dark themes and #bc4c00 on light ones (`body.vscode-light`), used for the tile border, the status pill, the reviewer chip, the PR rows of the work item cards, the task pill and the "Waiting for author" phase of the PR history; the solid badge is #f0883e with dark text. Warnings and "N unresolved" keep the theme's warning colour (`--warning-fg`, pulled 30% toward the text colour), and `--orange` is pulled 35% toward the text colour for the other uses. "N unresolved" took the tile's `--pill-color` because a later `.signal` rule won over `.signal-comments`; it is now `.signal.signal-comments`.
- **Purple means a completed PR; worktrees are blue**: the "Completed" PR badge and everything about worktrees (the **⧉ In worktree** card, the worktree badge, Open worktree in the menus) were all purple, so a worktree could be read as "completed". Purple stays with completed PRs, as in Azure DevOps and GitHub. "In a worktree" means the same as "checked out here", that I'm working on it, so it takes the same blue (`--working-worktree: var(--working-here)`) and is told apart by shape: a thin dashed border, an outline badge and no tint, against the solid badge, thick border and tint of "here". Teal was rejected because the VS Code chart palette has none, so it would be hard-coded and hard to keep readable in both themes.
- **All the action menus are the native QuickPick, not an in-webview popover** (task pill, the … of branch rows, the … of the Checkout / Open worktree buttons of cards, "Waiting for your review" and "My Pull Requests"). An in-card popover menu was built first (notch, header, opening animation, keyboard and focus handling, key-based open state) and **rejected: a webview cannot draw outside the sidebar**, so the menus were cramped at 260–340 px (long branch names, descriptions) and needed a lot of machinery to behave like a menu. The QuickPick has the room (it is drawn at the top of the window, over the editor), keyboard handling, filtering and the user's theme for free, and the extension already used it for the details panel. How it works: every trigger posts ONE message, `showActions` (`{ title, sections }`), built by the pure section builders (`taskMenuSections`, `branchMenuSections`, `checkoutMenuSections` over `checkoutMenuItems`, the single source of truth; `src/actionRequests.ts` adds the title); the extension (`src/actionPicker.ts` pure, `src/actionPickerUi.ts` wrapper) shows a separator per section and an item per action, and the chosen item goes through `onMessage` as if the webview had posted the message of that button, so there is one code path per action. The sections come from the webview, so the extension only runs the allowlist of actions that the builders produce (`actionToMessage`: `checkoutHere`, `openWorktree`, `removeWorktree`, `deleteBranch`, `openPullRequest`, `createBranch`, `createPullRequest`) with the right field types and rebuilds the message from known fields (nothing else of the data is passed on); the delete flow keeps its own modal confirmation. **Items that only inform** (a checked out or deleted branch, "Checked out") are **left out**: a QuickPick cannot show an inert item (choosing it would do nothing and close the picker, which reads as a bug); that information is on the hover card and the badge of the row, and a trigger with nothing to choose does nothing (no empty picker). The **… of the details panel** (`totalflowx.checkoutMenu` / `totalflowx.worktreeMenu`) use the same picker and `checkoutMenuSections`, built by the extension from the current state of the branch (a worktree that appeared meanwhile gives Open / Remove worktree whichever of the two commands was asked); the chosen item runs the `totalflowx.checkoutHere` / `openWorktree` / `removeWorktree` commands, which are what the previous two pickers ended in (`checkoutBranch(..., 'here')`, `openOrCreateWorktree`, `removeWorktreeOf`). Icons: each item has a codicon and a theme colour from its action (`actionMenuIcon`, `src/actionMenu.ts`), the same in every picker, so users recognise it before reading: `git-branch` blue Checkout, `folder-opened` blue Open worktree, `close` orange Remove worktree, `trash` red Delete branch, `git-pull-request` green Open PR, `git-pull-request-create` green Create PR, `git-branch-create` yellow Create branch. They are set as `QuickPickItem.iconPath` (`ThemeIcon` + `ThemeColor` with `charts.*`, in the VS Code 1.95 typings the extension builds against); the shape carries the meaning on its own because whether the colour is drawn depends on the VS Code version and theme.
- **All the popovers share one behaviour (delay, fade, focus, Esc, placement)**: the coverage details, the open predecessors, the PR history and the task pill card used to behave differently (the task card waited and faded, the others appeared instantly with `display`), which the user found inconsistent; native tooltips wait too, so everything waits. (1) One mechanism, only in the shared CSS (`.popover-anchor` on the wrapper, `.popover` on the direct child popover; the specific classes keep their own look and position): hidden with `opacity`/`visibility` (not `display`), so that showing can wait: on hover it fades in after `totalflowx.popovers.hoverDelay` ms (default 500, 0 to 3000; `normalizePopoverDelay` in `src/popoverDelay.ts`; the webview sets `--popover-delay` on `#app` through CSSOM), and hiding is a 0.12 s fade-out (not instant, on purpose: the `visibility` flip is delayed by the same 0.12 s because pressing Tab from the badge into the popover blurs the badge first; if the popover were hidden at that instant its file buttons could not take the focus. Esc and the click on a task pill hide at once). Moving the pointer across rows does not flash cards, because showing waits. Keyboard focus **on the trigger or inside the popover** (`.popover-anchor:has(:focus-visible)`) shows it at once, because a keyboard user cannot "hover longer" and must be able to Tab into the file buttons of the coverage popover; a mouse click focuses a button but is not `:focus-visible`, so a click does not keep the popover open after the pointer leaves (this is why `:focus-within` was dropped; it also keeps the nested badge inside the task card from opening the card's siblings: the rules use `>`, the direct child). **Esc** hides all of them (`.no-popovers` on the body, until the pointer moves). (2) After a **pointer click** on a task pill its card **stays hidden until the pointer leaves the pill and its card** (`suppressedTaskCard`, rendered as the class `card-suppressed`, because `render()` rebuilds the HTML on every update; cleared by a delegated `pointerover`, no render); keyboard clicks (`event.detail` 0) do not suppress it. Clicks on the text of any popover do not fold the row behind it. (3) **Placement**: the coverage popover (300 px, left edges aligned) and the task card (360 px, right edges aligned, `min(preferred, view - 16px)`) are placed by one routine: the pure `placePopover` (`src/popoverPlacement.ts`) clamps them to keep an 8 px margin on both sides and `placeAllPopovers` in `main.ts` writes `--popover-left` / `--popover-width` through CSSOM relative to the containing block. It uses `document.documentElement.clientWidth`, **not `window.innerWidth` or `100vw`**, which include the vertical scrollbar: with them a popover near the right edge made the whole sidebar scroll horizontally. Because hidden popovers (`visibility`) still count for the scroll width, **all** of them are placed after every render and on resize (not only on hover/focus, which left them stale after a re-render); the outer ones first, since a coverage badge can sit inside the task card. The predecessors and the PR history span their card (`left: 0; right: 0`) and need no placement. The padding on top of each popover is the pointer bridge. The task card has a lighter shadow, no notch, and a muted **"Click for actions"** footer when the picker has actionable items (`taskHasActions`).

### Settings

- **Settings are grouped by feature in the Settings editor, with keys named after their category and `application` scope for personal choices.** With ~80 settings on one flat page, related ones ended up far apart. `contributes.configuration` is an array of categories (Connection, Work Items List, Working On, Branches & Pull Request Creation, My Pull Requests, Reviews, CI & Coverage, Team Rules, Appearance, Advanced), each property with an `order`. Grouped **by feature** (where someone looks for "something about reviews"), except two cross-cutting groups: **Team Rules** (alerts, build notes, Integrated in Build: agreed by the team, meant for a committed `.vscode/settings.json`) and **Advanced** (poll intervals, `pipelines.branchRunsHours`, request log: rarely touched, and they drive the request budget). **Keys were renamed to match the categories** (`layout` → `workItems.layout`, `stateOrder` / `showInReviewState` → `workItems.*`, `hoverStyle` → `appearance.hoverStyle`, `baseBranch` / `branchTypeByWorkItemType` / `branchModules` / `linkBranchToWorkItem` / `stateOnBranchCreated` → `branches.baseBranch` / `.typeByWorkItemType` / `.modules` / `.linkToWorkItem` / `.workItemStateOnCreate`, `prFeatureNames` / `moduleToFeature` → `pullRequests.featureNames` / `.featureByModule`, `notifications.events` / `.pollIntervalSeconds` → `myPullRequests.notifications` / `.notificationsPollIntervalSeconds`, `statusBar.currentWorkItem` → `workingOn.showInStatusBar`) and the deprecated `tasks.hoverCardDelay` was removed, **without a migration of the old values**: the extension has a single user, whose settings did not use the old keys, so a migration would have been code to keep for nothing. If it ever gets more users, renames need a migration on activation. **Scope**: the personal choices the sidebar writes to the user settings (layouts, filters, the box toggles) and the look (hover, popover delay, task counts, animations, attention effect, fun) are `application`, so they follow the user everywhere (also into WSL / remote windows, where they are read from the local user settings) and a workspace cannot override them. Everything else keeps the default `window` scope, which already allows workspace settings; `resource` was not used, because it only adds per-folder values in multi-root workspaces and `getConfiguration(SECTION)` is read without a URI. `branchModules` / `prFeatureNames` must stay non-`application`: **Add new…** writes them to the workspace settings. **Totalflow X: Open Settings** opens the editor filtered on the extension (`@ext:<id>`, id from `context.extension.id`).
- **Removed with the redesign** (no migration, a single user then): `totalflowx.workItems.layout` (and the Use Compact / Large Layout commands) and `totalflowx.workingOn.section` (the Now tab lists the work items being worked on).
- **Personal settings that still mean something are kept; purely cosmetic ones the new design replaces are removed**, each one listed here and in the README when it goes.

### Fun features (`totalflowx.fun.enabled`)

- **Opt-in, private, never comparative.** Off by default: some people dislike confetti at work, and the sidebar is always visible. Nothing is a leaderboard or compares people: comparisons turn fun into pressure and invite gaming the numbers. The "karma" of the recap only compares the user's own reviews with their own PRs.
- **No new request.** Everything comes from responses the pollers already fetch: finished runs (`PipelineWatcher.onFinished`), the user's PRs and their threads (`PullRequestNotifier`, which now also keeps `creationDate`, `closedDate` and the publication date from the threads it already reads), the review poll (`getPullRequestsToReview`, the same response that feeds `activeReviewed`), and the sprint dates that `$timeframe=current` already returned (`attributes`).
- **A journal, recorded whatever the setting** (`src/funJournal.ts`, `FunJournalStore`, global state key `totalflowx.funJournal:<org>/<project>`). Recording always means the recap is complete when the user turns the features on, or opens it by hand. Lists are capped (500 entries). Several windows share the global state, so every recorder is idempotent by id and the store reads just before writing; a window that finds the entry already there says nothing about it, so a streak or a first approval is celebrated once.
- **Green streak = the user's own runs**: PR runs of the user's PRs (`isMine`; the store also follows other people's PRs linked to the user's work items), manual runs and post-merge runs (both already only the user's, STATUSBAR-CI-6/8). Canceled runs are left out (a cancel says nothing about the code); partially succeeded counts as red; a re-run of the failed jobs keeps the build id, so its new outcome replaces the old one. Ordered by finish time. Runs that finished while VS Code was closed are not caught up (the order would be guesswork). The status bar cannot animate, so a broken streak is told in the run notification.
- **The reviews counted by the recap break the "Reviewed is display-only" rule on purpose, in one place only.** `votedPullRequestIds` (REVIEWED-2) feeds the journal, which only the recap reads: the badge, urgency, Summary, status bar, digest and notifications still never see reviewed PRs. It works whatever `reviewedPeriod` is (the active PRs come with every review poll).
- **Merged PR**: one notification only. When the completion offer (tasks to Done, branch to delete, MYPR-OFFER) shows, it stays as it is and only the confetti celebrates; otherwise the celebration text replaces the plain "merged" text. Confetti is posted only to a sidebar that is open and visible (a webview view may not exist yet), and both the JS and the CSS skip it with reduced motion.
- **"This sprint"** is the sprint whose dates contain the merge (UTC days, as Azure DevOps stores them); without dates the count is left out rather than guessed. The countdown compares the local date with the date part of the finish date and counts working days (`reviews.workingDays`), today and the last day included, since "days left" matters in working days.
- **Clean board row** is only shown with the alerts on (without them a clean board means nothing) and some work items listed; it comes after "Nothing needs your attention", never counts in the badge and is not clickable.
- **Recap panel**: static HTML, scripts disabled, its own small stylesheet (`media/recap.css`), so no fourth bundle. Offered once per iteration path (marked in the journal before the notification shows, so two windows do not both offer it).
- **Sounds are a second opt-in** (`fun.sounds`, on top of `fun.enabled`): someone may like the confetti but not noise in an open-plan office. They are synthesized in the sidebar webview with the Web Audio API (oscillators with a fade), so there is no audio file to ship and the strict CSP needs no `media-src`. The extension host (Node) has no audio API, and spawning a system player (`afplay`, PowerShell, `paplay`) is per-platform and plays nothing under WSL, where the extension host runs; webviews render on the client side (Windows), so their sound reaches the user's speakers. VS Code's own accessibility signals cannot be played by extensions. The cost: like the confetti, the sound only plays while the sidebar is open and visible; keeping the webview alive when hidden (`retainContextWhenHidden`) would cost memory for the whole session, not worth a chime. Only three moments make a sound (merge, streak record, broken streak): comments and votes are frequent and would get noisy. The siren of a broken develop is not one of them: it has its own setting (see the base branch alarm). Whether VS Code's webviews let audio start without a click in the page must be confirmed in a real VS Code; if not, the sound stays silent (the code catches it).
- **More card animations** (`rainbow`, `neon`, `retro`) live under `workingOn.animation`, not under `fun.enabled`: they are a look the user picks, not a celebration. Same constraints as the others (pseudo-elements, opacity / background-position only, nothing with reduced motion). A blinking cursor after the badge was tried for `retro`, but it widened the badge and wrapped the card header: the scanlines take no space.

### Naming and identity

- Namespace `totalflowx.*` for settings, commands, views; display name "Totalflow X devtools for Azure Devops". The **extension ID stays `abb-totalflowx.vscode-azdo-workitems`** so installed state (globalState) survives renames; the coverage records keep their old storage key `azdoWorkItems.coverageRecords:` for the same reason.
- The per-work-item tab is the **Work Item Details panel**; its button on cards is "Details".

## 2. Sidebar

### Tabs, sprint strip and the "Needs you" rows

- **The sidebar has three tabs: Now, Work, PRs.** Now answers "what needs me" without scrolling past the boxes, Work is the list as before, PRs the two boxes as before. Only the shown tab is rendered, so a card is never twice on the page (the reveal and popovers find cards by id). The alarm of a broken base branch stays above the tabs. There is no Reviews tab: the PRs tab already holds the reviews, its count starts with them.
- **The "Needs you" rows unfold in place with the card the other tabs show**, not a new panel: the buttons and pickers of that card keep working there, and the row stays one line when folded.
- **The sprint strip is always shown**, not only with the fun features: the days left of the sprint matter to everyone; the emoji countdown stays a fun feature.
- **Station names in the track are not written under each segment**: six names do not fit a narrow sidebar; the segment tooltips name them and one caption names the station to look at.

### Work tab: cards, branches and tasks

- **Filters apply to Backlog Items and Bugs only**; nested tasks are never filtered. Work items with alerts follow the filters unless `filter.alwaysShowAlerts` (default off: the banner says how many are hidden and "Show only these" reveals them).
- Work items are always compact rows in the Work tab (the `workItems.layout` setting and its Compact / Large commands were removed with the redesign: the full cards live in the Now tab and unfold in place); the PR boxes keep their compact / large choice. A compact row unfolds into the full card in place.
- **The `Tasks` header of a card shows how many tasks are in each state, coloured, instead of `done/total`.** `done/total` only tells what is finished; the breakdown also tells what is being worked on. A segmented bar shows the proportions and each count sits on its own segment, so there is nothing to match by eye (an earlier version put the counts before the bar). Segments follow the workflow order, **To do, In progress, Done**, the same as the compact `to do/in progress/done` (a progress-bar order with Done first was tried and rejected by the user). **The numbers left the bar**: with the counts inside the segments the bar had to be 11 px thick, which the user found heavy, and the text on the segment colours was hard to read. The bar is a slim 4 px line (rounded ends, 1 px gaps) and each count is a small circle (14 px; a pill for 2+ digits) centred on its segment and on the line, like a marker on a track, touching the line (a ring in the card colour that separated them was removed at the user's request: the circle should sit on the line). Nothing is clipped (the circles are taller than the line); the circle is in the flow of its segment, so the segment's minimum width is the circle's width and circles never overlap, even for 1 to do and 14 done. Colours are the state categories of the work item cards (grey, blue, green); the tooltip and `aria-label` of the header spell the counts out (the bar is `aria-hidden`) so colour is not the only cue. **Two looks behind `totalflowx.tasks.countStyle`** (`filled` | `outlined`, class `task-counts-<style>` on `#app`, `normalizeTaskCountStyle` in `src/taskCountStyle.ts`; unknown values mean `filled`) because the user wanted to choose. `filled` is the default because its contrast is guaranteed: the circle is filled with the state colour and the number has a fixed text colour per theme kind, like the solid pills (priority, due soon), not a theme colour (the state colours vary a lot between themes and a text colour that follows the theme can vanish on them). Dark themes use `#1f1f1f` (contrast 4.8 to 9.0 on the default colours); light and high-contrast themes use `#000000` (4.9 to 9.4: white would give only 4.3 on green and 3.6 on blue, below the 4.5 needed for small text). `outlined` fills the circle with the card background and draws the ring and the number in the state colour, the same colours as the compact row's counts; in light themes those colours are too pale as text on the card (grey 2.1:1), so there the ring and the number are darkened 40% toward black (5.3 to 8.5 on the default colours). The theme's grey is translucent in light themes, so the segments and filled circles are painted over the card background to be opaque. Removed tasks are left out, as before (they never block a work item). The compact row (SIGNAL-7) keeps the short `to do/in progress/done` text (e.g. `2/1/3`) to take little room, with each number in the colour of its state and the slashes muted; its title says what each position means.
- **The ID in the header of a card (and of a compact row) opens the Work Item Details panel, not Azure DevOps**, and cards have no Details button: every other work item ID in the sidebar already opened the panel, and the button took room in the action footer. Azure DevOps is one click further, through the panel's **Open in Azure DevOps** button.
- **Hovering a card or PR tile does not change its background by default (`totalflowx.appearance.hoverStyle` = `border` | `tint` | `accent`)**: the old hover painted the tile with the list hover colour (`--vscode-list-hoverBackground`), which in many themes is close to the muted greys, the blue IDs and the state colours, so the text became harder to read exactly when the user was looking at it. `border` (default) leaves the background alone: the whole border takes the colour of the tile's thick left bar (the state of the work item: grey proposed, blue in progress…; the state of the PR: purple completed…; red alerts, blue "Working on", green ready to merge), so the hover says the same thing as the bar instead of adding a blue that means nothing there, and a soft shadow lifts the tile; contrast is unchanged. `tint` is a 5% foreground mix over the tile's own background (so "Working on" keeps its blue underneath), `accent` brightens the left bar and widens it by 2 px with an inset shadow (the content does not move). The style is a class on `#app` (`hover-<style>`, `normalizeHoverStyle` in `src/hoverStyle.ts`; unknown values mean `border`), the same rules apply on `:focus-within`. `--card-hover` stays for buttons, menus and rows, where there is no text-contrast problem to solve.
- **Task rows show every linked branch, deleted ones dimmed instead of hidden**: a Development link outlives its branch, and hiding it would make a task look branchless (and offer **Create branch** wrongly, which already keys on links). Existence of the branches linked to tasks is asked to Azure DevOps (`refs?filter=`, one request per distinct branch) and cached in memory for 10 minutes; a local branch with the same name counts as existing, and a failed request leaves the branch "not verified" (not deleted). In the picker of the task pill, a branch that exists offers **Checkout** (`checkoutHere`, kind `task`, straight to checkout) and **Open in a worktree** (`openWorktree`); deleted and other-repository branches are only on the hover card (a picker cannot show an inert item). A branch whose PR is completed and that still exists also offers **Delete branch** (red trash icon).
- **One pill per task row, with a native picker, instead of an icon per branch / PR plus two dashed create buttons**: the row of a card is narrow (260 px) and up to five small controls with different click meanings were confusing. The pill only summarises (icons coloured by state, counts; a dim "+" when empty); hover shows the details card (see the hover card entry below), click opens VS Code's QuickPick (see the picker entry below) that lists every action (checkout, worktree, delete, open PR, create branch / PR), titled `Task <id> · <title>`. The picker is not a popup of the pill, so the pill has no `aria-haspopup` / `aria-expanded`. Pure rules: `src/taskMenu.ts` (the sections), `src/actionRequests.ts` (title + sections of each trigger).
- **The switch between compact and large is a View Transition**: the two forms are different markup rendered again with `innerHTML`, so CSS transitions cannot morph them. `renderMorphing` (src/webview/main.ts) wraps the render in `document.startViewTransition` and gives each card / PR row a `view-transition-name` (`wi-<id>`, `review-<id>`, `mypr-<id>`; CSSOM, as the CSP blocks inline styles) only during the switch, and names the blocks around them (PR boxes, toolbar, filters, list) so they slide instead of cross-fading (their text showed twice). A duplicated name would abort the transition, so a second element with the same name is left out. Short (≈0.2 s) and clipped to the card's radius. Without the API (older VS Code) or with reduced motion the view is just rendered. Opening / closing the tasks of a card is the same morph (the card grows or shrinks with its tasks inside). Expanding / collapsing a PR box uses the same transition with only the blocks named: the box grows or shrinks with its rows inside it (named on their own, the rows would spill out of the shrinking box). The view the extension posts back after saving the layout is rendered without a transition: it is the same.
- **Only the card "here" can animate (the running border of `runningBorder` covers the card's border exactly, so it is as thick as the 5px left border on that side); card animations are off by default, the badge pulse is on** (`totalflowx.workingOn.animation`: `none` | `borderLight` | `runningBorder` | `glow` | `stripes` | `rainbow` | `neon` | `retro`; `totalflowx.workingOn.pulseBadge`): the sidebar is always visible, so continuous motion on many cards would distract; "In worktree" is a bookmark, not the current focus, so it never moves. The pulse (a halo expanding from the whole badge, every 2 s, like a live / recording light; a ring from the ● alone looked poor on the small glyph) is cheap and tells at a glance which one is live, hence on by default and independent from the card animation. All are pure CSS keyframes switched by classes on the list (`anim-*`, `pulse-badge`; strict CSP, no inline styles), built on pseudo-elements that take no space and ignore the pointer, so content, hover, the red `.has-alerts` border and the menus are untouched. They animate opacity / transform / background-position, except the running border: a short light moves along the border (`offset-path`) inside a masked ring that covers the card's border. A rotating conic gradient was tried first, but its speed followed the angle, not the border, so it raced along flat (compact) cards; the light moves at a constant 220 px/s instead, its duration set from each card's perimeter on every render (CSSOM, `placeRunningLights`), with a negative delay so a re-render does not restart it. The halo is blue (`--working-here`), never the red of alerts. Everything sits inside `@media (prefers-reduced-motion: no-preference)`, so with reduced motion the look is the static one. Classes come from `workingOnAnimationClasses` (`src/workingOn.ts`, tested); unknown values mean `none`.
- **Branch rows: one badge and icon buttons, details in tooltips**: a row had a location pill, a worktree pill, a text "Checkout ▾" / "Open worktree ▾" (now "Checkout …" / "Open worktree …") and "Delete", so in a 260 px sidebar the name (long: `feature/<area>/<id>-<title>`) was truncated to a few characters, and the name is what identifies the row. Now there is **one badge** (`src/branchBadge.ts`, pure and tested: location, `not deleted` when the PR is merged, plus `⧉` when a worktree has the branch, with the worktree tone) and **icon buttons** (checkout / worktree icons with a … more-actions button, trash for Delete) whose `title` / `aria-label` carry the words ("Checkout <branch>", "Open the worktree of <branch>", "Delete the branch <name>"). What the short badge cannot say (what `local` means, the worktree folder, why it is `not deleted`) is in the badge tooltip. Only branch rows are compact (`checkoutButton({ iconOnly })`): the card-level and PR-box Checkout buttons keep their text because they are the primary action there. The `⧉` is a character, not an SVG, so the badge keeps one text colour and no extra width.
- **The Checkout / Open worktree button has a … (ellipsis), not a ▾**: a chevron says "opens below me", and the picker opens at the top of the window. The button is a plain button, not a popup of itself, so it has no `aria-haspopup` / `aria-expanded` and no rotating chevron (titles stay "More checkout options" / "More worktree options"). (A single … button replacing the whole split button was rejected earlier: users prefer the visible Checkout / Open worktree icon next to it.) The icon is drawn with filled dots (`icons.ts` `ellipsis`, `.button.caret .icon circle`).

- **The Now tab has no "This sprint" list** (a design had one, with a "Not finished | All" switch; it was never built and was removed from the design): the Work tab already lists the work of the sprint, and Now is only about what needs the user.
- **The filter panel gets "Show all" and "Reset to default"** (designed, not built yet): the defaults are not "no filter" (they hide Done, Removed and Closed, and show only Backlog Items and Bugs), so clearing everything and going back to the defaults are two different clicks.

### PRs tab: the Reviews box and My Pull Requests

- **Completed PRs of "My Pull Requests" are listed for a chosen period** (`totalflowx.myPullRequests.completedPeriod`: hidden / 24 h / 7 days / 30 days; default 24 h). The latest 50 completed PRs are fetched in one request. Completed PRs barely change, so their threads (for the timeline popover) are fetched **once per PR, only while it is inside the period**, and cached in the watcher (entries of PRs no longer returned are dropped); this keeps the request budget low even with 30 days. Completed PRs outside the period cost no requests. Only active PRs get policies, runs and build notes.
- **Build notes are a folder of files, one per feature** (`build-notes/*-notes.md`, since User_Interface PR 13922): a single `developer-notes.md` edited by every PR caused merge conflicts, so the team split it and the build notes tool merges the files. Changing **any** of them satisfies the rule (the extension does not try to tell which feature a PR belongs to). Only files directly in the folder whose name ends with `totalflowx.buildNotes.fileSuffix` count, as the tool globs them: `_template.md` (copied to start a feature) and subfolders do not. `developer-notes.md` still matches the suffix, so branches from before the split still count. The old `totalflowx.buildNotes.path` setting was replaced by `directory` + `fileSuffix` (a new key, so a saved file path is ignored rather than read as a folder). Create PR's "I'll write the notes" lets the user pick the file (with the feature name of its first `# ` heading) instead of opening a fixed one.
- **"Reviewed" PRs are display-only and kept apart.** `totalflowx.reviews.reviewedPeriod` (hidden by default) lists the PRs of others the user already voted on (`toReviewedRequests`, src/reviewedRequests.ts) below the waiting ones. The watcher stores them in separate fields (`activeReviewed`, `closedReviewed`), never in `requests`: the badge, urgency, Summary, status bar, digest and `detectReviewEvents`/notifications only read `requests`, so a reviewed PR can never count or notify (a test asserts it). The exceptions are the private sprint recap (the user's votes go to the fun journal, which nothing else reads; see [Fun features](#fun-features-totalflowxfunenabled)) and the cleanup of worktrees (`pullRequestsForWorktrees`: whether the PR of a review worktree is still active, or approved; it never counts or notifies a review; see "Leftover worktrees" below). Active ones come from the existing `getPullRequestsToReview` response (no request). Completed/abandoned ones need `searchCriteria.status=all&reviewerId=…&$top=100` (the active query cannot return them), made only while the period is day/week/month, inside `withFeature('reviews')`, at most every 10 minutes (history changes little), or on "Check now" / when the period is first selected.
- **Voting does not take the branch of a review away.** Voting moves a PR from the waiting list to "Reviewed", but reviewers often check the branch out again after the author pushes, or keep a worktree for the review. So the Checkout / Open worktree buttons (and their ...) look the PR up among all the active PRs where the user is a reviewer (`reviewBranchTarget`, REVIEWED-8, the same response as `activeReviewed`, no request), and the unfolded card of an active reviewed PR shows the branch row. Closed reviewed PRs get none: their branch is usually deleted. With `reviewedPeriod` = hidden a voted PR leaves the box; its worktree stays reachable from the Worktrees view.
- **"Reviewed" PR details are fetched lazily, only for unfolded rows.** Reviewed rows are foldable tiles; the webview posts `setReviewedExpanded` (the unfolded ids, again when it loads with its saved state) and `ReviewRequestsWatcher.setReviewedExpanded` fetches with `PullRequestExtrasLoader.fetch` + `fetchFilesChanged` inside `withFeature('reviews')`, following the pure policy of src/reviewedRequests.ts (`reviewedIdsToFetch` / `reviewedIdsToDrop`, tested). Why: a PR's details cost 4-7 GETs (policies, threads, work item ids, builds, iterations, changes; plus work item types and build test/coverage details, both cached), so fetching them for every listed PR (up to 100 over a month) would multiply the review polling. Closed PRs never change: fetched once, cached for the session (0 per poll). Active ones are fetched on unfold and refreshed at each poll only while unfolded (the poll has just read their threads, so those are reused); folding drops their details so an old copy is never shown. The large layout of the box keeps reviewed PRs folded (it only applies to the waiting ones) so it does not trigger mass fetches. The details have no timeline / time left / bar: the PR is not waiting. They never feed the badge, urgency, Summary or notifications. The webview keeps at most the 50 most recent unfolded ids.
- Boxes (Waiting for your review, My Pull Requests) look like framed panels, deliberately different from the iteration group headers.
- **The PR boxes have no thick left bar; their background and frame colour tell whether they need you, even collapsed.** The 4 px bar is the state bar of the tiles and means nothing on a box. Waiting for your review: red when a required review is overdue, orange when any PR is waiting, neutral when none. My Pull Requests: orange when an active PR needs you (same rule as the tile pulse), blue when there are active PRs (drafts included) and none needs you, neutral otherwise. Completed PRs and the Reviewed list never count. It reuses `countLate` and `needsAttention` (src/panelTone.ts, rules PANEL-TONE-1..2), so it costs no request.
- The PR history popover lists the latest events first.
- **The tiles of My Pull Requests that need the user get a background effect, chosen with `totalflowx.myPullRequests.attentionEffect` (`none` | `static` | `pulse` (default) | `waves` | `shimmer` | `ripple` | `rainbow` | `breathe`; `needsAttention` in `src/myPullRequestsAttention.ts`, effect list and class in `src/attentionEffect.ts`).** The user asked for it: the status bar item says it, but a sidebar that is open should also show _which_ PR it is; first it was a boolean pulse (never released), then the user asked to choose the effect. Triggers: the status-bar "need you" reasons (`attentionReasons`: Waiting for author / Rejected, conflicts, failed or partially succeeded CI, unresolved comments) **plus** the team-rule warnings of the tile (`pr.warnings`), so it is deliberately broader than the status bar item, which ignores rule warnings. Active, published PRs only (drafts and completed ones never get it). Only My Pull Requests: the author is the one who can act on these; the tiles of Waiting for your review have their own urgency bar and pulse, and work item cards are not about a decision of the user. Background only, drawn on the `::before` (and `::after` for `ripple`, which needs two layers) pseudo-element behind the content: the tile's own background, hover styles, green "ready", the left bar and menus are untouched; the pseudo-elements sit inside the padding edge, ignore the pointer and clip themselves (no `overflow:hidden` on the tile, because popovers and menus must not be clipped). Peak opacity 12-20 % so the text contrast holds in dark and light; only opacity, transform and background-position are animated, with slow cycles (2.4-10 s). The colour is the fixed orange `--waiting` (#f0883e dark, #bc4c00 light), not the theme warning colour, which is gold in some themes and would read as a task; `rainbow` is the only exception, because the user asked for it explicitly. A `glitch` effect (brief jitters of offset bands) was offered and removed at the user's request. All motion sits in `prefers-reduced-motion: no-preference`; with reduced motion every animated effect falls back to the static 8 % tint (`static` is exactly that). `none` draws nothing. On by default (`pulse`), unlike the "Working on" card animations (off by default, because many cards would move at once and "here" is only a bookmark): few PRs need attention at a time. Class `attention-<effect>` on `#app` switches it; unknown values mean `pulse`.

## 4. Track board

### Mine + my reviews (phase 5)

- **The board derives each card's column from the track** (`workItemTrack` + `currentStation`, TRACK-9), not from rules of its own, so the sidebar and the board cannot disagree. Only three things are the board's: To start versus Branch · Draft (a not started work item with nothing yet), a published PR whose own station is broken (TRACK-9 points at "Pull request", but the PR is not coding any more, so the column of the next open station: BOARD-4), and the collapse of finished work items.
- **No request and no polling**: the board is built from the store, My Pull Requests and the review requests, and redrawn on their change events (and on settings changes). Opening it while those are still loading shows "Checking…", then the cards as they arrive.
- **The buttons are the sidebar's**: the board posts the same messages and `src/sharedMessages.ts` runs them for both views, so a button never has two implementations. One button per card only where an existing command is obvious (Create branch, Publish, Complete…); Checkout, Open PR, All details and the CI buttons live in the drawer.
- **"Current" is the first row of the Now queue, not the first work item**: reviews come first in the queue (NOW-1: a colleague waits on you), so when a review is overdue its card gets the strong outline, not the work item the design shows it on. A PR whose CI still runs is skipped: you cannot review it yet.
- **PRs to review**: a draft is not shown (the Reviews box does not list drafts, REVIEW-REQ, so the board has no data about them); CI running goes to the CI column when the details of the PR are already known, else to Review. "Your approval completes it" only appears when the review details carry it.
- **The board reads My Pull Requests as the sidebar shows it**: with `myPullRequests.showDrafts` off, the board has no model of the user's drafts, so it offers no Publish (the status line still says "Draft PR …", from the work item's own PR). The runs of a card are the store's (the track reads them, and Show tests / Open run find them by id).
- **Whole team is phase 7**: the board shows a "Mine + my reviews" label, not a switch, until the team data exists. The Sprint timeline tab is phase 6.
- **Left out and why**: "Blocked · #63290 waits on it" (successors that wait on the work item are not in the work item model; it shows the open predecessors and the blocking tags it has), hovering the time of a review for the PR history (the review model carries the timeline but showing it is a separate piece of work; not done), and the arrow keys between cards (Tab moves, Enter opens).
- **The hover summary and the drawer share the card data** (`hover` / `facts` of the model), the strict CSP applies (sizes by CSSOM after the render, the popover is placed with `style.left/top`), and the delay is the common `popovers.hoverDelay` setting.

### A work item with several open PRs gets one card per PR

Work item 67145 has five PRs in flight at once (one failing CI, one ready to complete) plus tasks not started; a single card in Review hid all that. The stations are a PR's journey, not the work item's, so with 2 or more open PRs (BOARD-20) each PR is a card placed by its own track (BOARD-21), the tasks not started are one card and the tasks In Progress without a PR one card each (BOARD-22). Work items with 0 or 1 open PR are unchanged, so the common case stays as simple as before. Merged PRs leave the board (they are one line in the drawer), and the work item only reaches Done when it is finished (BOARD-5), when its cards become one again. Item-level things (rules broken, blocking tags, predecessors, zZ, "here", Checkout) sit on the card of the PR the track follows, not on every card; the Now queue row of a PR points at that PR's card. The sidebar and the details panel keep one track (TRACK-1) with a "+n PRs" suffix (TRACK-10): they are not a board. A PR card's title drops the `[<id>] ` prefix of the naming convention, since the header already has the id.

### Whole team: lanes per person (phase 7a)

- **A lane per person** because the questions of the whole-team view are about people ("who is overloaded, whose review is late, who waits for whom"), and the columns already answer "where is the work". Cards stay the board's own (same split, merged and Completed rules, BOARD-20..25: they are built by the same code, `boardCards`), so the two views never disagree. The user's lane is the full board of Mine + my reviews; the user's reviews are marked on the author's card instead of a separate row, because the question there is "whose work waits for me".

## 5. Sprint timeline

### Mine + my reviews (phase 6)

- **The rows come from the board's cards, one per work item** (`board.work` of `currentBoard`, `src/trackBoard.ts`), not a second selection: a work item split into several cards (BOARD-20) is one row, the one of its primary card, and the finished ones are drawn after the open ones, always (TIMELINE-19; the board is built for the timeline with `showCompleted` on, whatever the board's chip says). The timeline only adds time; the header, the status and the buttons come from the board model, so the two tabs never disagree (the last span of an open PR is what the board says now, TIMELINE-16). The tabs switch from a button in each header (`openTimeline` / `openBoard`); "Open on board" selects the card (`select` message).
- **Which timestamp each moment uses (TIMELINE-16..20)**: the start of the work is the implementation of its first PR (TIMELINE-20), else a task in progress without PR, else `Microsoft.VSTS.Common.ActivatedDate` of the work item (it comes with `GET wit/workitems?$expand=relations`, no request; verified on #66280); the draft ends at the publication (the `IsDraftUpdate` threads, or the stamps of My Pull Requests); CI, votes, pushes and the merge come from the threads and the CI history of the PR; the zZ period from `System.ChangedDate`; a finished work item ends at its last merge, its mark at `dates.stateChanged`.
- **Approximate rather than invented**: when a start is not known (no activation date, or it is later than the PR: the work item was reactivated, no PR dates because the PR is in another repository or is not the user's) the span starts at the first day of the sprint, or the PR's span is drawn as one approximate bar, and its left edge fades; the tooltip says "The start is not known". A start before the sprint is clipped to its first day and also faded ("since before the sprint"). We did **not** call `GET wit/workitems/{id}/updates` for the real history of state changes: one request per work item for a more exact start of a bar did not seem worth the request budget, since ActivatedDate is right for the usual case.
- **Position on the axis is by calendar time of the local day** (the review deadline also counts all 24 hours of a working day, PRIM-2), so a moment on a day off is drawn at the start of the next working day. The sprint is the one the board header and the sidebar strip show (the one that ends first).
- **Request policy (TIMELINE-14)**: no polling, and no history request for a row that is not expanded (TIMELINE-29). The base branch strip uses the 50 runs the store already fetches every minute for the alarm (`baseBranchHistory`), so with the alarm off the strip says so, and it can start after the sprint did. Hidden tabs do not redraw (`panel.visible`); they redraw when shown again. The other request is the threads of the merged PRs (TIMELINE-17), once per PR. Requests are attributed to the "Sprint timeline" feature of the usage report.
- **Work items by station, PRs by lifecycle (TIMELINE-1, TIMELINE-16, TIMELINE-17)**: the first version drew one row per board card and, for a work item with several PRs, a group of rows. That mixed two things: a work item goes through stations (branch → PR → CI → review → ready to be merged → done), but a PR has no stations of its own; it has a life (implementation, draft, review, ready to merge, merged) with things happening in it (pushes, CI runs, votes). So the work item row shows its stations and the PRs, under it, their lifecycle and events. The station of a work item with several open PRs is the one of its **least advanced** PR (it is not shipped until the last one is), except that **needs you wins** (a failed CI or a reviewer who waits must not be hidden behind a draft that was just created: the row of #67145 would otherwise never show it), and when merged PRs leave tasks open it goes back to Branch (TRACK-7). The price is noise: a new draft PR on a work item whose other PRs are in review pulls the whole row back to "PR" for the hours it stays a draft; that is what the rule says, and the expanded row shows why.
- **Merged PRs are faded rows of their work item (TIMELINE-17, TIMELINE-19)**: a timeline is history, and a PR merged this sprint used to vanish from it (it has no board card). They are drawn as faded rows under the expanded work item (not as a one-line count) because they are part of how the work item went: the dates are the same ones as an open PR's. The data is the list of the latest 50 completed PRs of the user that My Pull Requests already has (no request) and, for the history (votes, CI), the same lazy read as the open PRs (TIMELINE-29). Not drawn: PRs merged before the axis (only counted in the state of the row) and abandoned ones. Until the history arrives a merged PR is one approximate review bar (nothing is invented: without a vote event there is no green span).
- **A final state is a point, not a section (TIMELINE-35, TIMELINE-19)**: Done, Closed and Removed last no time: nothing happens in them, so drawing them as a coloured bar up to now gave a long green or grey stripe that said nothing and competed with the work that took time. They are a round badge at the exact moment of the change (✓ Done / Closed, ✕ Removed), with the bar of the previous state ending there, one mark instead of the old "✓ done" text mark, and a tooltip with who did it (`System.ChangedBy` / `revisedBy` of the update, verified on our organization). **Exception**: a Done (or Removed) period that was left (the item went to ReOpened or another open state) lasted real time and explains the ReOpened that follows, so it is a normal bar; only the final finish gets a badge. **Ready to Test stays a bar** with its own colour (a light green, paler than Done: "almost done"; violet is used elsewhere for completed things): it is the finish line of developers for a Bug, but testers can reopen it, so it is not final, and Done was its colour before, which hid the difference. Removed items are not on the board, so the Removed badge only appears where the row is built from another source (a past sprint).
- **Days before the sprint are a maximum used as needed (TIMELINE-2, `appearance.timelineDaysBeforeSprint`)**: a PR often starts a day or two before the sprint (the work was prepared at the end of the previous one) and its bar was cut at the first day, which hid when it really began. A fixed margin would waste a column on every sprint, and a bigger one when no PR needs it, so the axis grows only as far as the earliest drawn PR needs, capped by the setting (default 1, so a PR started three weeks ago does not stretch the whole timeline; 0 turns it off). It is measured on the axis of the sprint alone (a PR merged before the days added is not counted), and in Whole team it takes the PRs of everybody chosen, so every section shares one axis. A guess that "starts with the sprint" still starts on the first sprint day, not in the added days.
- **When the implementation starts is the earlier of the first commit and the linked task, and the developer can choose (TIMELINE-20, `appearance.timelineCodingStart`)**: the work item's activation made every PR of a work item with several PRs start on the same early day (the first PR's), so the bars said nothing about each PR. The texts call it "implementation" (the PR row's first phase and the start of the Branch station); the key of the setting keeps its old name (no backward compatibility is needed, but renaming a user-level setting for a word costs the users their value). Each PR has two better clues: its first commit and the activation of the Task linked to it. Neither is reliable alone: the first commit can come days after the work began (a developer reads, experiments and writes before the first commit), and the task activation depends on how tidy the developer is with states (a task may be activated late or all of them on the first day). The earlier of the two is the best guess of the real start, hence the default; since it depends on how each developer works, it is a personal setting (`application` scope) with `firstCommit` and `taskActivated` as the alternatives (the latter makes no request). Without the chosen source the other is used, then the work item's activation drawn approximate (it says nothing about this PR), then the sprint start. The setting sits in **Appearance** next to `showCompleted`, the other setting of the timeline, since there is no timeline category. Costs one `commits` request per PR drawn, cached (a merged PR for good; an open one by its last merge source commit); the oldest of the pages is taken instead of trusting the order, and at most 500 commits are read, so for a larger PR the start may be too late.
- **Expansion: one click, remembered, and the history is read only for what is open (TIMELINE-18, TIMELINE-29)**: a work item like #67145 has eight PRs, and drawing them all for every work item buries the sprint under rows nobody asked for. A click anywhere on the row expands it (the `#id` opens the details panel instead). Rows whose station needs the user start expanded (so a failed CI is not hidden behind a chevron), but only the user's own: expanding everybody's by default would read the history of every PR of the team on opening. The user's own clicks win and are remembered per work item id in the webview state (UI-only); **Collapse all** is in the header, and there is no "Expand all" because it would read the history of every PR (it could be added with a confirmation if it is missed). The history costs, per PR, one request for the whole run history and one for the threads (none for the user's own PRs: My Pull Requests already has them), so it is read when the row is expanded and the tab is visible, with a soft light sweeping along the row (`aria-busy`, no visible text: near the end of the sprint a message fell off the right edge); the collapsed row is drawn from what is known and its unknown parts fade (TIMELINE-28). Keys are immutable: a closed PR for good, an open PR by its last commit and its votes (both already in the listing), the runs again while one is running (at most once a minute).
- **Conflicts have no history (TIMELINE-27)**: Azure DevOps only has the current `mergeStatus`, so the PR row draws a ⚠ at now for an open PR that has conflicts and nothing in the past (docs/AZURE_DEVOPS.md). A CI run is tied to the latest push by time (it starts after the push; `sourceVersion` is the merge commit and `triggerInfo` has no head commit), which is also what the threads give: nothing else is needed.
- **Left out and why**: "⛓ blocks #63290 (Ana, next sprint)" (successors are not in the work item model; only the open predecessors and the blocking tags are shown); the review rows start at the publication, not at "when you were added" (the review request carries no such date); the develop strip shows the latest 50 runs only.

- **The marks of a PR are one line above its bar, spread sideways** (TIMELINE-30): the first version put marks that would touch on new rows of the strip (the row grew) and the commits over the bar; with every comment, commit and reviewer as its own mark, a busy day stacked them into a tower and the commits hid the phases. One line, with the ones that would touch moved just after each other (in pixels, so it holds at any width), keeps the row height and the bar readable; the exact moment of a moved mark is in its tooltip.
- **Day lines and bursts** (TIMELINE-42): with only the week separators it was hard to tell the day of a mark; a line per day at rest would compete with the bars, so it is barely visible until the pointer is on the timeline. A rebase followed by a forced push makes a crowd of commits and pushes at one moment that pushed the other marks aside; within ten minutes they are one mark drawn thicker (a bigger dot for comments), so a single commit still reads as one and the tooltip lists them all.
- **A PR is dated from its own details when My Pull Requests does not have it** (TIMELINE-17): My Pull Requests lists the user's own latest PRs only, so a PR of another author linked to the user's work item, or an open PR of a past sprint, had no dates ("dates not known") and no history. The store (and the read of a past sprint) already holds each linked PR's details, creation and closing included: no request more.
- **The details of a PR bar are read on hover, with a loading indicator** (TIMELINE-39): the commits of the PR and the history of its Task cost one request each per PR, too many to read for every row, but cheap when only the bar the user points at asks, once, cached by immutable keys. The user must see that something is coming, so a soft light sweeps along the row until the data arrive. No text: a message at the end of the bar falls off the right edge near the end of the sprint, where the NOW line is.
- **The implementation phase of a PR row comes from its linked Task before the PR** (TIMELINE-39): PRs are created once there is code to push and the Task usually exists before, so its "to do" and "in progress" states show when the developer started, even before the first commit. What happens to the Task after the PR is created says nothing about the work and is not drawn. As built, the start of the implementation still follows `appearance.timelineCodingStart` (TIMELINE-20: the earlier of the first commit and the task activation by default), so the setting keeps its meaning; the task adds the hatched "task to do" part before it (from its creation) and names the implementation "task in progress" when it starts at the activation. The design said "no task: start at the first commit"; that is what `firstCommit` does, and `earliest` falls back to the commit too when there is no task, so nothing else changed.

- **The work item row shows its states, not stations computed from its PRs** (TIMELINE-35, TIMELINE-36; replaces "Work items by station" above): the station of a work item with several PRs, each at a different point, had to be computed now and again for every past moment (least advanced PR, needs you wins, merged PRs leaving tasks open), and that was the hardest and most fragile part of the timeline. Merging the PR, CI and Review stations was considered and rejected: the aggregation stays the same with any number of stations, and the board would lose its Review bottleneck and the timeline the time spent waiting for reviewers. The states have a history of their own (one request per work item, cached by revision); the detail of the PRs is in the PR rows. In review is derived (STATE-10), so its past is approximated by the publication of the first PR. The station of the work item **now** is still computed (it is cheap and already tested) only to say after the bar what the work item needs from the user ("needs you · CI failed in PR 14021"): a state bar alone would hide it. The state history is one `updates` request per work item, keyed by `System.Rev` (which comes with the work item already read), so a work item that does not change is read once per session; until it arrives the bar is guessed from `StateChangeDate` (exact for the state now) and the activation (approximate). The others' work items in Whole team cost the same, which is the price of drawing everybody the same way.

- **The legend of the timeline is closed by default** (TIMELINE-34): once learned it is not read again, and two always-visible rows of it took the height of two work item rows.

- **The timeline keeps the PRs the user already reviewed** (TIMELINE-37): the timeline is also the history of the sprint, and the reviews done are part of the user's work, so they stay as faded rows like the finished work items. This is one more reader of the reviewed PRs, still display-only: the rule "Reviewed is display-only and kept apart" (PRs tab) is about counting and notifying, which the timeline never does. The moment of the vote is the **first** vote of the user (when they reviewed it; later votes are re-reviews), and the mark has the colour of that vote. The active PRs and their threads come from the review poll, so they cost nothing more; the closed ones need the listing the Reviewed section already uses (read for the timeline even when that section is hidden, at most every 10 minutes) and one threads request per PR, once.
- **The develop strip marks every merge** (TIMELINE-38): its point is to see when the CI broke and which merges came just before. Since 2026-10-22 the develop pipeline runs as batched CI: a run carries no "Merged PR n" message (`triggerInfo` is empty), only the `sourceVersion` it built, so the runs cannot say which PR was merged when. The timeline therefore reads the commits of develop within the axis (the squash commits "Merged PR n: …"), only while its tab is open and the develop bar is shown, not in the store (the store polls with the tab closed). The key is the axis, plus the `sourceVersion` of the newest run for the current sprint: a new run is a new head, so the commits are read again, with no polling of their own; a past sprint is read once. A failed read changes nothing: the ticks fall back to the merge messages of the runs (only the old individual CI runs have them). A batched run covers several merges, so the culprit above a red span names the merges between the commit of the previous run and the one of the run that turned it red ("PR 14002 +2 → red"). Still on the PR of the runs, and so silent with batched CI: the "broken … · after PR X" label and the texts of the develop alarm (BASE-CI).

- **The timeline always shows the finished work and the merged PRs** (TIMELINE-19; the Completed chip left the timeline, it stays on the Track board): a timeline is the history of the sprint, so hiding what was done only removes part of the story; on the board, a work surface, hiding the finished cards still makes sense.

- **The timeline shows only the current sprint** (TIMELINE-2; "This + next sprint", its planned rows and the "spills over" projection, TIMELINE-10, were removed): the work is planned and reviewed sprint by sprint, and the next sprint added a query, planned rows and a projection for little use; focus on the sprint in progress first.

- **The timeline can show the 4 sprints before the current one** (TIMELINE-40, TIMELINE-41): looking back a few sprints (what was carried over, how long reviews took, when develop broke) is enough for a retrospective; more would cost requests for little use. Past sprints are read only when opened, and once. They are read **as they were when they ended** (`ASOF` in the WIQL, `asOf` on the work items): on the first day of a new sprint the unfinished work items have already moved to it, so a plain query of the old iteration would show the sprint emptied. The end is the end of the last day in UTC: verified on Sprint 122, the team moves the unfinished work items and tasks on the first morning of the next sprint (14 Oct 08:48 UTC), after that moment, so they are still in the sprint that ended (see AZURE_DEVOPS.md). A team that moved them before the end would see them missing; the moment is easy to change in `asOfMoment`. The work items are shaped with the whole-team code (TEAM-5: no alerts, no branches, no CI details): a past sprint is history, there is nothing to act on, and it avoids a second copy of the store. In Whole team the people chosen are read the same way (one query for all of them, their tasks and their linked PRs), once per sprint and set of people: the design draws the sprint switch on the Whole team boards too, so a past sprint is not only the user's.
- **The header of the timeline is made of icons, and what it shows is switched in View options** (TIMELINE-45, TIMELINE-46): the labelled buttons took a large part of the header. Icons keep it on one line; their name is in the tooltip and the `aria-label`. People N ▾ keeps its label: it is a picker with a count, and a third people icon next to Whole team would be ambiguous. The Track board / Sprint timeline buttons were removed from both headers: each view opens from the sidebar and its command, and they cost room for a jump that is rarely needed (Open on board stays in the popovers). REVIEWED BY YOU, the DONE and MOVED OUT groups and the develop bar are useful to some and noise to others, so each is a personal switch (settings, `"scope": "application"`) rather than a team decision; when DONE is not grouped the rows follow the order of the work items of the sprint (the sidebar's), since the board order would still put the finished ones last. Dimming the completed rows is a setting, not a switch: it is a matter of taste set once, and the user who asked for it does not like the faded rows while others may. The rows moved out of a past sprint stay faded either way: they are not the sprint's work any more.
- **A past sprint shows every work item that was in it, not only those still in it at the end** (TIMELINE-43, TIMELINE-44): the team cannot always plan the whole sprint before it starts or on its first day; work items are often added while it runs, and some leave before it ends (replanned to a later sprint, sent back to the backlog, reassigned). Reading only what was there at the end hid both. WIQL `EVER` gives the candidates, but each condition matches any revision on its own (the path in one, the assignee in another, even before the sprint started), so the updates of each candidate decide: it counts only if it was in one of the sprint's iterations **and** assigned to a person shown at the same moment within the sprint. That costs one request per candidate (16 for the user on Sprint 123, against 5 at its end), once per sprint opened; the same updates give the states of the rows, which the timeline would read anyway. A work item that left is read as it was just before it left (its state, its assignee then), so it lands in the section of the person who had it. Where a work item went is told by a pill ("→ Sprint 124") rather than by drawing it in both sprints: the bar is the time it spent in this one. If WIQL ever refuses the query, the sprint falls back to what was in it at the end (TIMELINE-41) rather than to an error.

- **Each view of the timeline has its own row style, Normal or Compact** (TIMELINE-32, TIMELINE-33): the user's own work is read in detail (Normal by default), the whole team is scanned (Compact by default, many people on one screen); the user can change either. The row style only changes the size: in both, the PR bar shows at rest its phases and the problems the user must act on (the latest CI run failed, conflicts now), and everything else on hover. A problem must not depend on the user pointing at the right bar; the history (earlier runs, auto-complete, commits, comments, votes) would be noise at rest.

- **The timeline reserves 2 days after the sprint for what follows the bars** (TIMELINE-31): near the end of the sprint the NOW line reaches the right edge and the notes and buttons after the bars had no room; the code moved them over the end of the bar, hiding exactly what is happening now. A fixed column on the right was tried and rejected (it looked like a separate table and took 200 px); a margin of 2 days costs less (each day is 1/12 of the width instead of 1/10) and keeps the text next to its bar.

- **After the sprint, open bars keep running, faded** (TIMELINE-31): stopping them at the end of the sprint hid that the work is still going on; running them at full colour put the text on top of the bars, and pushing the text after NOW left it no room. Faded under the hatch of the margin, the bars show the work goes on and the text over them stays readable.

- **The footer is the only loading indicator, and there is no progress bar (TIMELINE-50)**: a timeline loads in many small pieces (the sprint, each person, the history of each PR, the states of each work item) that finish at different times, so a bar under the header would either lie about a total nobody knows or jump back. The footer says what is being read now ("Loading the PR events of 3 PRs…") with a spinner, stays visible at the bottom whatever the scroll, and is the same in Mine and Whole team. Where the data will appear the rows are skeletons (first load, a person not read yet) and PR rows have their own sweep, so the shape of the page does not jump when the data arrives. Motion stops with `prefers-reduced-motion`.
- **Zoom changes the width of the days only, and it is saved (TIMELINE-48, TIMELINE-49)**: the rows already have the height their two lines and the strip of marks need; making them taller or shorter helps nothing, while a wider day is what separates events that fall in the same hours. It is a personal setting (`appearance.timelineZoom`), shared by both views and every sprint, so the timeline opens as the user left it; the webview draws the new zoom at once and writes the setting after 1.5 s of quiet (remembering the zoom is not urgent, nobody closes the panel right after zooming) because the wheel and repeated presses fire many steps. **Root cause of the "jumps and recalculation after zooming"**: the write fired `onDidChangeConfiguration`, which rebuilt and re-posted the model (and redrew the board, the sidebar…), and the webview redrew everything and took `model.zoom` back: with rapid presses the echo of the first write (an older value) arrived after the next press and moved the zoom back, then forward. Now the extension ignores the change event of a value the webview wrote itself (`isOwnZoomChange`), the webview never redraws to zoom (it changes `--tl-day-min`, the marks and the scroll only) and takes a zoom from a model only when it changed elsewhere and no write or animation is pending. The other switches of the timeline (view options, density) are single clicks and keep redrawing the tab. The label column is made sticky (it spans its row so a sticky item can leave its grid cell), so a zoomed timeline stays readable.
- **The wheel zooms with Ctrl by default, Shift on request (TIMELINE-49)**: Ctrl + wheel is the zoom gesture of browsers, maps and editors, and a trackpad pinch already arrives in Chromium as a wheel event with `ctrlKey`, so one handler serves both (small deltas add up). Shift + wheel was the first choice, but it is the usual sideways scroll on a mouse, so it stays as an option (`appearance.timelineZoomModifier`). Only the chosen key zooms, and the event is cancelled (non-passive listener) so neither the page zoom nor the sideways scroll happens. VS Code's webview forwards wheel events to the editor, without the modifier keys, for its own `editor.mouseWheelZoom`; this was read in the code of the webview host, not tried with a real VS Code. The maximum zoom is 1000 %: a 14-day axis is then about 9000 px wide, which the marks and the scroll anchor handle
- **The pinned columns cover everything under them (TIMELINE-48)**: the sticky headings were as wide as their text, and the cell of a row stopped 1 px short of the line between rows, so the NOW line, the hatched margins and the NOW flag showed beside or between pinned cells. Every pinned cell is at least as wide as the label column, opaque, and draws the row line itself; the NOW flag sits inside the header row, not half below it
- **The minimum zoom is "fit", and only the buttons animate (TIMELINE-49)**: at 100 % the days already stretch (`1fr`) to fill the panel, so zooming out from there changed nothing while − stayed enabled down to 50 %. The lowest useful zoom is the one where the whole axis fits the lanes, measured in the webview (the panel width is only known there) and followed with a `ResizeObserver`; the stored setting may stay below it, so the same setting works in a narrow and a wide panel. The buttons animate the change in 150 ms because a jump of the whole grid loses the reader's place; the animation moves the CSS variable `--tl-day-min` with `requestAnimationFrame` (CSS transitions on a grid with percentage-positioned children do not keep the anchor, and the marks of the PRs are placed in pixels, so they are re-placed every frame) and updates the scroll on every frame so the centre of the visible lanes stays put. The wheel stays instant: an animation per step would lag behind the hand and fight the next one; its events are added up and applied once per frame. The buttons are disabled while an animation runs (and the layout after it), so a rapid series of presses cannot pile up animations. Steps are relative (× or ÷ 1.25 of the zoom drawn): with fixed steps, a stored zoom below "fit" made the first press go from fit to the next fixed step, a change of a few percent.
- **A note after a bar starts where the bar ends (TIMELINE-17)**: a bar is never narrower than its padding and its text, so the last bar of a PR merged shortly after its last vote was drawn wider than its days and covered the "✓ merged" note, green on green. The note is placed in pixels after drawing (like the marks) and again after every zoom and resize.
- **The margin after a past sprint looks like the one before it (TIMELINE-31, TIMELINE-41)**: the margin after the sprint had a 55 % wash over the bars and its bars at 22 %, the margin before had neither, so the same PR looked washed out on one side. In a past sprint the work in the margin is history, not "overtime", so both sides use the hatch only and full-opacity bars. The strong fade stays in the running sprint, where it is the signal that an open item runs past the end. An open PR of a past sprint was also drawn only up to the end of the sprint (its `now`) while its events kept going: now it runs to the end of the axis, or the real present if earlier.
- **A click on an ASLEEP id flashes its row (TIMELINE-51)**: the footer names the asleep items but they may be far from the screen; the id scrolls to the row and highlights it for 1.5 s with the look of the duplicate highlight, so one visual language means "this row".
- **What stops a PR in review, after its bar (TIMELINE-52)**: a PR in review sat there with no hint of why it was not merged. The note is hidden when a button or a NEEDS YOU station already says what to do (the bar and the button win, two messages for one thing is noise). The user's PRs reuse the sidebar's "Next" line; the PRs of others have no policy evaluations (they cost a request each), so their note is built from the reviewers, the conflicts and the CI only and may miss a policy such as a minimum number of approvers or unresolved comments.

### Whole team (phase 7b)

- **Others' implementation starts at the task activation, never the first commit**: the first commit is one request per PR; for everybody that is too many. The linked task is already in the batch of children. The publication date is the creation unless TEAM-6 read the threads, and their PRs are drawn without threads until the user expands the row (approximate phases, no green span); then their threads and CI history are read like the user's (TEAM-8). Rules TIMELINE-22, TIMELINE-24.
- **The user's reviews stay in the user's section**: the PR of someone else you owe a review on is also marked on that row ("your review 5 h"). Rule TIMELINE-23.
- **No "At risk" footer** (an early design had "4 items cannot reach Done before Tu 27 at the current pace"): it needs a prediction of the pace, and the data for it (effort, daily updates) are not reliable enough; a precise-looking number that turns out wrong costs trust. The ASLEEP footer covers most of the need with facts.

- **"PR events always visible" loads only the visible PR rows and shows their marks at rest (TIMELINE-39, TIMELINE-45)**: the details of a PR (commits, task history, threads and CI) cost requests per PR, and a busy sprint draws dozens of expanded PRs. The switch posts the same `hoverPullRequest` message as the first hover, only for the rows that are drawn and intersect the viewport (an `IntersectionObserver`), once per PR and tab; scrolling reveals the rest. Reading all of them at once would burn the request budget for rows nobody looks at. Off by default for the same reason. The marks other than the problems are hidden at rest by CSS (TIMELINE-33), so loading alone showed nothing and the switch seemed to do nothing: with it on, the grid has the class `marks-always` and every mark is visible.
- **Duplicates are highlighted from data already read (TIMELINE-47)**: the Duplicate relations come with `$expand=relations` and the related items are loaded for the alerts, so the highlight makes no request. "Not in this view" is decided in the webview from the rendered rows, because only it knows what the current scope, sprint and options draw.

## 6. Dependency map

### Dependency map

- **Iterations are `<Project>\<Release>\<Sprint>`**: depth 1 = limbo (ignored, counted in a note), depth 2 = release container ("not scheduled in a sprint yet" column after its sprints), depth ≥ 3 = sprint.
- **Columns are sprint periods** (same start/finish dates), with one lane per team sprint, always in the same team order; different date ranges get their own columns. Do not compare iterations by the container's dates (a release starts long before its sprints).
- **Risk**: done → grey; predecessor in a release or limbo → "not scheduled yet"; same sprint period (even different teams) → tight; later period → late; earlier → ok. The same rule drives the cards' open-predecessor warnings and the Work Item Details panel.
- **Done work items are always shown** (the "Hide done" option was removed): hiding them cut the chains and made the arrows of the remaining work items look unexplained. What matters at a glance is handled by the dashed grey arrows and the state colours; "Hide bugs" and "Sort by state" cover decluttering.
- **The border of a card is coloured by state, its ID by type, as in the sidebar** (the whole border, 3 px on the left, so the state reads at a glance on small cards; ID colours from `typeIdClass`). My work items used to have a blue frame; the state border took its place, so they are told by the highlighted **Me** of the footer. `media/dependencies.css` is loaded after `webview.css`: a border colour set on `.node` alone overrides the `state-border-*` classes (that bug made every card grey), so `.node` draws its border in `--bar`, set per state in `webview.css`.
- **Priority** (1 critical … 4 very low, `Microsoft.VSTS.Common.Priority`) is a pill in the card header with the same solid colours as the sidebar. **P1 work still to do glows in red** (not finished ones: the emphasis is about not missing critical work; they keep the pill): only a red halo **behind** the card (`box-shadow`), as if lit from behind, inspired by the lit cells of the UniFi UI. The card itself is unchanged (no red border or tint: the user preferred this to a thick outline and then to a tinted card), so it keeps its state border. It is also the **tie-breaker of the ordering**: when two work items weigh the same, the higher priority goes first (P1 … P4, then no priority), then the ID.
- **Ordering of a lane** (pure, `layoutGraph`): barycenter, 8 sweeps alternating left→right and right→left (a single direction leaves the last columns unsettled), the weight of a card being the average **vertical position in pixels** of its neighbours (card centre, lane headers and gaps included), not its row: lanes of different sizes in different columns would skew a row index. Deterministic: ties by priority then ID; the result does not depend on the order of the input.
- **Sort by state** (off by default) groups each lane by state in this order: in progress (Committed, In Progress, Active), not started (New, Approved, To Do, and any state we do not know: the `proposed` category), finished (Ready to Test, Done, Closed…), removed. Rationale: **active work first**, finished work is context. Inside a group the line-straightening order applies, so with the option on some arrows cross more: that is the price of the grouping.
- **Hide bugs** (off by default) hides Bug work items and their arrows; the focused work item is never hidden. It is applied **before** the "without dependencies" rule: a work item whose only links were to hidden bugs has nothing left to show, so it is hidden too unless "Show work items without dependencies" is on (the point of hiding bugs is to declutter, and a lone card would look like a work item with no dependencies at all). The "+N" count still includes dependencies that are bugs.
- Work items without dependencies are shown on demand.

## 7. Status bar & notifications

### Status bar, badge and Summary view

- **The CI status bar item is labelled `CI` and ordered by severity; canceled runs are only in the tooltip.** The rocket icon looked like one more run state, and the order (failed, partial, running, queued, succeeded) puts first what needs the user. A canceled run (usually replaced by a newer push or stopped by hand) asks nothing from the user, so it only adds noise to the text; it stays in the tooltip with its icon and totals. When canceled runs are all there is, they are shown so the item is not empty (`ciStatusText`, src/pipelines.ts; STATUSBAR-CI-\*).
- **The CI runs use colour emojis, not codicons** (`STATE_ICONS`, src/pipelines.ts): the status bar can only colour a whole item, not one codicon, so ✅ and ❌ make a failure easy to tell from a success at a glance, in the item, its tooltip and its picker alike. Running keeps the animated `$(sync~spin)` codicon: the motion says more than a colour. The section titles of the tooltip (AFTER MERGE, RUNS WITHOUT A PULL REQUEST) are in capitals so they read as section labels, not as one more PR.
- **The colour of the CI item follows the checked out branch** (STATUSBAR-CI-3/9): it answers "how is the branch I am working on?", while the counts and the tooltip keep the overview of every run (a failure of another PR no longer turns the item red). The state is the most severe one of the branch's PR runs, else of its manual runs; merges never count. VS Code allows only two fills on a status bar item (`statusBarItem.errorBackground`, `statusBarItem.warningBackground`; any other background is ignored), so failed is red and partially succeeded orange, and the other states tint the text with contributed colours (`totalflowx.ci.*Foreground`, pale defaults in light themes because the light status bar is a saturated blue). No webview: the API has none for status bar items or their tooltips.
- **The status bar item of the current work item shows the ID alone by default, with the icon and colour of its type** (`src/currentWorkItem.ts`: `statusBarText`, `statusBarTypeIcon`, `statusBarTypeColor`). With the title it took a lot of space next to the other items; the ID plus the type icon is enough to recognise it, and the title is in the tooltip. `workingOn.statusBarLabel: idAndTitle` brings the title back (personal choice, `application` scope). The status bar only renders codicons, not the SVG icons of the sidebar, so the closest ones are used (book, bug, tasklist, trophy for Features, crown for Epics, issues otherwise), and `color` tints the whole item (icon and text cannot have separate colours). The colours are contributed (`totalflowx.workItemType.*Foreground`) with pale light-theme defaults, for the same reason as the CI colours. The branch icon of the user's own work items was replaced by the type icon; work items of other people keep the eye in front.
- **The status bar lists every work item linked to the branch, closest iteration first, at most `workingOn.statusBarMaxItems` (3) then `+N`** (Rules STATUSBAR-WI-1..6, `src/branchWorkItems.ts`). One branch often serves a PBI and its tasks, or a bug fixed with a story, and the item used to show only the one in the branch name, hiding the rest of what the user is working on. The linking is the same as the sidebar's "linked work items" (`workItemsOfBranch`, WORKON-1/2) so both agree. The order puts the current sprint first because that is the work that matters now; a past and a future sprint at the same distance: the future first, since upcoming work is more useful than finished work; Done work items stay in the list, as they are part of the branch. A Task is dropped when its parent is in the list too: the parent already represents its tasks, so showing both is noise and would use up the `+N` slots (the parent id comes from the work item's relations, no extra request; a Task with an unknown parent stays). N is configurable because the status bar is shared with other items. A status bar item has a single colour, so it takes the one of the first work item's type (the icon still tells the type of each ID). For a colleague's branch only the named work item and the ones of the active PR are fetched (4 requests, cached 5 minutes per branch): finding Development links of work items outside the list would need a query per branch, too much for the request budget.
- **The CI tooltip has one block per PR, the PR of the checked out branch first** (`src/ciTooltip.ts`, STATUSBAR-CI-5/7). The flat list (run line, its failures, then the PR title) made it hard to tell which lines belonged to which PR: now the header (PR link + title) comes first, the runs are indented below it, and a rule separates the blocks. Indentation uses `&nbsp;` because four leading spaces would make a Markdown code block in the hover. Titles and test names go through `appendText` (escaped).
- **Runs without a PR and runs after a merge are shown in their own sections, only the user's own** (STATUSBAR-CI-6/8). Manual runs (`reason=manual`, e.g. an experiment branch) are requested for the user (`requestedFor`). Post-merge runs on develop are **matched by the PR number** in `Merged PR <id>:` against the user's PRs (active and completed, from the My Pull Requests poll), not by `requestedFor`: that is whoever completed the PR, which may not be the author. Other CI pushes are ignored. A manual run on a branch that has a PR stays with the manual runs: it is a different build from the PR validation. Window: 24 h (`totalflowx.pipelines.branchRunsHours`, 0 = off), so old experiments do not stay forever. Cost: 2 requests (the push one is skipped when the user has no PR), every 15 s only while one of these runs is active, otherwise at most once a minute, even while PR runs keep the fast polling going. They count in the status bar item (a failure there needs the user) but not in the Summary "failed CI runs" row, which stays about PRs (SUMMARY-5); their coverage is not recorded (records are per PR).
- **A separate status bar item for the user's own PRs that need them** (`src/myPullRequestsStatusBar.ts`, pure logic in `src/myPullRequestsAttention.ts`). Why separate: the review item is about other people's PRs and its colour follows the 24 h rule; the own PRs have different reasons and a different colour logic, and each can be switched off (`totalflowx.myPullRequests.showInStatusBar`). It reads the same models as the sidebar (`MyPullRequestsWatcher.models()`), so it costs no request. Which reasons count (active, published PRs only): Rejected, Waiting for author, conflicts, failed or partially succeeded CI, unresolved comments. Not counted: missing approvals or running CI (nothing to do but wait), drafts (work in progress) and PRs that complete by themselves. "Ready to merge" is shown too (good news that still needs an action: complete the PR) but never colours the item. Colour: red when something blocks the PR and only the author can fix it (rejected, conflicts, failed CI); yellow when it is a request or a chore (waiting for author, unresolved comments); default for ready only (STATUSBAR-MYPR-\*).
- **The status bar tells the main folder from a worktree** (WORKTREE-WINDOW-1, src/worktreeStatusBar.ts). Worktrees open in their own windows, which look identical; committing or running `npm` in the wrong one is easy. The item is shown in both ("main" is the reassurance), but only the worktree gets a background colour (`statusBarItem.warningBackground`): the exception must stand out, not the usual case. The main folder is the first entry of `git worktree list` (the one with the real `.git`), the same rule as WORKTREE-3. One `git worktree list` when the repository opens, because the store only lists the worktrees after its first Azure DevOps load; afterwards it reuses the store's list. No request.
- **Stale worktrees get a Summary row but no badge, and one notification ever** (SUMMARY-10, WORKTREE-NUDGE-1). Cleanup is housekeeping, not urgent: the badge stays for what blocks the team. The notification is sent once per folder + branch, stored per main repository so other windows do not repeat it; the first check ever only records a baseline (no flood on install) and waits until the work items, both PR lists and git have answered once, and a worktree that looks in use for a while (a source failed) is not notified again. It is not added to the "PR merged" offer of the notifier (as first planned): that offer only exists for the user's own PRs, while the worktree one also covers reviews, abandoned PRs, closed work items and deleted branches, so it lives in the tracker. To avoid two notifications for the same merge, a worktree whose only reason is the merge of one of the user's PRs is left to the notifier's **Delete branch**, which removes the worktree too (WORKTREE-NUDGE-2). "No longer active" for an origin PR (WORKTREE-STALE-4, WORKTREE-STALE-8) covers what the lists cannot say: the user's abandoned PRs are not fetched and old completed ones drop out of the page.
- **The activity bar badge lives on the native "Summary" tree view, not on the webview view.** VS Code creates (resolves) a webview view only when it is first shown, so on a cold start there is no `WebviewView` to set `badge` on until the user opens the sidebar. A `TreeView` made with `createTreeView` at activation exists immediately, so `src/summaryView.ts` sets its badge (work items with alerts + PRs waiting for review, `src/summaryRows.ts`) at startup and on every change of the store and the watchers. The webview view must not set a badge too: the container would show a double count. Whether the badge of a _collapsed_ tree view reaches the container icon must be confirmed in a real VS Code.
- **Status bar order is fixed by priorities** (`statusBarOrder.ts`, STATUSBAR-ORDER-1): alarm 1000, place 990, work item 980, CI 970, reviews 960, my PRs 950, to fix 940. All stay on the left, as before: the right side is crowded by VS Code and other extensions, and the design reads left to right. Without explicit priorities the order depended on the creation order, which is not guaranteed. A side effect: our items now sit left of items with a lower priority (e.g. the git branch).
- **"N to fix" is the former "N work items" item** (it already existed, ALERT-SHOW-5): same data (work items with alerts), renamed to the design's wording, warning background instead of error (the red ones are the alarm, CI failed and a review overdue; a team-rule alert is not an emergency) and its click opens the Work tab instead of just focusing the view. It has no setting, as before: it is hidden at 0.
- **Moods use only the two backgrounds VS Code allows** (`statusBarItem.warningBackground` / `errorBackground`): calm = none, attention = warning (a review due soon, a PR that waits on you with warnings), alarm = error. Foregrounds are left to the theme.
- **"My PRs that need me" in the Summary counts what the Now queue calls unblock** (NOW-2) instead of only the PRs with warnings, so the Summary, the queue and the status bar describe the same PRs. The "ready to merge", "failed CI runs" and cleanup rows keep their rules.

### Broken base branch alarm

- **A broken base branch raises an alarm you cannot miss** (`src/baseBranchHealth.ts` pure, `src/baseBranchAlert.ts`; BASE-CI-\*; `totalflowx.pipelines.baseBranchAlert`, on by default). Team rule: develop must always be stable, and a red develop must be fixed before anything else, whoever broke it. So it is not limited to the user's own merges like the AFTER MERGE section (STATUSBAR-CI-8). Choices: (1) **its own query**, `branchName=refs/heads/<base>` on the open repository, last 50 runs of any reason and **no time window**: the push query of STATUSBAR-CI-8 is skipped without own PRs, turned off with `branchRunsHours: 0` and limited to 24 h, and none of these may hide a develop broken three days ago; schedules and manual runs on develop count too (it is develop's code). (2) **Broken = the last finished, not canceled run of a pipeline is failed or partially succeeded**: a running run (maybe the fix) and a cancel never clear it, only a succeeded run does. (3) **The culprit is the first failure after the last green run**, not the latest failure: a later merge that did not fix it did not break it. A **re-run of the failed jobs keeps the build id** and makes the build active again: it keeps the state it had at the previous fetch (`finishedStates`), otherwise a re-run of the breaking build would turn develop green or move the culprit and show the modal again; after a cold start during a re-run there is no previous state, so develop looks green until the re-run finishes (accepted). **Known limit**: the 50 runs are shared by every pipeline on develop, so a rarely run pipeline (a nightly) can fall out of the window after more than 50 runs of the others and read as green; `maxBuildsPerDefinition` may fix it, to verify with real data. (4) **Pipelines with no run on develop for 14 days are ignored** (a pipeline that no longer runs there would keep the alarm forever) and a team can list pipelines to ignore (`baseBranchIgnoredPipelines`, e.g. a flaky nightly). (5) **Request budget**: one request at most once a minute with the CI polling and on each load; develop runs never make the polling fast (develop runs after every merge of every team, and every fast tick also refetches all the followed PRs), so the alarm comes within about a minute; only the failing runs get their details (cached by build id). (6) **Four layers**: a red status bar item, leftmost, that stays until green (no dismiss: the alarm ends when the branch is fixed); a **modal** dialog, the only VS Code UI that cannot be overlooked, **once per incident** (pipeline + breaking build), remembered in the global state before it shows so the other windows (worktrees open their own) and reloads do not show it again; it is triggered from the state, not from a run that just finished, so a develop broken while VS Code was closed is announced at startup; never awaited, so the polling goes on while it is open; no reminders: the status bar item is the reminder. A red banner at the top of the sidebar (with the clock time it broke, not an elapsed time: the webview only renders when the state is posted, so an elapsed time would go stale) and the first Summary row (+1 on the badge, which shows without opening the sidebar). (7) The modal is blunt ("Your merge broke develop") only when one PR broke every new incident and it is in My Pull Requests; otherwise it is the neutral text, also while that list is not loaded. (8) **The siren is not a fun feature**: its own setting (`pipelines.baseBranchAlarmSound`, `application` scope, on) instead of `fun.sounds`, which is off by default; square waves, two tones, about 1.8 s. Like the other sounds it only plays while the sidebar is visible (whether a webview may play audio without a click must be confirmed in a real VS Code). Not done: an editor tab that opens by itself (too intrusive for now) and OS-level notifications (VS Code has no API; spawning a Windows toast from WSL is fragile).
- **"I'm on it" is local** (BASE-CI-11). Azure DevOps has no place to say it and the team shares no state of this extension, so writing it anywhere would invent a feature that needs new requests. It is kept in the global state per organization / project, by incident (pipeline + breaking build), so a later failure of the same red streak stays acknowledged and a new break does not. The alarm has no repeating sound or modal to silence (both fire once per incident), so what it changes is the banner: it shrinks to its title and "You're on it". The banner stays while the branch is broken. The modal button does the same.

### Notifications

- **The notification of a finished run names the PR by its title and links its work items** (`finishedRunMessage`, `src/runDetails.ts`): an id alone does not say which PR it is. The work items are Markdown links in the text (`[#1234](command:totalflowx.openDetails?[1234])`), which VS Code notifications render and run, rather than buttons: a PR can have several work items and buttons are kept for actions on the run (Open Run, Show Tests). They come with no extra request: for the user's own PRs the work items Azure DevOps links to the PR (already fetched for My Pull Requests), else the work items of the list (and their tasks) that link the PR. The title comes from the PRs the store already knows; without one the notification shows only the id, as before.
- **Reviewer/vote notifications ignore the user's own actions**; reviewer changes are attributed from the `ReviewersUpdate` system threads.
- **Left out on purpose**: the notification "PR N passed: 95 tests, coverage 87% ▲ 3.2." already exists (CI run notifications, same data); "Your approval completes it" in the due soon notification would need the number of approvals still missing, which the review model does not carry, so the text says only that the PR is due; the "Set Done + delete branch" button deletes through the existing Delete branch flow, which still asks for confirmation when needed.
